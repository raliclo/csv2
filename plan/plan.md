## 為什麼值得做

不是因為缺少一個 CSV 工具，而是因為**這個 repo 已經被天真的逗號切割咬過**。

`TARGET_PACKAGES.csv` 的 `status_notes` 欄含有帶引號、內有逗號的敘述文字。就在
2026-08-15，一支用 `${line%,*}` 切欄位的腳本改寫了那些註記的中段——它「成功」執行、
回報了變更清單，而清單裡的舊值是半句話。檔案是從 git 還原的。

同一天 `artifacts.csv` 也被寫壞過一次：一個 commit 字串被寫進了 `built_utc` 這個
時間戳欄位，沒有任何東西報錯。

這兩次都不是 CSV 格式難懂，而是**沒有工具可用**，於是每個人都用 `cut -d,` 和
`${line%,*}` 自己來。這支工具的存在意義是讓「正確處理 CSV」比「隨手切逗號」更方便。

因此第一個需求不是效能也不是功能數量，而是：**RFC 4180 的引號、內嵌逗號、內嵌換行、
CRLF、BOM 必須全部正確**，且錯誤要明確失敗而非靜默產生半對的輸出。

### 但在本專案內，只有測試腳本可以呼叫它（2026-08-18）

上面那兩次事故發生在母專案的 host 端腳本裡，而那正是這支工具被寫出來的理由。即使如此：

> **母專案的建置與維護腳本不使用 csv2。只有測試腳本可以。**

理由是相依性方向：`update_licenses.zsh` 這類腳本必須能在「csv2 尚未建置」的環境下執行，
而把它們接上 csv2，等於在母專案的流程前面插入一個建置步驟。csv2 又刻意不進 guest
rootfs（見「目前不進 rootfs」），因此那個相依在某些環境下根本無法被滿足。測試腳本沒有
這個問題——它們本來就在「已經建好 csv2」的前提下執行。

這條界線要記在此處，因為它與上面那段動機讀起來會像互相矛盾：事故催生了這支工具，
而這支工具目前不去修那些事故發生的地方。兩者都為真，只是「可用」與「被採用」是兩件事。

**對評估的影響：** 不要把「沒有真實腳本採用它」列為缺口或待辦。它仍然構成一項限制——
csv2 的驗證全部來自它自己的測試——但要取得非自身視角的證據，用的是換平台（第 6 階段）
與換讀者（`read_easy`），不是接一支真實腳本。

### 為什麼不叫 `csv`

原本指定的是 `csv`，改成 `csv2` 同時解決兩件事。

**`csv` 無法搜尋。** 這三個字母在本 repo 的腳本裡出現 **93 次**、49 個檔案提到它——
因為到處都是 `.csv` 副檔名、`artifacts.csv`、`TARGET_PACKAGES.csv`、`checksum.csv`。
相較之下 `swift_tar` 出現 127 次，而那 127 次**全部都是指那支工具**。日後要查「誰呼叫
了它」「這個旗標用在哪」，`grep -rn csv` 幾乎全是雜訊。這個專案的除錯高度依賴 grep，
所以不是理論上的不便。

`csv2` 沒有這個問題：它不會出現在任何副檔名或既有檔名裡。

**PATH 上的靜默碰撞。** `csv` 是任何人都可能取的名字（Python、npm、Homebrew 都有）。
裝了第二個之後，決定跑哪一支的是 PATH 順序，**不會有任何提示**。`csv2` 撞名機率低
得多。

（`csv` 本身**不是安全問題**——POSIX 沒有定義它，這台機器上也沒有同名執行檔，已查證。
它不遮蔽任何東西。）

而 `2` 剛好也說明了格式：**兩列標頭**。

**repo、submodule、執行檔、副檔名一律都叫 `csv2`。** 這與 `swift_tar` 的命名慣例不同
（那裡 repo 與執行檔都是 `swift_tar`，但格式是通用的 tar）；此處四者同名是刻意的，
因為它們指的確實是同一件事：一個格式，以及讀寫它的工具。看到 `foo.csv2` 就知道要用
`csv2` 讀。

**Submodule 規則與 dependency 不同。** CLAUDE.md 的 fork 規則（`origin` = 上游唯讀、
`ralic` = 我們的 fork）是為「別人的程式碼」設計的。`csv2` 是我們自己的，沒有上游，
因此：

```
origin = https://github.com/raliclo/csv2.git    （唯一 remote，可推可拉）
```

與 `sos/kernel`、`render/*` 那種「無修改、單一 origin」不同——它們的 origin 是別人的。
這是第三種情況。母專案的 CLAUDE.md 原本沒有涵蓋，**現已補上**（見其「Submodule
管理規則」中「我們自己寫的 submodule 不適用 fork 規則」那一段），判斷方式是看 `origin`
的 URL 是不是 `raliclo/`。`sync_all.zsh` 也有對應的分支處理這一種。

## CLI 介面

### 你指定的旗標

```
csv2 -r            讀取模式
csv2 -insert N ROW 插入為第 N 筆
csv2 -append ROW   加在最後
csv2 -delete a[,b]      刪除第 a 筆，或第 a 到第 b 筆
csv2 -delete -cell r:c  清空第 r 筆第 c 欄
csv2 -update r:c VAL    更新第 r 筆第 c 欄
csv2 -contains S   輸出含有 S 的列，前綴列號（如 cat -n）
csv2 -A N          比對到的紀錄之後再輸出 N 筆（如 grep -A）
csv2 -B N          比對到的紀錄之前再輸出 N 筆（如 grep -B）
csv2 -C N          前後各 N 筆，等同 -A N -B N（如 grep -C）
csv2 -head N       前 N 筆
csv2 -tail N       後 N 筆
csv2 -mid a,b      第 a 到第 b 筆（含兩端）
csv2 -t            輸出帶上標頭列（預設不帶）
csv2 -rownum       最前面加一欄紀錄號
csv2 -i FILE       輸入檔
csv2 -o FILE       輸出檔
csv2 -si           由 stdin 讀
csv2 -so           寫到 stdout
csv2 -md           輸出 Markdown 表格（與 -head/-tail/--filter 組合）
csv2 -encrypt COLS 加密指定欄位（ChaCha20-Poly1305，需 -keyfile）
csv2 -decrypt COLS 解密指定欄位（需 -keyfile）
csv2 -hash COLS    以 SHA-256 遮蔽指定欄位（單向，不可還原）
csv2 -keyfile P    金鑰檔路徑。預設為 multissh 私鑰，見下
csv2 -debug        把診斷訊息印到 stderr（log4j 層級）
csv2 -log FILE     把帶時間戳的操作紀錄追加到 FILE
```

### 兩個要先講清楚的落差

**一、`-si` / `-so` 並非「像 swift_tar」。** swift_tar **沒有**這兩個旗標——我查過它的
原始碼，那些 `standardOutput` 的出現處都是它在生成子行程，不是它自己的 stdio。所以
「像 swift_tar 那樣」這句沒有可對照的實作，語意必須在此定義：

```
-si    由 stdin 讀取，且不得整檔載入記憶體
-so    寫到 stdout，且不得在寫出前緩衝整份輸出
-i/-o  檔案路徑；與 -si/-so 互斥，同時給出即為錯誤而非默默擇一
```

「不得整檔載入」是硬需求而非最佳化：這支工具要能處理比 guest 記憶體大的檔案，而
guest 只有 2–4 GiB。

**二、旗標風格與 swift_tar 不一致。** swift_tar 用的是 `--long`（`--zstd`、
`--strip-components`），短旗標才用單破折號（`-c`、`-f`）。你指定的是 `-contains`、
`-head`、`-tail`、`-si`、`-so`——單破折號配長名。

建議：**兩種都接受**（`-contains` 與 `--contains` 等價），文件以你指定的寫法為準。
成本極低，而且避免使用者按 swift_tar 的習慣打字時撞牆。未知旗標必須報錯——multissh
今天才剛修好「未知選項被當成主機名稱吞掉」的同型缺陷。

### `-head` / `-tail`：以資料筆數計算；`-t` 才帶標頭

**N 數的是資料筆數**，不是物理行。含引號換行的紀錄可以跨多行，數行會給出半筆資料。

**預設只輸出資料列，`-t` 才帶上標頭。**

```sh
csv2 -head 3 -i a.csv2            # 3 個資料列
csv2 -head 3 -t -i a.csv2         # 標頭 2 列 + 3 個資料列
```

預設不帶標頭是對的選擇，因為多數用途是把結果餵給下一個工具或直接看，那時標頭是雜訊；
要串接多份輸出時也不會夾雜重複標頭。

**這使 `-tail` 與 POSIX `tail` 一致**（都給最後 N 個單位），差別只在單位是「筆」而非
「行」。這比先前的設計好記。

**但它產生一個必須擋住的危險組合。** 沒有 `-t` 的輸出是**資料片段，不是合法的 csv2
檔案**。若把它寫進 `-o foo.csv2`，下次讀取時前兩筆資料會被當成標頭吃掉——正是這支工具
存在的理由所在的那個錯誤。

決定：**`-o` 指向 `.csv` 或 `.csv2` 時，必須給 `-t`**，否則報錯並說明原因。這是「副檔名
宣告格式」那條規則的必然結果：一個沒有標頭的 `.csv2` 檔案，是在對自己的格式說謊。

不帶 `-t` 的輸出應該去 stdout（`-so`）或非 CSV 副檔名的檔案——那裡沒有格式承諾，也就
沒有謊言。

| 組合 | 結果 |
|---|---|
| `-head 3 -so` | 3 個資料列到 stdout。正常 |
| `-head 3 -o x.txt` | 3 個資料列到檔案。正常 |
| `-head 3 -o x.csv2` | **錯誤**：`.csv2` 需要標頭，請加 `-t` |
| `-head 3 -t -o x.csv2` | 標頭 + 3 筆，是合法的 `.csv2` |

**與串流相容。** 標頭在檔案開頭就讀到了，`-tail` 只需一個 N 筆的環狀緩衝（與 `-B`
相同的機制），因此 `-si` 的串流保證不受影響——`-t` 與否都一樣。

**`-head` 與 `-tail` 同時給出即為錯誤**，不要自作聰明地解釋成「中間」或「兩端」。

### `-mid a,b`：取第 a 到第 b 筆

```sh
csv2 -mid 3,7 -i TARGET_PACKAGES.csv     # 第 3 到第 7 筆資料，含兩端
```

**兩端皆含**，與 `sed -n '3,7p'` 一致。1-based，與其餘定位一致。標頭的規則與
`-head`/`-tail` 相同：預設不帶，`-t` 才帶，寫入 `.csv`/`.csv2` 時必須給 `-t`。

**它是唯一完全不需要緩衝的範圍操作。** `-tail` 要環狀緩衝、`-B` 要環狀緩衝，而 `-mid`
只需「跳過到 a、輸出到 b、然後停」——連 `b` 之後的內容都不必讀。對大檔案而言它比
`-head` 之外的任何選項都便宜，這值得寫進 `--help`，因為使用者會需要一個可以安全用在
巨大檔案上的取樣方式。

**參數的驗證要明確失敗，不要自作聰明：**

| 情況 | 行為 |
|---|---|
| `a > b`（如 `-mid 7,3`） | **錯誤**。不自動對調——使用者若寫反了，多半是別處的邏輯也反了 |
| `a < 1` | 錯誤。0 或負數在 1-based 的體系裡沒有意義 |
| `b` 超過總筆數 | **不是錯誤**，輸出到檔尾為止。與 `head -100` 在五行檔案上的行為一致 |
| `a` 超過總筆數 | 輸出零筆資料（有 `-t` 時只有標頭）。仍然合法，不報錯 |

**開放端**：`-mid 5,` 為第 5 筆到結尾，`-mid ,5` 為開頭到第 5 筆。後者等同 `-head 5`，
但兩種寫法都保留——寫程式產生參數時，能不用特判會方便得多。

**與 `-head` / `-tail` 互斥**，理由同前：三者同時給出沒有一個合理的解釋。

**與 `-contains` 可組合**，語意是「只在第 a 到第 b 筆之內搜尋」。這是有用的組合，因為
它讓搜尋範圍可以先被縮小。

那個逗號是**命令列參數的分隔符**，與 CSV 的欄位分隔符無關——在一支 CSV 工具裡這值得
講明，雖然實際上不會有歧義。

### `-rownum`：在最前面加一欄紀錄號

```sh
csv2 -head 3 -rownum -t -i a.csv2
```

```
rownum,pkg_name,version,…
列號,套件名稱,版本,…
1,busybox,1.37.0,…
2,glibc,2.42,…
```

命名理由：與 `-head`/`-tail`/`-contains`/`-mid` 的「單破折號＋長名」風格一致。`-num`
有歧義（number of what？），`-rn` 太短且與 `-r` 易混。`-n` 本來最自然，但已被保留。

有 `-t` 時，新增的欄在兩列標頭都要有名字：`rownum` 與 `列號`。少了這一步，標頭的欄數
就會比資料少一——正是「欄數不符」那條檢查要擋的情形，而且是由這支工具自己製造出來的。

**陷阱一：欄號會整批位移。** 加了這一欄之後，原本的第 1 欄變成輸出的第 2 欄。若
`-contains` 的定位報告也跟著位移，同一份資料在加不加 `-rownum` 時會給出不同的欄號，
而使用者不會預期一個「只是多印一欄」的旗標改變定址。

決定：**定址永遠以輸入為準。** `-rownum` 是輸出端的加工，不改變 `record:field` 的意義。
輸出裡它是第 0 欄，不是第 1 欄。

**陷阱二：新增的欄不參與比對。** 否則 `-contains 12` 會命中所有紀錄號含 12 的列——那
是工具自己加的資料，不是使用者的資料。搜尋的對象永遠只有原始欄位。

**與 `-md` 組合**時同理，`rownum` 成為表格的第一欄。這在文件裡很有用，因為讀者可以直接
引用「第 7 筆」。

### `-md`：輸出 Markdown 表格

與 `-head` / `-tail` / `-contains --filter` 組合，把子集直接貼進文件：

```sh
csv2 -head 5 -md -i TARGET_PACKAGES.csv
```

**兩列標頭與 Markdown 的衝突。** Markdown 表格只有**一列**標頭，而 `.csv2` 有兩列。
決定：預設把兩者合併在同一個儲存格，以 `<br>` 分隔——

```markdown
| pkg_name<br>套件名稱 | version<br>版本 |
|---|---|
| busybox | 1.37.0 |
```

這符合本專案文件雙語並列的習慣。`--en` / `--zh` 可只取其一。

**跳脫是這裡的正確性問題，不是排版問題。** 儲存格內的 `|` 會把表格切開，內嵌換行會
把一列拆成兩列。兩者都必須跳脫（`|` → `\|`，換行 → `<br>`）。

這與天真的逗號切割**是同一類錯誤**：輸出看起來像表格、renderer 也不會抱怨，只是欄位
跑到別欄去了。`TARGET_PACKAGES.csv` 的 `status_notes` 就含有會觸發這個問題的內容，
因此它同樣是最好的測試素材。

**`-md` 是單向的。** 產出的 Markdown **不能**再被 `csv2` 讀回來，所以 `-head`/`-tail`
那條「輸出必須是合法的同格式檔案」在此不適用——`-md` 屬於呈現，不屬於篩選。

因此：`-md` 搭配 `-o foo.md` 合理，搭配 `-o foo.csv2` **即為錯誤**（副檔名宣告的是
csv2，內容卻是 Markdown）。這是副檔名決定格式那條規則的自然延伸。

`-md` 與 `--json` 互斥。

**`-md` 需要 `-t`。** Markdown 表格的語法要求有標頭列與其下的分隔列（`|---|`）；沒有
標頭就渲染不出表格，只會是一堆以 `|` 分隔的文字。

決定：`-md` 未搭配 `-t` 時**報錯並說明原因**，而不是自動補上。自動補上會讓「預設不帶
標頭」這條規則出現一個看不見的例外，而看不見的例外正是這份設計一直在避免的東西。

**對齊會犧牲串流。** 把欄寬對齊需要知道所有列的最大寬度，也就是必須先讀完整個輸入
再輸出——那會破壞 `-si` 的串流保證。

決定：**預設不對齊**（`|a|b|` 這種最小形式，renderer 呈現結果完全相同），`--pretty`
才對齊，且其說明必須寫明它會放棄串流。這個取捨要顯式呈現，因為「好看」與「能處理大
檔」在此無法兼得，而預設值應該是後者。

### `-encrypt` / `-decrypt` / `-hash`

**SHA-256 是雜湊，不是加密。** 它不可逆，所以「用 SHA-256 加密再解密」在數學上不成立。
若照字面實作，`-decrypt` 只能失敗或吐出垃圾——一個名字承諾了安全性、行為卻做不到的
功能，是最糟的一類。

因此這裡是**兩個不同的功能**，需要先確定你要的是哪一個（或兩個都要）：

| 旗標 | 性質 | 用途 |
|---|---|---|
| `-hash` | **單向**，SHA-256 | 遮蔽。把欄位換成雜湊值，之後仍可比對「是否為同一個值」，但取不回原文 |
| `-encrypt` / `-decrypt` | **可逆**，需金鑰 | 保護。取得金鑰即可還原原文 |

**演算法：直接用 swift_tar 的 `crypto.swift`。** 它已經實作了 ChaCha20-Poly1305 AEAD
（RFC 8439）、PBKDF2-HMAC-SHA256、scrypt，且已在本專案內受測。

這同時回答了「或任何更快的演算法」：**ChaCha20 就是更快的那個**。在沒有 AES 硬體
指令的目標上（本 guest 是 QEMU 下的 aarch64），純軟體的 ChaCha20 明顯快於 AES，這正是
它被設計出來的原因。不需要另尋演算法。

AEAD 的 Poly1305 認證標籤還帶來一個 SHA-256 給不了的性質：**密文被竄改時解密會失敗**，
而不是安靜地還原出錯誤的內容。

### 金鑰不要走命令列參數

`-key SECRET` 會出現在 `ps` 的輸出裡，同一台機器上的任何行程都看得到，也會留在 shell
歷史中。

本專案對此已有既定立場：swift_tar 用 `--keyfile <path>` 並在終端機上提示輸入；multissh
的 `--passphrase-file` 註明「避免秘密出現在 process arguments」。

決定：**只提供 `-keyfile <path>`**，並支援在終端機上提示輸入。**不提供 `-key`。**

不提供，而非提供並警告。一個「方便但不安全」的選項，警告只會在第一次被讀到，之後它
就只是比較好打的那一個——最終會被用在正式資料上。既然安全的做法只多一個檔案，就不需要
保留不安全的那條路。

### `-keyfile` 的預設值：multissh 的金鑰

未給 `-keyfile` 時，預設使用 multissh 的私鑰。實地查證的結果如下。

**金鑰在哪。** 有兩個位置，是不同的東西：

| 路徑 | 性質 |
|---|---|
| `~/.multissh/generated/` | **執行時**的金鑰，multissh 自己的搜尋順序第一位 |
| `<repo>/multissh_keys/generated/` | 由 `mssh-keygen` 產生的**診斷**金鑰，README 原文稱 diagnostic |

決定：**預設 `~/.multissh/generated/mldsa44-ed25519.key.raw`**。它是 multissh 執行時
實際使用的身分金鑰，也是「multissh 的私鑰」這句話在這台機器上唯一合理的指涉。repo 內
那份是測試素材，不該拿來加密正式資料。

已查證：該檔存在、64 bytes、mode `0600`、未加密（raw 格式，無 passphrase），因此可直接
作為 KDF 的輸入。`multissh_keys/generated/` 被 `.gitignore` 排除，不在版控內。

**找不到金鑰就報錯，不要後援。** 沒有 multissh 金鑰時直接以錯誤結束，不自行產生、不改用
其他檔案、不提示輸入密語。理由是：任何後援都會產生一個「能解密、但不是你以為的那把
金鑰」的檔案，而那件事要到日後解密失敗時才會發現。錯誤訊息要指出去哪裡取得金鑰
（`release/mssh-keygen -o ~/.multissh/generated`）。

**未給 `-keyfile` 時警告並詢問 y/n。** 因為「用了哪一把金鑰」決定了這個檔案日後還能不能
讀，而預設值是使用者沒有打出來的東西——沉默地採用它，等於讓最重要的一項決定發生在
畫面之外。

```
警告：未指定 -keyfile，將使用 multissh 的私鑰
  ~/.multissh/generated/mldsa44-ed25519.key.raw  (指紋 a1b2c3d4)
若此金鑰被重新產生或遺失，本檔案將永久無法解密。
繼續？[y/N]
```

**沒有 tty 時不得詢問，一律以錯誤結束。** 無法顯示的提示絕不可視為「是」——否則腳本與
排程工作會靜默地採用預設金鑰，而提示的用意正是不讓這件事靜默發生。要在腳本中使用時，
明確給 `-keyfile`，或以 `--yes` 表示已知悉。

**必須做網域分離（domain separation）。** `mldsa44-ed25519.key.raw` 是**簽章**金鑰，不是
加密金鑰；把同一份秘密同時用於兩種用途，是密碼學上明確不建議的事。緩解方式是不直接把
檔案內容當金鑰，而是經過帶標籤的 KDF：

```
key = KDF(檔案位元組, salt = 每檔隨機, info = "csv2-column-encryption-v1")
```

`info` 標籤使推導出的金鑰與任何簽章運算在數學上無關，即使輸入是同一把私鑰。KDF 用
swift_tar `crypto.swift` 既有的 PBKDF2-HMAC-SHA256 或 scrypt。

**檔頭要記錄金鑰指紋。** 這是為了一個具體的失效情境：`mssh-keygen` 重新產生金鑰後，
新金鑰是另一組隨機位元組，於是所有先前加密的 CSV 全數無法解密——而該目錄不在版控內，
git 也救不回來。

指紋擋不住這件事，但能讓它**大聲失敗**。沒有指紋時，解密只會得到 Poly1305 認證失敗，
那個錯誤看起來像檔案損毀，會把人引去查錯的方向。有指紋時訊息是明確的：

```
錯誤：本檔案以指紋 a1b2c3d4 的金鑰加密，目前的金鑰指紋為 ef567890
      金鑰可能已被 mssh-keygen 重新產生。
```

指紋取推導後金鑰的 SHA-256 前 4 bytes，是公開值，不洩漏金鑰。

**這把金鑰在 guest 裡不存在。** 已查證：`build_multissh-workspace` 的 rsync 未納入
`multissh_keys/`，`~/.multissh/` 也不會隨 rootfs 進入 guest。因此在 guest 內執行加密
一定會走到「找不到金鑰」那條錯誤路徑。這是正確的行為，但要寫進文件，否則會被當成 bug。

### 記錄：`-debug` 與 `-log`

兩個不同的東西，不要合成一個旗標。

| 旗標 | 去哪裡 | 內容 |
|---|---|---|
| `-debug` | stderr | 診斷細節：解析狀態、欄位判定、走了哪條分支 |
| `-log FILE` | 指定的檔案 | 操作紀錄：做了什麼、對哪個檔案、結果如何，每行帶時間戳 |

**為什麼分開。** `-debug` 是給「現在正在查一個問題」的人看的，量大、格式可變、用完即棄。
`-log` 是給「日後要回頭查這個檔案被誰改成這樣」的人看的，量小、格式穩定、要能長期保存。
把兩者寫進同一個地方，會讓歷史紀錄被除錯輸出淹沒。

**log4j 風格的層級與格式。**

```
2026-08-15T14:23:07.412+08:00 INFO  csv2 -update 12:6 -i TARGET_PACKAGES.csv -o TARGET_PACKAGES.csv --in-place
2026-08-15T14:23:07.418+08:00 DEBUG parser: record 12 spans lines 31-33 (embedded newline in field 6)
2026-08-15T14:23:07.421+08:00 INFO  update 12:status_notes: "舊值" -> "新值"
2026-08-15T14:23:07.425+08:00 INFO  wrote 247 records, 8 fields, atomic rename OK
```

層級 `ERROR > WARN > INFO > DEBUG > TRACE`。`-debug` 等同把門檻降到 DEBUG；
`-debug=trace` 之類的形式可以再降。預設門檻是 WARN，也就是**預設什麼都不印**——一支
會在正常路徑上說話的 CLI 沒辦法放進管線。

**時間戳用 ISO 8601 並帶時區位移。** 不用 `date` 的預設格式，因為那個格式在不同 locale
下會變；guest 的 locale 設定與 host 不同，同一份 log 會出現兩種格式。帶位移是必要的：
guest 在 UTC、host 在 +08:00，沒有位移就無法把兩邊的事件排在同一條時間線上。

**三個必須守住的性質：**

**一、`-log` 追加，不覆寫。** 覆寫會讓「日後回頭查」這個唯一的用途失效。

**二、log 絕不記錄金鑰、密語或明文儲存格的內容。** `-update` 的紀錄會寫出舊值與新值，
若該欄正在被加密，那就等於把明文寫進了一個沒有人在保護的檔案。因此：被 `-encrypt`
或 `-hash` 指定的欄位，其值在 log 中一律以 `<redacted>` 取代，只記錄欄名與是否變更。

**三、寫 log 失敗不得使操作失敗。** log 檔所在目錄不可寫時，應向 stderr 警告一次後
繼續完成操作。反過來的設計會讓一個純粹的觀測功能變成一個新的失敗來源。

**`-so` 時 log 不能走 stdout。** 那會把時間戳混進 CSV 輸出裡。`-log -` 若要支援，
指的是 stderr 而非 stdout，且這一點要寫在 `--help` 裡，因為 `-` 的慣例通常是 stdout。

### 加密的是儲存格，不是列——三個必須定義的點

**一、標頭永遠不加密。** 標頭被加密後，檔案就不再是可解析的 csv2，`-contains`、
`-rownum`、欄數檢查全部失效。而且標頭是欄位「名稱」，通常不是機密——機密在值裡。

**二、密文必須編碼成文字。** ChaCha20-Poly1305 的輸出是二進位，CSV 是文字格式。
以 base64 編碼（其字元集 `A-Za-z0-9+/=` 不含逗號、引號、換行，因此不需要額外跳脫）。
儲存格會變長：nonce 12 bytes + 標籤 16 bytes + 明文，再乘以 base64 的 4/3。小欄位的
膨脹比例可觀，這要寫進說明。

**三、同樣的明文每次產生不同的密文。** AEAD 每次使用新的 nonce，這是正確且必要的
（重用 nonce 會摧毀 ChaCha20-Poly1305 的安全性），但有兩個後果必須講明：

- **加密後的欄位無法用 `-contains` 搜尋**，連「找出所有值相同的列」都做不到
- **重跑一次加密，整個檔案的 diff 會全變**，不適合放進版控後期待穩定的 diff

若真的需要「相同明文得到相同密文」，那是另一種取捨（確定性加密會洩漏「哪些值相等」），
必須是明確的另一個模式，不能當成預設。

`-hash` 沒有這個問題——SHA-256 是確定性的，所以遮蔽後仍可比對相等性。**若你的實際需求
是「看不到原文但仍能比對」，你要的是 `-hash` 而不是 `-encrypt`。**

### 選擇要處理哪些欄位

`-encrypt` / `-hash` 需要一個欄位選擇器，否則整列都被處理（包含不敏感的欄位）：

```sh
csv2 -encrypt 3,5 -keyfile k -i a.csv2 -o b.csv2    # 只處理第 3、5 欄
csv2 -hash status_notes -i a.csv2 -o b.csv2         # 以欄名指定
```

**已加密的欄位需要被標記**，否則 `-decrypt` 無從知道哪些欄該處理，只能全試一遍。
建議在標頭的欄名後加上後綴（`status_notes:enc`），如此：

- 資訊留在檔案本身，不需要外部的 metadata
- `-decrypt` 讀標頭即可知道要處理哪些欄
- 對已加密的欄再次 `-encrypt` 可以直接拒絕，而不是疊加一層

### 編輯：`-insert` / `-append` / `-delete` / `-update`

取代原本語意不明的 `-w`。四個動詞，各自只做一件事：

```sh
csv2 -insert 5 'busybox,1.37.0,"a, b",…'   # 插入為第 5 筆，原第 5 筆之後順延
csv2 -append 'busybox,1.37.0,…'            # 加在最後
csv2 -delete 5                             # 刪除第 5 筆
csv2 -delete 5,9                           # 刪除第 5 到第 9 筆（含兩端）
csv2 -delete -cell 12:6                    # 清空第 12 筆第 6 欄
csv2 -update 12:6 '新的值'                  # 更新第 12 筆第 6 欄
```

**`-delete a,b` 沿用 `-mid` 的範圍語意**（1-based、兩端皆含），因為兩者都是在講「一段
紀錄」。一致是刻意的。

### `-update` 用 `r:c` 而不是 `a,b`

動詞從 `-set` 改為 `-update`，這比 `-set` 好：`-insert` / `-update` / `-delete` 是
SQL 的既有詞彙，四個動詞一起看就是一組認得出來的東西，而 `-set` 是設定值的意思，
在 CLI 裡常被拿去指「設定選項」。

位址你提的是 `a,b`，但我建議 `r:c`，理由有兩個：

**一、`a,b` 在這支工具裡已經是「範圍」的意思。** `-mid 3,7` 是第 3 到第 7 筆，若
`-set 3,7` 變成「第 3 筆第 7 欄」，同一種寫法在不同旗標下代表不同概念——那是使用者遲早
會弄錯的東西，而且弄錯時不會報錯，只會改到別的儲存格。

**二、`r:c` 正是這支工具自己輸出的定址格式。** `-contains` 印的是 `12:6 status_notes`，
所以流程可以直接接起來：

```sh
csv2 -contains "舊的值" -i a.csv2      # → 12:6 status_notes …
csv2 -update 12:6 "新的值" -i a.csv2 -o b.csv2
```

**找到什麼就能直接改什麼**，不需要在腦中把座標轉換成另一種寫法。若仍要接受 `12,6`，
可以一併支援，但文件與輸出一律用 `r:c`。

`-update` 也接受欄名：`-update 12:status_notes '值'`。純數字視為欄號，其餘視為欄名；
欄名本身就是數字的情況以 `--by-name` 消歧義。

### `-delete -cell`：儲存格層級的刪除只能是「清空」

```sh
csv2 -delete 5           # 整筆刪掉，後面的紀錄往前遞補
csv2 -delete -cell 12:6  # 只清空那一格，紀錄仍在、欄數不變
```

**「刪除一個儲存格」在 CSV 裡只能是清空，不能是移除。** 真的把那個欄位拿掉，該列就會
比其他列少一欄，後面所有欄位往前位移一格——於是 `status_notes` 的內容出現在 `license`
欄底下。那正是這支工具存在的理由所在的那類損壞，而且它不會報錯，只會安靜地錯位。

因此 `-delete -cell 12:6` 的定義是：**把該儲存格設為空字串，欄數不變。**

**CSV 沒有 NULL。** 空字串就是空字串，格式本身無法表達「這一格沒有值」與「這一格的值
是空的」之間的差別。若上游資料需要區分，那要在資料層用一個哨符值（例如 `n/a`）處理，
不是這支工具能給的。`update_licenses.sh` 就已經走過這條路：它刻意寫入
`n/a (not a buildroot package)` 而不是留白，因為留白會被讀成「沒有授權」。

**它與 `-update 12:6 ''` 等價，但仍然值得存在。** 在 shell 裡把「空」當成參數傳很容易
出錯——引號漏了一邊，`-update 12:6` 後面的下一個旗標就會被當成值吃掉，而且不會報錯。
`-delete -cell` 沒有值參數，也就沒有這個失誤空間。

**位址形式與旗標必須一致，不一致即報錯，不要自行推斷：**

| 寫法 | 結果 |
|---|---|
| `-delete 5` | 刪除第 5 筆 |
| `-delete -cell 12:6` | 清空該儲存格 |
| `-delete 12:6` | **錯誤**：`12:6` 是儲存格位址，請加 `-cell` |
| `-delete -cell 5` | **錯誤**：`-cell` 需要 `r:c` 形式的位址 |

用 `:` 的有無自動判斷是做得到的，但那會讓「刪掉一整筆」與「清空一格」這兩件差很多的事，
差別只在一個標點符號上。這裡要的是打錯字時報錯，而不是靜默地做另一件事。

**`-insert -cell` 不存在，且必須明確拒絕。** 在一列中間插入一個儲存格，會把該列後面的
欄位全部往後推一格，同樣造成上述的錯位。錯誤訊息要說明原因，而不是只說「不支援」——
使用者需要知道為什麼，否則會去找別的方法達成同一件錯事。

（要移除的是「一整欄」時，那是另一種操作：它要同時從每一列與兩列標頭中移除該欄，欄數
才會保持一致。目前未納入，見文末的待決問題。）

### 編輯的三個陷阱

**一、多個編輯的索引以「輸入」為準，一次套用。**

```sh
csv2 -delete 3 -delete 4 -i a.csv2 -o b.csv2
```

若逐一套用，刪掉第 3 筆之後原本的第 5 筆就變成第 4 筆，於是第二個 `-delete 4` 刪錯
對象。使用者寫下這行時，想的必定是輸入裡的第 3 與第 4 筆。

決定：**所有索引都指向輸入，全部收集完再一次套用。** 這也讓 `-insert` 與 `-delete`
可以在同一次呼叫中混用而不互相干擾。

**二、`-i` 與 `-o` 指向同一個檔案會毀掉輸入。** 開啟輸出即截斷，而那時輸入還沒讀完。

決定：**同路徑預設拒絕**；要就地編輯需明確給 `--in-place`，且實作必須是「寫入暫存檔
→ 成功後 rename」。rename 在同一檔案系統上是原子的，因此中途失敗時原檔完好——這一點
在本專案格外重要，這個 session 已經有兩次 CSV 被寫壞、靠 git 還原的紀錄。

**三、索引超出範圍是錯誤，不是「自動長大」。** `-update 99:3` 在只有 20 筆的檔案上必須
失敗，而不是補出 79 筆空紀錄。`-insert 99` 同理。唯一的例外是 `-append`，它的語意本來
就是「在結尾」。

### 插入的資料為什麼是「一整列 CSV 文字」

`-insert` 與 `-append` 的參數是**一列 CSV 編碼過的文字**，由同一個解析器處理：

```sh
csv2 -append 'busybox,1.37.0,"含有, 逗號的值"'
```

不用 `-append v1 v2 v3` 這種多參數形式，是因為那等於要求使用者用 shell 的引號規則去表達
「值裡面有逗號」，而 shell 與 CSV 的引號規則不同——那正是這支工具要消滅的那類轉換錯誤。
交給自己的解析器處理，只有一套規則。

欄數必須與標頭相符，否則錯誤。這是同一條「欄數不符即失敗」的規則，套用在寫入端。

### 兩種輸出形狀，不要混為一談

這一點必須先分清楚，否則 `-t` 這個旗標會被套用到它沒有意義的地方：

| 模式 | 輸出 | 標頭 |
|---|---|---|
| `-head` / `-tail` / `-mid` / `-contains --filter` | **資料列**；加 `-t` 才是同格式的合法檔案 | 預設不帶，`-t` 帶上 |
| `-contains` 的定位報告（`12:6 status_notes …`） | **報告**，不是 CSV | 不適用——標頭不是資料列 |

也就是說 `-contains` 有兩種用途：**篩選出符合的紀錄**（產出 CSV），與**指出命中在哪個
儲存格**（產出報告）。預設為報告，`--filter` 切換為產出 CSV 子集。`--json` 兩者皆可，
形狀不同。

### `-A` / `-B` / `-C` 的兩個非顯而易見之處

**單位是紀錄，不是物理行。** 與列號同樣的理由：`-A 2` 應該給你「之後兩**筆**資料」，
而不是「之後兩個換行」。在含有引號換行的檔案上，後者會給出半筆紀錄。

**`-B` 與串流的衝突。** `-A` 只需向前讀，可以完全串流。`-B N` 必須保留最近 N 筆
紀錄——這是一個有界的環狀緩衝，記憶體上界是 `N × 單筆最大紀錄`，不是整個檔案。實作
時必須是環狀緩衝而非「先讀完再回頭找」，否則 `-si` 的串流保證就破了。

grep 在多個匹配區塊之間會印 `--` 分隔線。建議照做，並在 `--help` 說明它是分隔線而非
資料——否則下游腳本會把它當成一筆紀錄。

## 兩列標頭：格式定義

```
row 0a   pkg_name,version,size_on_target,…        ← 英文標題
row 0b   套件名稱,版本,目標端大小,…                ← 正體中文標題
row 1    busybox,1.37.0,…                          ← 第一筆資料
```

兩列標頭必須有**相同的欄數**，且與資料相同。欄數不符即為錯誤，不得靜默補空——這正是
今天 `artifacts.csv` 被寫壞時缺少的那道檢查。

### 格式由副檔名宣告，不靠猜

```
foo.csv    標準 CSV，一列標頭
foo.csv2   兩列標頭：第一列英文、第二列正體中文
```

**這是這份設計裡最重要的一個決定。** 內容本身無法可靠判斷「第二列是中文標題還是第一
筆資料」——任何啟發式（看有沒有中文字、看型別像不像）都會在某些檔案上猜錯，而猜錯的
後果是**第一筆資料被當成標題吃掉，且不會報錯**。

副檔名讓格式成為一個**被宣告的事實**而非推測。誤用會在檔名上看得見，不會藏在解析器
裡。

這也順帶解決了遷移問題：本 repo 現有的 `artifacts.csv`、`TARGET_PACKAGES.csv`、
`checksum.csv` 都是 `.csv`，因此**自動被當成單列標頭讀取，不需要任何遷移**，既有的
`tail -n +2` 也不會偏移。要改用兩列標頭時，就是把檔案改名為 `.csv2` ——那一刻所有讀取
端都會看到檔名變了，不會有人在不知情的情況下讀到偏移一列的資料。

**寫入端同理**：`-o foo.csv2` 產生兩列標頭，`-o foo.csv` 產生一列。

### 副檔名不存在的兩種情況

**一、`-si` 從 stdin 讀。** 沒有檔名就沒有副檔名。此時**必須**以 `--headers 1|2` 明確
指定，未指定即為錯誤而非預設猜一個——這是唯一無法由副檔名回答的情形，預設值在此就是
猜測。

**二、副檔名與內容不符。** 讀 `.csv2` 但檔案只有一列標頭（或欄數對不上），必須**明確
失敗**並指出是哪一列不符，不得繼續。可檢查的條件：兩列標頭的欄數必須相同，且與第一筆
資料相同。

啟動時把解析結果印到 stderr（`format=csv2 fields=7 records=21`），讓工具「認為」的格式
可見；`--json` 的 metadata 一併帶出。

### 兩個標題名，`--json` 兩個都給

```json
{"record":12,"field":6,"header_en":"status_notes","header_zh":"狀態註記","value":"…"}
```

文字輸出預設印英文標題（腳本友善），`--zh` 改印中文標題。兩者都印會讓行變得太長。

`-contains` **預設只搜資料**，不搜標頭——否則搜 "version" 會先命中標題列，那幾乎不會
是使用者想要的。`--include-headers` 可一併搜尋，命中時 record 回報為 `0a` / `0b`。

### 遷移既有檔案的代價

若要把 repo 內既有的 CSV 改成兩列標頭，**每一個現有的讀取端都會靜默偏移一列**。今天
的腳本裡有 `tail -n +2`、`head -1`、以及 python 的 `rows[0]` / `rows[1:]`——全部假設單列
標頭。

建議：**先不要遷移。** 新檔案用兩列，既有檔案維持單列並以 `--headers 1` 讀取。等
`csv2` 成為這些檔案的唯一存取途徑之後再遷移，那時只需改工具的呼叫參數，而不是去找
出散落各處的 `tail -n +2`。

## 找到字串之後，如何回報儲存格位置

這是這支工具與 `grep` 的根本差異：grep 的答案是「第幾行」，而 CSV 的答案應該是
**「第幾筆、第幾欄」**。做對了它能直接餵給後續處理；做錯了它只是換個格式的 grep。

### 預設輸出格式

```
12:6  status_notes  "…so compressed archives can still be handled through a pipe…"
│  │  │             └ 該儲存格的值（未經 CSV 引號編碼）
│  │  └ 欄名，取自標頭列
│  └ 欄號（1-based）
└ 紀錄號（1-based）
```

紀錄號與欄號都用 **1-based**，理由是 `cut -f`、`awk $1`、試算表全都是 1-based；
0-based 會讓人把結果貼進 `cut -f` 時差一格。

### 三個必須先定義、否則會靜默給錯答案的地方

**一、標頭列算不算第一筆。** 選錯不會報錯，只會讓每個答案差一或差二。

決定：**標頭不佔用資料的編號，第一筆資料永遠是 row 1。** 兩列標頭分別是 `0a`、`0b`
（單列標頭時只有 `0`）。這樣「row N」永遠指第 N 筆**資料**，與人們口語一致，而且
`--headers` 從 1 改成 2 時，資料的編號不會整批偏移——那種偏移正是這類工具最容易
產生的靜默錯誤。

**二、比對的對象是解碼後的欄位值，不是原始位元組。** 這個差異在搜尋含逗號的字串時
會顯現：

```
原始一列：  a,"b,c",d
搜尋 "b,c"  → 解碼後比對：命中欄位 2        ← 正確
            → 原始位元組比對：命中，但跨越了引號，位置無法對應到任何單一儲存格
```

決定：**一律在解碼後的值上比對。** 這也表示搜尋 `,` 永遠不會匹配分隔符本身，只會
匹配「某個欄位的值裡真的有逗號」——那正是使用者想問的。

**三、同一儲存格內多次命中、同一筆紀錄多個儲存格命中。** grep 對一行只印一次。
決定：**每個命中的儲存格印一次**（同儲存格內重複出現不重複印），因為單位是儲存格；
同一筆紀錄有兩欄命中就印兩行，它們是兩個不同的位置。

### 換行：一律寫 LF；讀取時自動接受 CRLF

**輸出的紀錄分隔符永遠是 `\n`，在任何平台上都一樣，不偵測作業系統。**

這不是風格偏好，有三個具體理由：

**一、否則跨平台逐位元相同的驗收條件根本不可能成立。** 若行尾隨平台而變，mac 與 Linux
的輸出必然不同，那條驗收條件就得放棄——而它是目前最有力的一項檢查。

**二、尾隨的 CR 在 shell 裡是隱形的。** 欄位值變成 `value\r` 之後，`[ "$x" = value ]`
會是偽，但錯誤訊息印出來看起來完全正常——因為 CR 只是把游標移到行首。這是最難查的
一類 bug，而本 repo 的資料檔正是被 shell 腳本讀的。

**三、混合行尾會讓 git diff 整片變動**，掩蓋真正的修改。

### `.csv2` 的硬性不變式：一筆紀錄 = 一行

**`.csv2` 的儲存格內不得含有原始的 `\n` 或 `\r`。** 寫入時自動跳脫（見下），讀取時
若遇到原始換行即為格式錯誤。

**這個限制在我們的資料上是免費的。** 已實測本 repo 樹內所有 CSV：

| 檔案 | 含換行的儲存格 | 紀錄數 | 物理行數 |
|---|---|---|---|
| `TARGET_PACKAGES.csv` | 0 | 22 | 22 |
| `artifacts.csv` | 0 | 22 | 22 |
| `checksum.csv` | 0 | 201 | 201 |
| `marathon-data.csv`（第三方，37k 列） | 0 | 37251 | 37251 |
| `cpuid.csv` | 0 | 1195 | 1195 |

**一個都沒有**，且紀錄數與物理行數在每一份檔案裡都相等。

**換來的是：那些弄壞過我們檔案的工具，在 `.csv2` 上變成正確的。**

```sh
wc -l foo.csv2        # 紀錄數（減去標頭）
sed -n 12p foo.csv2   # 第 12 行就是第 12 筆
head / tail / grep -n # 行號與紀錄號一致
split -l              # 切塊不會切壞紀錄
```

csv2 的目的是讓「正確處理 CSV」比「隨手切逗號」更方便；這條不變式更進一步——**它讓
隨手切也不會出錯**。我認為這比兩列雙語標頭更能構成 `.csv2` 存在的理由。

連帶的簡化：`--physical`（紀錄號與物理行號不一致）對 `.csv2` 不再需要；平行掃描不必做
兩狀態推測，直接按 `\n` 切塊即可。

**`.csv` 不可能有這個保證。** RFC 4180 明文允許引號內換行，Excel 會產生它，而那些檔案
已經存在。完整的 RFC 4180 解析器不會因此變得不需要。

### `.csv2` 的換行以反斜線跳脫

```
儲存格內的 \n  →  寫成 \n（兩個字元）
儲存格內的 \r  →  寫成 \r
儲存格內的 \   →  寫成 \\
```

**這不是發明。** PostgreSQL 的 `COPY ... TEXT` 與 IANA 的 `text/tab-separated-values`
用的正是這一套，目的相同：讓紀錄保持行分隔。

選反斜線而不選「資料中不可能出現的控制字元」（例如 VT `0x0B`，那樣可以完全不需要跳脫
系統），是因為**可讀性在這裡是功能而非裝飾**：這個格式有一半的價值在於能被人在 git diff
裡讀懂，而 `note1\nnote2` 一眼可辨、`note1^Knote2` 不行。

**代價要講明：`.csv2` 因此有兩套跳脫機制並存**——RFC 4180 的 `""`，加上反斜線。這是個
wart，不藏。而且既有資料中的每個反斜線（Windows 路徑、正則式）寫進 `.csv2` 時會變成
`\\`：可逆、不歧義，但位元組會變。

三個必須釘死的細節：

**只在 `.csv2` 生效。** `.csv` 的輸出維持純 RFC 4180，引號內就是真的換行。那是標準，
Excel 讀得懂，不能動。

**只有含這四個字元的儲存格會被改動**，其餘逐位元原樣寫出。

**讀取端一律解釋反斜線**，因此含孤立反斜線的儲存格**必須**寫成 `\\`，否則讀回來有歧義。
未定義的跳脫序列（例如 `\q`）是**錯誤**，不是「原樣保留」——後者會讓兩個不同的位元組
序列讀回同一個值，破壞無損性。

**這取代了先前「拒絕寫入含換行的儲存格」的決定。** 自動跳脫使 `.csv` → `.csv2` 的轉換
永遠成功；一個轉換工具在合法輸入上失敗，是很難向使用者解釋的行為。

### 讀取：不「偵測檔案的行尾」，而是逐筆判斷

**不要先掃描整個檔案、判定它是「CRLF 檔」或「LF 檔」，再據此解析。** 那個做法在混合
行尾的檔案上會錯——而混合是真實會發生的：有人在 Windows 上編輯了檔案的一部分，或是
兩份不同來源的資料被 `cat` 在一起。

正確的規則不需要偵測，也不需要任何全域狀態：

> 紀錄邊界是**引號外的 `\n`**；若其緊鄰的前一個位元組是 `\r`，該 `\r` 屬於分隔符，
> 不屬於資料。

這一條同時正確處理純 LF、純 CRLF、以及混合的情況。**「偵測是不是 Windows 來的」這件事
因此自動完成了**，不需要一個獨立的偵測步驟——而少一個步驟就少一處可能判斷錯的地方。

### 但引號內的位元組一個都不能動

這裡有一個必須講明的衝突。「檔案裡只能有 `\n`」若照字面執行，就得把**引號內**當作資料
的 `\r\n` 也改掉——而那會破壞計畫中第一項、也是最有價值的那個測試：
`TARGET_PACKAGES.csv` round-trip 後逐位元相同。

決定：**「一律 LF」講的是紀錄分隔符，不是檔案裡的每一個位元組。** 引號內的內容是資料，
原樣保留，包含其中的 `\r`。

因此嚴格來說輸出檔案可能仍含有 `\r`——但只會在引號內。這個區別要寫進 `--help`，因為
「LF only」這句話單獨看會被理解成前者。

保真勝過整齊：一個工具若會安靜地修改它宣稱只是在讀取的資料，就不能被信任拿來處理
正式檔案。

### 讀 CRLF、寫 LF 意味著檔案會變

`csv2 -r -i x.csv -o x.csv` 在一個 CRLF 檔案上，會使整份 git diff 變動。這是正確的行為
（那正是本專案要的結果），但會讓人意外。

決定：以 INFO 層級記入 `-log`（「輸入含 N 筆 CRLF 行尾，已正規化為 LF」），**不印到
stderr**——正常路徑上不出聲那條規則不因此破例。要事先知道的人可以先跑 `-debug`。

### 純 CR（舊 Mac）視為資料，但要能說出問題

單獨的 `\r` **不是**紀錄分隔符。把它當分隔符會破壞含有 CR 的資料，而 OS X 之前的
CR-only 慣例早已絕跡。

但這會產生一個很難懂的失敗：一個 CR-only 的檔案裡沒有任何 `\n`，於是整份被解析成
**一筆有數百萬欄的紀錄**，接著撞上欄數檢查，錯誤訊息卻在講欄數。

決定：偵測「完全沒有 `\n`、卻含有 `\r`」這個特定情況，並以明確的訊息結束——
「本檔案使用 CR 行尾（OS X 之前的 Mac 慣例），非 CSV 所支援；請先以 `tr '\\r' '\\n'`
轉換」。這是「大聲失敗」的典型案例：診斷成本幾乎為零，而少了它，使用者會被引去查
一個完全無關的方向。

### BOM 是同一類問題

UTF-8 BOM 同樣是「這個檔案來自 Windows」的標記——Excel 匯出的 CSV 就帶著它。
**讀取時偵測並剝除，寫入時永不產生。**

不剝除的話，第一欄的欄名會變成 `\ufeffpkg_name`，於是以欄名定址全部失敗，而印出來
看起來完全正常。這與尾隨 CR 是同一種失敗：肉眼不可見，比對卻不相等。

### 對平行區塊掃描的影響

區塊邊界可能剛好切在 `\r` 與 `\n` 之間。掃描器必須處理「本區塊以 `\r` 結尾」的情況，
不能假設兩者總在同一塊內。這是小事，但漏掉就會在特定檔案大小上偶發，正是最難重現的
那一類。

### 引號內含換行時，「row」與人眼看到的行不一致

一筆紀錄可以跨多個物理行。使用者拿 `12` 去 `sed -n 12p` 會取到錯的東西。

決定：**預設回報紀錄號**（那是 CSV 的正確答案），並提供 `--physical` 額外輸出該紀錄
起始的物理行號。兩者同時需要時，格式為 `12:6@L34`。

這一點必須寫進 `--help`，因為它與 `grep -n` 的直覺相反，而不一致的直覺是錯誤的來源。

### A1 記法

試算表使用者熟悉 `F12` 這種寫法。它易讀，但超過 Z 之後變成 AA、AB，且它假設了一個
試算表模型（有標頭、欄固定）。

決定：**不做預設，提供 `--a1` 作為額外輸出**。CSV 未必有標頭、欄數未必一致，把 A1
當主要格式會在那些檔案上變成謊言。

## `--json` 輸出

**採用。** 給下游腳本用的格式不該需要再解析一次對齊過的文字——這支工具的存在理由
正是「不要再自己解析了」，若它的輸出還要別人 `awk` 一遍就自相矛盾。

每列一個 JSON 物件（JSON Lines），而非一個大陣列——這樣可以串流，與 `-so` 的
「不得緩衝整份輸出」一致：

```json
{"meta":{"headers":2,"fields":7,"records":21}}
{"record":12,"field":6,"header_en":"status_notes","header_zh":"狀態註記","value":"…","line":34}
{"record":12,"field":2,"header_en":"version","header_zh":"版本","value":"…","line":34}
```

第一行是 metadata，帶出工具「認為」的格式。下游可以據此斷言 `headers` 是否符合預期，
而不是默默接受一個猜錯的解析。

`--json` 與 `-contains`、`-head`、`-tail`、`-A/-B/-C` 皆可組合。字串一律以 JSON 規則
逸出，因此含引號、換行、tab 的欄位值可以安全傳遞——這正是目前用 `cut -d,` 做不到的。


## `.csv.index` / `.csv2.index`：紀錄偏移量的 sidecar

### 它永遠是最佳化，永遠不是必要條件

**這是這整個功能的第一條規則，其餘都從它推導：沒有索引時，程式的行為必須完全一樣。**

| 情況 | 行為 |
|---|---|
| 索引不存在 | 掃描。正常路徑，不警告 |
| 索引過期 | 忽略，掃描。以 INFO 記入 `-log` |
| 索引損毀／截斷／版本不符 | 忽略，掃描。**不是錯誤** |
| 索引所在目錄不可寫 | 不寫。警告一次，操作照常完成 |

**任何情況下都不得因為索引而使操作失敗，也不得因為索引而產生不同的輸出。** 有索引與
無索引的輸出必須逐位元相同——這要納入驗收條件，與「平行與單執行緒輸出相同」同一條理由。

一個會很快給你錯資料的索引，比沒有索引糟得多。因此**驗證失敗時的預設動作是丟棄**，
不是修復，也不是報錯。

### 為什麼寫入時做幾乎免費

寫入端本來就知道每一筆從哪個 byte 開始——它剛剛才寫下去。順手記下來不需要額外掃描。
接手別人產生的 CSV 時才需要付一次完整掃描，而那次掃描本來就要做。

### 格式：二進位定寬

一筆 8 bytes（u64 LE），第 N 筆的偏移量就在 `header + 8*N`——**O(1) 直接 seek**。
若寫成一行一個數字的文字檔，得先掃描索引才能找到第 N 筆，那就沒有意義了。

這不違背本專案「檔案要人看得懂」的立場：索引是衍生的快取，不是資料。

**稀疏，不是每筆都存。** 只存第 0、stride、2×stride… 筆的偏移量，stride 記在檔頭
（預設 256）。要第 N 筆就 seek 到 `⌊N/stride⌋` 那一格，再向前解析至多 stride 筆。

密集索引（每筆 8 bytes）在大檔案上會失控：1 GB、每列 500 bytes 是 200 萬筆，索引就要
16 MB。stride 256 讓它變成 64 KB。而向前掃描的那段只有幾十 KB，一兩次磁碟讀取就拿到，
與省下的整檔讀取相比可以忽略。

**這對兩種格式都成立**，因為 stride 格點上的偏移量必定是紀錄的起點，也就必定在引號外——
從那裡開始解析不需要知道任何前文狀態。

只索引資料列；標頭的結束位置與總筆數寫在檔頭（總筆數讓 `-tail` 不必先數）。

### `.csv` 與 `.csv2` 的索引：檔案格式相同，建立方式不同

**索引檔的格式一模一樣**——偏移量就是偏移量。一種格式、一條讀取路徑、一套驗證邏輯。
不要為兩種副檔名做兩種索引，那只會多一倍的錯誤面積。

差別在**怎麼算出那些偏移量**：

| | `.csv2` | `.csv` |
|---|---|---|
| 找紀錄邊界 | `memchr('\n')`，因為一筆 = 一行 | 完整 RFC 4180 解析，要追蹤引號狀態 |
| 平行化 | 直接按位元組切塊，無需推測 | 需要兩狀態推測解析 + 一次 O(區塊數) 的序列定案 |
| 建立成本 | 記憶體頻寬等級 | 數倍於前者 |

**因此索引對 `.csv` 反而更有價值。** `.csv2` 沒有索引時，切塊平行處理仍然是無腦的；
`.csv` 沒有索引時，連「這個位元組是不是在引號內」都要從檔頭推導。索引把那件事一次算完
並存下來。

**檔頭多存一個布林值：`no_embedded_newlines`。** 建立索引時順手就知道，而它的用處很大：
為真時，`.csv` 之後的平行操作可以走 `memchr` 的快路徑，不必再做兩狀態推測。

這不是罕見的情況——本 repo 樹內**每一份** CSV 都是這樣（實測，見上）。所以那條快路徑
是常態而非例外。

### 驗證：全部 O(1)，且明說它是啟發式

檔頭記錄 `(檔案大小, mtime 到奈秒, 前 64 bytes 與後 64 bytes 的雜湊, 格式版本)`。

要說清楚這是**啟發式而非證明**：`rsync -t`／`cp -p`／`tar -p` 會保留 mtime，理論上可以
構造出「內容不同但大小與 mtime 相同」的檔案。前後 64 bytes 的雜湊擋掉絕大多數，但不是
證明。需要確定的人用 `--verify-index` 做 O(n) 的完整比對。

### 寫入順序

**資料檔 rename 完成之後才寫索引**，索引自己也走 temp+rename。中途被打斷的話，索引要嘛
不存在、要嘛驗證不過——兩種都會退回掃描，都是安全的。反過來寫（索引先落地、資料寫失敗）
會得到一個描述著不存在內容的索引。

### 自動啟用的門檻用 bytes，不用列數

**已量測**（本機，warm cache，`memchr` 等級的換行掃描）：

| 大小 | 紀錄數 | 掃描時間 | 吞吐量 |
|---|---|---|---|
| 1 MiB | 41,943 | 0.35 ms | 2868 MiB/s |
| 16 MiB | 671,088 | 5.49 ms | 2916 MiB/s |
| 64 MiB | 2,684,354 | 19.69 ms | 3250 MiB/s |

**列數是錯的判準，有兩個理由。**

**一、同樣的列數代表差 20 倍的成本。** `TARGET_PACKAGES.csv` 是 478 bytes/列，
`marathon-data.csv` 是 23 bytes/列。10,000 列在前者是 4.8 MB（約 1.6 ms），在後者是
230 KB（約 0.08 ms）。用列數當門檻，行為會取決於列寬——而列寬不是決定成本的東西。

**二、要知道列數就得先數列**，那正是想省掉的掃描。檔案大小 `stat` 一次就有，O(1)。

**門檻起點 16 MiB**，以 `CSV2_INDEX_MIN_BYTES` 覆寫。環境變數不只是為了調校，是為了
**能測試**——否則驗證這條邏輯需要 16 MiB 的 fixture。

### 索引真正省下的是 I/O，不是 CPU

上面的數字只說明 CPU 掃描成本。關鍵在 cold cache：有索引時，取第 10,000 筆是「讀 8
bytes 索引 + seek + 讀一筆」，**整個檔案根本不必讀進來**。在 QEMU 的磁碟上，一個
100 MB 的檔案是數百 ms 到 1 秒。

這也劃出了它不管用的地方：`-r`、`-contains` 這類**全檔掃描**的操作無論如何都要讀完整個
檔案，索引幫不上忙。只有隨機／局部存取（`-mid`、`-tail`、`-update r:c`）受益——`-tail`
從環狀緩衝掃全檔變成 seek，`-mid` 從跳過前 a 筆變成 seek。

因此：**只在該次操作用得到隨機存取時建索引，以及寫入時順手建。** 全檔掃描的操作不留下
索引檔，那是純浪費。`-so` 不寫（沒有可並排的檔案）。

### 兩件要誠實講明的事

**這個 repo 自己的資料永遠不會觸發它。** 我們的 CSV 是 10–24 KB，比任何合理門檻低三個
數量級。寫在這裡，是為了日後不要有人以為「自動索引壞了」——它是刻意不作用。

**`-update` 迴圈是病態案例。** 每次改寫都讓索引過期，於是索引維護反而成為主要成本。
單靠檔案大小分辨不出「穩定的大檔被反覆讀」與「大檔被反覆寫」，所以要留一個關閉的方式
（`--no-index`）。

### `.gitignore`

`*.csv.index` 與 `*.csv2.index` 是衍生物，不進版控。母專案的 `.gitignore` 要一併加上。

## 多核

依你的指定：**固定為 `ProcessInfo.processInfo.activeProcessorCount`**，不提供旗標
（`-n` 已被列號佔用）。這與 swift_tar 的做法相同（`swift_tar.swift:3407`）。

**但 CSV 解析本身無法從任意位元組位移切開。** 一個位移落在引號內或引號外，語意完全
不同，而要知道自己在不在引號內，必須從檔案開頭讀過來。所以「多核」不能是「把檔案切
成 N 段各自解析」。

可行的做法，依風險由低到高：

1. **解析單執行緒、每筆紀錄的工作平行化**（`-contains` 的比對、欄位轉換）。安全，
   對大量欄位的檔案有效，對 `-head 10` 無意義。
2. **切段後重新同步**：從每段起點掃描到下一個「確定在引號外」的換行。這在 RFC 4180
   下**無法保證**——一段全是引號欄位的資料可以讓兩種對齊都自洽。若採用，必須以
   單執行緒解析結果做交叉驗證，並在不一致時失敗。
3. **先做一次快速掃描建立紀錄邊界索引，再平行處理。** 掃描仍是單執行緒但很便宜
   （只找引號與換行），之後可完全平行。這是我建議的路線。

不論選哪一條，**驗收條件是「平行與單執行緒的輸出逐位元相同」**，並以此寫成測試。
今天這個 session 已經反覆證明：這個專案的失敗多半是靜默的，平行化尤其容易產生
「大部分情況正確」的結果。

## `-append` 的快路徑：不重寫整個檔案

### 為什麼只有 `-append` 值得這樣做

其餘的編輯動詞都要重寫全檔（temp + rename）。**而既然已經在寫每一個位元組，就已經知道
每一筆的新偏移量——邊寫邊產出新索引即可，不需要任何 delta 運算。**

（先前寫的「`-update` 迴圈會讓索引抖動」是把重點放錯了：抖動的成本在**資料的重寫**，
不在索引。索引是順手的副產品。此處更正。）

所以「用 byte offset 增量更新索引」只有在**資料本身也能增量寫入**時才有意義，而那只有
一種操作成立。

| 操作 | 做法 | 理由 |
|---|---|---|
| **`-append`** | **`O_APPEND` 就地追加，O(1)** | 安全且快，見下 |
| `-update`（等長） | 不列入預設 | 技術可行，但放棄原子性與讀者快照 |
| `-update`（變長）／`-insert`／`-delete` | 重寫全檔，邊寫邊產索引 | 尾端搬移**既是 O(n) I/O 又失去原子性**，兩邊都輸給重寫 |

這把「加一筆到 1 GiB 的檔案」從 **26 秒**變成毫秒級。`artifacts.csv` 每次建置追加一列，
正是這個形狀。

### 為什麼追加是安全的，而就地覆寫不是

**斷電時的最壞情況是「檔尾多了一筆不完整的紀錄」**，前面所有內容與索引都仍然有效。
相對地，就地覆寫一個等長的儲存格，斷電可能留下一個既非舊值也非新值的垃圾——而這個
專案的資料檔正是靠 temp+rename 的「要嘛全新、要嘛全舊」在支撐的。

就地覆寫還會失去另一個性質：目前 rename 之後，並行的讀者仍持有舊 inode，看到的是一份
一致的快照。就地覆寫讓讀者看到半更新的狀態。

**追加是唯一一個多寫入者安全的操作。** POSIX 保證 `O_APPEND` 的偏移量更新與寫入是原子
的，因此只要每筆是**單一次 `write()`**，兩個並行的 `-append` 不會交錯。這與其餘操作
形成對比（那些的「後 rename 者全贏」問題仍然存在）。

**但這個保證有邊界，要寫進說明**：NFS 上的 `O_APPEND` 不是原子的；超過一定大小的
`write()` 也可能被拆開。因此**保證是「盡力」，不是「必然」——偵測仍然必須存在。**

### 撕裂的追加要能偵測，且不自動修復

`.csv2` 保證一筆一行且以 LF 結尾，因此**檔案未以 LF 結尾**就是撕裂的信號。
`.csv` 另可從「EOF 處有未閉合的引號」偵測。

決定：偵測到就**明確報錯**，指出最後一筆不完整，並提供 `--truncate-partial` 讓使用者
明示要丟掉它。**不自動修復**——自動丟棄一筆使用者以為已經寫入的資料，正是這份設計
一直在避免的靜默行為。

### 追加之前必須做的三件事

**一、檢查檔案是否以換行結尾。** 若否（前一次寫入不完整，或別的工具產生的檔案沒有
結尾換行），必須先補一個 LF，否則新紀錄會被接到最後一筆的尾巴上，**兩筆變成一筆**。
這是 seek 到 `size-1` 讀一個位元組，O(1)。

**二、驗證欄數與標頭相符，且在寫入之前。** 寫下去就收不回來了——這與重寫路徑不同，
那裡失敗只是丟掉暫存檔。

**三、套用 `.csv2` 的反斜線跳脫與 RFC 4180 引號。** 與其他寫入路徑同一套程式碼，
不要為快路徑另寫一份。

### 索引怎麼跟上

**沒有索引時不要建。** 為了一個 O(1) 的操作去做一次 O(n) 的全掃描，是把快路徑的意義
全部抵銷掉。維持沒有索引。

**有索引時**：紀錄數 +1；若跨越了 stride 格點就追加一格偏移量（就是追加前的檔案大小）；
重新計算檔頭的驗證欄位（大小、mtime、尾端 64 bytes 的雜湊）。全部 O(1)。

**順序：先寫資料並 `fsync`，再更新索引。** 中間被打斷的話索引是過期的，會被驗證擋下並
退回掃描——安全的降級。反過來則會得到一個描述著不存在內容的索引。

### 檔案不存在時

`-append` 到一個不存在的檔案：**報錯**，除非同時給了 `-t` 與標頭來源（`--headers-from`
或輸入檔）。無聲地建立一個沒有標頭的 `.csv2` 會產生一個對自己格式說謊的檔案——與
`-head` 那條規則同一個理由。

## 與資料庫的比較，以及該在哪裡收手

| | 舒適讀取規模 | 硬上限 | 改一格要寫入 |
|---|---|---|---|
| **csv2**（唯讀 + 索引） | ~100 GiB | 檔案系統 | — |
| **csv2**（有寫入） | **< 1 GiB** | ~17 GiB（2× 空間） | **整個檔案** |
| **SQLite** | 100 GiB – 1 TB | 281 TB | 一個 page（4–8 KB）+ WAL |
| **PostgreSQL**（單機） | 數百 GiB – 數 TB | 32 TB/表 | 一個 8 KB page + WAL |

### 差距不在容量，在「改一格的成本」

1 GiB 的資料集，改一個儲存格：PostgreSQL 寫約 **10 KB**，csv2 寫 **1 GiB**——約十萬倍。

以實測的 39 MiB/s 換算，PostgreSQL 是 0.25 ms，csv2 在 **16 MiB** 的檔案上就已經是
0.4 秒。**即使在小到不像話的規模，資料庫也已經快了 1600 倍**，且比值隨檔案線性擴大。

這不是實作品質的差距而是架構的差距：資料庫用固定大小的 page + 就地更新 + WAL，
csv2 用「重寫全檔 + rename」換取原子性與純文字。`-append` 的快路徑正是為了在最常見的
那個形狀上避開這個代價。

### 讀取的比較完全不同

- **全表掃描 csv2 有優勢。** PostgreSQL 的 seq scan 每列要處理 24 bytes 的 tuple
  header、page 結構與 MVCC 可見性判斷；CSV 掃描只有 `memchr` 與解析。
- **依位置隨機存取打平。** 稀疏索引是 seek + 掃 ≤stride 筆；B-tree 是 3–4 次 page 讀取。
- **依鍵值查詢輸得很慘。** O(n) 全掃 對 O(log n)——索引只索引位置，不索引內容。

### 儲存空間 csv2 比較小

PostgreSQL 每列有 24 bytes 的 tuple header，加上對齊與 page 填充率，再加上索引（單欄
B-tree 通常是表大小的 20–40%）。同一份資料在 PostgreSQL 裡通常是 CSV 的 1.3–2 倍；
窄表可以到 3–5 倍。

「用 CSV 省空間」是真的，只是省下的空間換掉了寫入效能與查詢能力。

### 界線

> **超過 1 GiB 且有寫入流量，或需要依鍵值查詢時，改用 SQLite。**

SQLite 才是 csv2 真正的鄰居，不是 PostgreSQL：同樣單一檔案、無 daemon、無 schema
migration，但它有 B-tree、page 級更新與交易。

csv2 相對 SQLite 只剩下**一個**優勢：**檔案是人看得懂、git diff 得出來的純文字**。

而那個優勢對本專案恰好是全部的重點——`TARGET_PACKAGES.csv` 與 `artifacts.csv` 靠 git
保存與審閱，先前兩次寫壞都是從 git 還原的。SQLite 檔案在 git 裡是一團二進位，diff 不
出來，也還原不了「只有中間幾個字被改掉」那種損壞。

**csv2 的定位是「給人看、給 git 管、給腳本安全處理的表格檔」，不是儲存引擎。**

## Unicode 與 emoji

`.csv` 與 `.csv2` **一律 UTF-8**，兩者規則相同。emoji 必須完整支援，包含 ZWJ 序列、
膚色修飾符、區域指示符旗幟與 keycap。

### 對解析器來說，emoji 是免費的

**UTF-8 是自同步的**：多位元組序列的任何一個位元組都 ≥ 0x80，不可能與 ASCII 的
`,`、`"`、`\n`、`\r`、`\` 混淆。已實測驗證。

因此**以位元組為單位的解析器天生就正確處理 emoji**，包含平行切塊——區塊邊界即使切在
一個 4 位元組序列的中間也不影響邊界判定，因為那些位元組不會被誤認為分隔符。

危險的是反過來做：把輸入解碼成 `String` 再逐 `Character` 迭代，不但慢，而且**更容易出錯**。

**核心以位元組處理，只在真正需要時才解碼。** 這條規則同時帶來一個額外的好處：內含
非 UTF-8 位元組的檔案（Latin-1 的舊資料）也能逐位元 round-trip，而不是被換成 U+FFFD ——
那會是靜默的資料損毀。UTF-8 的驗證只在需要的操作上做（`--json`、`-md` 的寬度計算、
正規化），不合法時**報錯**，不替換。

### 真正會出問題的地方：顯示寬度

實測數據：

| 樣本 | 位元組 | 碼位 | grapheme cluster | 終端機顯示寬度 |
|---|---|---|---|---|
| `ok` | 2 | 2 | 2 | 2 |
| `套件名稱` | 12 | 4 | 4 | **8** |
| 😀 | 4 | 1 | 1 | 2 |
| 👍🏽 | 8 | 2 | 1 | 2 |
| 👨‍👩‍👧‍👦 | 25 | 7 | **1** | 2 |
| 🇹🇼 | 8 | 2 | 1 | 2 |
| 1️⃣ | 7 | 3 | 1 | 2 |

**這是四個互不相等的數字**，而 `--pretty` 的欄寬對齊需要的是最後一欄。

Swift 的 `String.count` 給的是 grapheme cluster 數：家庭 emoji 是 **1**，但佔 2 欄；
`套件名稱` 是 **4**，但佔 8 欄。用 `.count` 對齊，兩者都會歪。

**而這個問題在 emoji 出現之前就已經存在了**：`.csv2` 的第二列標頭是繁體中文，全形，
每字 2 欄。所以 `--pretty` 對既有的設計資料就是壞的。emoji 只是讓它更明顯。

決定：**`--pretty` 需要一張 UAX #11（East Asian Width）的寬度表**——全形與 emoji
presentation 記 2，組合記號／ZWJ／variation selector 記 0，其餘記 1。若不做這張表，
`--pretty` 的說明必須寫明它只對 ASCII 正確。

**預設不對齊這個決定因此更站得住腳**：最小形式的 `|a|b|` 在任何 renderer 下呈現結果
相同，且完全不需要知道顯示寬度。

### 正規化：儲存絕不動，比對才動

`é` 的 NFC 是 2 位元組、NFD 是 3 位元組（實測）。macOS 的檔案系統回傳 NFD，Linux 慣用
NFC，因此**同一個字串在兩個平台上可能是不同的位元組**。

emoji 本身不受 NFC/NFD 影響（沒有分解形式），但帶重音的拉丁字母與諺文會。

決定：

- **儲存時絕不正規化。** 正規化會改動位元組，破壞 round-trip 逐位元相同這項第一測試。
- **比對預設逐位元組。** 這使輸出在兩個平台上可預測。
- `--normalize` 讓 `-contains` 在比對前把兩邊都轉成 NFC。這是選擇加入的，因為它會讓
  「找得到」與「檔案裡實際是什麼」分離，那個差異必須是使用者明確要求的。

**`-hash` 雜湊的是儲存的原始位元組**，不是正規化後的形式。因此同一個「看起來一樣」的
字串，在 NFD 檔案與 NFC 檔案上會得到不同的雜湊。這要寫進說明——否則跨平台比對雜湊
會得到假的不相符，而原因完全看不出來。

### 截斷必須在 grapheme cluster 邊界

任何會截斷儲存格的地方——最可能是**錯誤訊息裡回顯的欄位值**——若按位元組截斷，會切壞
UTF-8 序列，產生亂碼或使後續處理失敗。

家庭 emoji 是 25 個位元組、7 個碼位、1 個 cluster。從中間切開會得到半個家庭。

決定：截斷一律在 grapheme cluster 邊界，且在被截斷處加上明確標記。**一個在報告錯誤時
自己產生亂碼的工具，會讓人去查錯的方向。**

### `--json` 直接輸出 UTF-8

emoji 以原始 UTF-8 寫出，那是合法的 JSON，也比 `\ud83d\ude00` 的代理對短。
**預設不跳脫非 ASCII 字元。** 需要純 ASCII 輸出的場合另以 `--json-ascii` 提供。

必須跳脫的只有 JSON 規定的控制字元。

### 測試素材

測試檔要包含：ZWJ 家庭、膚色修飾符、區域指示符旗幟、keycap、全形中文、NFC 與 NFD 的
同一個字、以及一段非 UTF-8 的位元組。全部都要 round-trip 逐位元相同。

`TARGET_PACKAGES.csv` 是最好的真實素材，但它是純 ASCII；上述這些要另外造，因為它們
不會自己出現，而不會自己出現的東西就不會被自然測到。

## 規模與效能的邊界

### 已量測的兩個數字

| | 數值 |
|---|---|
| 換行掃描（warm cache，`memchr` 等級） | **2900 MiB/s** |
| 寫入 + `fsync`（`/Volumes/LinuxCS`） | **39 MiB/s** |
| 該 volume 可用空間 | 34 GiB |

**寫入是讀取的 1/75。** 瓶頸不在解析，在寫。

那個 39 MiB/s 的性質要講明：`LinuxCS.sparseimage` 是掛在 `/Volumes/Windows` 上的
sparse image，且這是寫入尚未配置的區塊。但那正是 csv2 的情況——temp+rename 每次都寫
全新的區塊，所以這就是相關的數字。**guest 在 QEMU 下要另外量，只會更慢。**

### 會先壞掉的地方，依順序

**一、任何編輯都要重寫整個檔案。**

| 檔案大小 | 改一格的時間 |
|---|---|
| 16 MiB | 0.4 s |
| 1 GiB | **26 s** |
| 10 GiB | **4.4 min** |

代價與檔案大小成正比，與改了多少無關。

**二、原子寫入需要 2 倍磁碟空間。** 34 GiB 可用 → 可編輯檔案上限約 **17 GiB**。
失敗模式是對的（寫暫存檔時 ENOSPC，原檔完好），但錯誤訊息必須明說需要 2 倍空間，
否則會被當成檔案系統故障。

**三、索引在編輯迴圈裡抖動。** N 次 `-update` = N 次全檔重寫 + N 次索引重建。
這使「所有索引指向輸入、一次套用」那條規則不只是語意正確——在大檔案上它是唯一的活路。
要寫進 `--help`。

**四、guest 只有 2–4 GiB RAM。** 三個必須盯住的地方：

- **平行區塊的記憶體 = 工作者數 × 區塊大小。** 絕不可寫成「檔案大小 ÷ P」，那會把
  100 GiB 切成 8 個 12.5 GiB 的區塊。必須是固定大小的小區塊（4–16 MiB）配工作佇列。
  這是這類程式最經典的錯誤。
- **`-tail N` 與 `-B N` 的記憶體由使用者控制。** `-tail 10000000` 就是 OOM。要設上限
  或溢寫到磁碟，不能照做然後死掉。
- **`--pretty` 已明文放棄串流**，在大檔案上是 OOM 而非變慢。應在超過門檻時**拒絕**，
  而不是試著做完後被 OOM killer 殺掉。

**五、加密會膨脹。** 每格 nonce 12 + tag 16 = 28 bytes，再乘 base64 的 4/3。暫存檔那
2 倍空間是以**輸出**大小計算的。

### 規模分級

| 大小 | 預期 |
|---|---|
| < 16 MiB | 瞬間完成，不需索引也不需平行。**本 repo 全部資料都在此區間** |
| 16 MiB – 1 GiB | 索引開始有價值。編輯 0.4–26 s。可接受 |
| 1 – 10 GiB | 只讀 + 索引仍舒適（隨機存取 O(1)）。編輯難以忍受。串流紀律在此受考驗 |
| 10 – 17 GiB | 空間上限。只讀可行，編輯基本上不可行 |
| > 17 GiB | 唯讀且只做隨機存取。全檔掃描以分鐘計 |

**簡短版：讀取可以撐到很大，寫入在 1 GiB 就開始痛，17 GiB 是硬牆。**

### 寫程式之前應該先量的（事後才量，2026-08-18）

- **guest 在 QEMU 下的磁碟吞吐量**
- **Swift 實作的完整 RFC 4180 解析吞吐量** —— 上面 2.9 GB/s 是純 `memchr`，真正的解析器
  會慢一個數量級，而那決定了平行化值不值得
- **`fsync` 的固定成本** —— 它決定小檔案編輯的時間下限

本專案有過「開機時間結論錯誤、事後要更正並修一輪文件」的紀錄。這幾項要在寫程式之前量，
不是事後。

**這段警告沒有被遵守。** 三項都是在第 1–6 階段全部完成之後才量的，量測腳本是
[`../verifications/measure.zsh`](../verifications/measure.zsh)，結果在
`measure_output.txt`。以下是實測（macOS arm64，26.6 MB／20 萬筆、含逗號的引號欄位）：

| 項目 | 計畫的假設 | 實測 | 差距 |
|---|---|---|---|
| 完整 RFC 4180 解析 | 2900 MiB/s（純 `memchr`），並預期「慢一個數量級」 | **45 MiB/s** | **慢 64 倍**，不是 10 倍 |
| 平行解析 | 未預測 | **124 MiB/s，2.76×**（10 個 worker） | 遠非線性 |
| 重寫整檔 | 39 MiB/s | **38 MiB/s** | 準確 |
| 1 GiB 改一格 | 26 秒 | **26.9 秒**（依實測推算） | 準確 |
| 最小編輯的下限 | 未量 | **0.019 秒**／次 | — |

**寫入端的預測是準的，讀取端差了 64 倍。** 計畫自己已經警告過「真正的解析器會慢一個
數量級」——方向對了，幅度低估了六倍。

### 而門檻因此變得比原本更站得住腳

16 MiB 的索引與平行門檻是對著 2900 MiB/s 挑的。在那個速率下，掃描 16 MiB 只要
**0.0055 秒**——為此維護一個 sidecar 說不過去。在實測的 45 MiB/s 下是 **0.355 秒**，
那個門檻就合理了。

**結論是對的，理由原本是虛的。** 這正是那段警告在防的事：一個從錯誤數字推出的正確
答案，下一次換個情境就不會再對。現在它有實測撐著了。

平行只有 2.76 倍而非接近 10 倍，原因寫在 `Parallel.swift` 裡：第一遍找紀錄邊界與計數
是單執行緒的，之後才平行。要寫進說明，否則會有人期待線性加速。

### guest 在 QEMU 下（第三項，已量）

`run_csv2_test.zsh` 現在會在 guest 內跑同一支 `measure.zsh`，並把輸出擷取回 host
（`verifications/measure_output_linux.txt`）。以 20000 筆的語料，與 macOS 同筆數的
執行相比：

| 項目 | macOS（20000 筆） | guest（20000 筆） | |
|---|---|---|---|
| 完整解析 | 41 MiB/s | **37 MiB/s** | 只慢一成 |
| 重寫整檔 | 28 MiB/s | **33 MiB/s** | guest 反而較快 |
| 最小落地編輯 | 0.0192 s | **0.0045 s** | guest 快 4 倍 |
| 平行（強制開啟） | 2.7× | **0.94×**——比單執行緒更慢 | |

**解析只慢一成**，因為 guest 走的是 `-accel hvf`：Apple Silicon 上的 aarch64 是硬體
虛擬化而不是指令模擬。這對「什麼東西該在哪裡跑」的判斷有直接影響。

**寫入端那兩個數字不能照字面讀。** guest 看起來比較快，是因為它做的事比較少：QEMU 的
`-drive` 沒有指定 `cache=`，預設 `writeback`；guest 的 flush 到達 host 之後是
`fsync(2)`，而在 macOS 上 `fsync` 並不會強制磁碟清空自己的揮發性快取——那需要
`F_FULLFSYNC`，也正是 csv2 在 Darwin 上直接呼叫的東西。所以 macOS 的 0.0192 秒與
guest 的 0.0045 秒衡量的不是同一件事：一個是資料真的落到碟片，另一個是資料離開了
guest。**guest 的持久性數字上限受 host 的 QEMU 設定所限，不是 Linux 的性質。**

**平行在 guest 上是淨損失（0.94×）**，而這正好證明門檻有在做事：那個 2.6 MB 的語料
遠低於 16 MiB，量測是用 `CSV2_PARALLEL_MIN_BYTES=1000` 強制開啟的。在預設門檻下平行
根本不會啟動——也就是說，門檻擋掉的正是一次會讓事情變慢的平行化。這是門檻第二次被
實測支持，而且這次是在它「該拒絕」的那一側。

## 建置與打包

### 目前不進 rootfs

**決定（2026-08-15）：csv2 暫不納入 guest rootfs、常駐 workspace 或 prebuilt 收成。**

這**不表示不在 Linux 上跑**。測試仍必須兩個平台都做（見「測試」一節）——「不隨映像
出貨」與「不在該平台上驗證」是兩件不同的事，混為一談就會得到一個從未在目標平台上
執行過的工具。

理由是使用場合就在 host 上。會被 csv2 修好的那兩次事故——`TARGET_PACKAGES.csv` 的
`status_notes` 被 `${line%,*}` 改寫、`artifacts.csv` 的 commit 字串被寫進 `built_utc`
——都是 **host 端的腳本**造成的，而 `update_licenses.sh` 這類真正需要 CSV 解析的東西
也在 host 上跑。guest 裡目前沒有任何東西讀寫 CSV。

暫緩也拿掉了兩項成本：不必佔用 rootfs 那 47.4 MiB 中的任何一份，也不必在建置流程尚未
穩定時再多綁一個交叉編譯目標。

**已更新（2026-08-16）：** 上面原本寫著「尚未寫入任何建置腳本」。現在有
`compile_csv2.zsh` 了，但它是 **host 端**的建置，只產生 `release/csv2`。
「暫不進 rootfs」這個決定沒有變——`csv2` 仍然不出現在母專案任何 rootfs／workspace／
prebuilt 的腳本中，因此這仍然不是「移除」，只是不要開始。第 6 階段要新增的
`compile_csv2_linux.zsh` 也屬於「能在 Linux 上建置並測試」，不屬於「隨映像出貨」。

這也讓一件事變得沒有意義：guest 內的 `-encrypt`。multissh 的金鑰本來就不隨 rootfs 進入
guest（見上），所以那條路徑原本就只會走到「找不到金鑰」的錯誤。

**要恢復時，需要的是下面這張表**，原封保留於此，因為屆時重新推導一次沒有意義：

| 階段 | 對應的既有機制 |
|---|---|
| guest 內建置 | 新增 `compile_csv2_linux.zsh`，比照 `compile_swift_tar_linux.sh` |
| workspace | 建置腳本的 rsync 區段新增一條，或改為與 swift_tar 同層 |
| prebuilt 收成 | `update_prebuilt.sh` 的清單新增 `csv2`，`MANIFEST.csv` 自動涵蓋 |
| 產物記錄 | `artifacts.csv` 新增一列；`version.txt` 新增 `csv2_commit` |
| 授權 | MIT（見 `LICENSE`）。我們自己的程式碼，`TARGET_PACKAGES.csv` 不涵蓋（那是 buildroot 套件） |

**體積預算**（同樣留待日後）：rootfs 是固定 128 MiB，裝進 git 之後剩 **47.4 MiB**。
swift_tar 是 668 KB，`csv2` 應在同一量級。若超過 5 MiB 就該回頭檢查是不是靜態連結了
不需要的東西。

### host 端建置

以 `swiftc` 直接建置，比照 swift_tar 的做法（純 `.swift` 原始檔、Foundation + Dispatch、
無 SwiftPM）。這一段從第一天就要能用，否則每次測試都得開一台 VM。

**即使暫不進 guest，程式碼仍不應綁死 macOS。** 不使用 Darwin-only 的 API，讓日後要交叉
編譯時不必回頭重寫——這個成本現在幾乎是零，日後才發現則不是。

## 測試

### 兩個平台都要測

**同一批案例必須在 macOS 與 aarch64 Linux 上都跑過。** 這與「暫不進 rootfs」不衝突：
**能在 Linux 上測試**與**隨 rootfs 出貨**是兩件事。測試時把執行檔放進 workspace 映像
（`buildroot-vm-workspace.ext4`，與那 128 MiB 的 rootfs 是不同的映像）即可，不佔 rootfs
的空間預算。

**為什麼不能只測 macOS。** Linux 上的 Foundation 是
swift-corelibs-foundation，**另一份實作**，不是同一份程式碼跨平台編譯。因此「在 mac 上
會過」對 Linux 的行為不構成證據。具體會咬人的地方：

| 差異 | 會壞在哪 |
|---|---|
| Foundation 是兩份實作 | `String`／`Data`／`FileHandle` 的邊界行為、`String.Encoding` 的處理 |
| 頁面大小 4 KiB（guest）對 16 KiB（Apple Silicon） | mmap／分塊讀取的邊界，只在某一邊對齊時才踩到 |
| `activeProcessorCount` 不同 | 分塊數不同，平行路徑走的是不同的切法 |
| 時區 UTC（guest）對 +08:00（host） | `-log` 的時間戳與其位移 |
| locale 與大小寫摺疊 | `-contains` 的比對 |

這些沒有一項會在編譯時被抓到，全部要到執行才會出現——而其中幾項（分塊邊界）只在特定
的檔案大小上才會顯現，正是那種「大部分情況正確」的失敗。

**驗收條件是跨平台逐位元相同。** 同一份輸入、同一組旗標，在 mac 與 Linux 上產生的輸出
必須完全一致。這比「兩邊都通過」強：兩邊各自通過但輸出不同，代表其中一邊是錯的，
而分別跑的測試不會發現。

體例比照 `sos/linux_test/test_git_submodule.zsh`——**測行為，不測檔案存在**。因此測試
腳本不得寫入任何綁定 host 路徑的假設，一開始就要能在兩邊跑。
### 測試案例清單

每個案例都編了號（`T1`…`T56`），實作的測試腳本以同一組編號命名，於是計畫與測試之間
是一對一的對照，而不是靠讀者自己比對敘述。編號依階段分組，因此一個階段完成時，該組
應該全部打勾。

前兩項直接來自本 repo 踩過的坑。

#### 第 1 階段：解析與 round-trip

- [x] **T1 帶引號的內嵌逗號** —— 以 `TARGET_PACKAGES.csv` 本身為 fixture，斷言 round-trip
  後**每一欄位元相同**。這是最有價值的測試，因為它就是真實的失敗案例
- [x] **T2 欄位型別不被搬錯** —— 讀出再寫回，`built_utc` 欄不得出現非時間戳的值
- [x] **T3 欄位數不一致的列** —— 必須明確報錯，不得靜默補空
- [x] **T4 CRLF 與 LF 混用於同一檔案** —— 逐筆判斷而非整檔偵測；輸出全部為 LF
- [x] **T5 引號內的 `\r\n` 原樣保留** —— 與 T4 同時測試，兩者的規則相反且容易互相踩到
- [x] **T6 CR-only 檔案給出的是專屬訊息**，不是欄數不符
- [x] **T7 BOM** —— 剝除後以欄名定址仍正確，且輸出不含 BOM
- [x] **T8 非 UTF-8 位元組 round-trip** —— 不得被換成 U+FFFD
- [x] **T9 `-si`/`-so` 串流**（T9a–T9c）—— RSS 不隨輸入大小成長、低於輸入大小，且**不隨
  紀錄數成長**。第三項是 2026-08-19 補的，而它是唯一抓得到當時那個缺陷的一條

#### 第 2 階段：選取與定位

- [x] **T10 引號內含換行的紀錄**，`-contains` 的紀錄號正確
- [x] **T11 `-t` 的輸出可被讀回，且不加 `-t` 時拒絕寫入 `.csv2`** —— `-head 3 -t` 的輸出
  餵回 `csv2` 必須得到 3 筆資料與相同標頭；`-head 3 -o x.csv2`（無 `-t`）必須報錯而非
  產出一個會讓前兩筆被當成標頭的檔案

- [x] **T14 `-mid` 的邊界** —— `a>b` 與 `a<1` 明確失敗；`b` 超過總筆數輸出到檔尾而不報錯；

## 實作時定案的四件事

以下四點在實作時才浮現：計畫對每一項都有立場，但兩條立場在同一個地方相撞，或是
一條立場沒有把邊界說完。記在這裡，而不是留在程式碼裡——那樣下一個人會以為它是隨意
決定的。

### 一、`--json` 的紀錄總數移到最後一行

計畫的 metadata 範例是 `{"meta":{"headers":2,"fields":7,"records":21}}` 且置於首行。
**這兩件事無法同時成立**：要知道 `records` 就得先讀完整份輸入，而在讀完之前不輸出
任何東西，正是計畫列為硬需求的串流保證的反面。

決定：首行 metadata 保留 `format`、`headers`、`fields`（這三個在讀完標頭時就已知），
`records` 與 `matched` 放在**最後一行的第二個 metadata**。串流保證是硬需求，
metadata 的形狀不是，因此讓步的是後者。

### 二、缺少結尾換行：`.csv` 補、`.csv2` 報錯

計畫在兩處給了相反的指示：「撕裂的追加要能偵測，且不自動修復」說未以 LF 結尾即報錯；
「追加之前必須做的三件事」說未以換行結尾就必須先補一個 LF。

決定：**兩者各自對應它被寫下時所講的格式**。

| 格式 | 缺少結尾 LF 的意義 | 行為 |
|---|---|---|
| `.csv2` | 違反「一筆一行、以 LF 結尾」的不變式，是撕裂寫入的證據 | 報錯，`--truncate-partial` 才丟棄 |
| `.csv` | 沒有這個承諾，很多工具產生的檔案本來就沒有結尾換行 | 補上 LF，否則新紀錄會黏在最後一筆的尾巴上 |

自動補在 `.csv2` 上會遮蔽撕裂；在 `.csv` 上報錯則會對一個完全正常的檔案報錯。

### 三、`-A` / `-B` / `-C` 隱含 `--filter`

計畫定義 `-contains` 有兩種輸出（定位報告與 CSV 子集），也定義了上下文旗標，但沒有
說兩者相遇時是什麼。**上下文紀錄沒有命中的儲存格**，定位報告對它們無話可說。

決定：給了 `-A`/`-B`/`-C` 就切換到紀錄形狀的輸出，與 grep 相同。

### 四、整檔轉換隱含 `-t`

`-encrypt`／`-decrypt`／`-hash` 會改寫檔案的每一筆，產出的是一個完整檔案而非選取的
片段。`-t` 那條規則是為了阻止「片段被寫進承諾了完整檔案的位置」，在這裡沒有東西要擋。

決定：未搭配任何選取旗標的欄位轉換，一律寫出標頭。

## 第 5 階段實作時定案的三件事

### 五、索引 seek 只在「沒有內嵌換行」時啟用

索引存的是位元組偏移量，不是行號。若檔案有內嵌換行，紀錄號就不再等於行號，而從
格點恢復解析的程式無從得知前面有幾個物理行——於是 `--physical` 會回報一個「完整掃描
不會給出」的行號。

而驗收條件是**有無索引的輸出必須逐位元相同**，行號就是輸出的一部分。因此索引 seek
只在檔頭的 `no_embedded_newlines` 為真時啟用。這對 `.csv2` 永遠成立（那是它的不變式），
對本 repo 樹內每一份 `.csv` 也都成立（已實測）。

### 六、索引在「掃描本來就要發生」時才建立

計畫說「只在該次操作用得到隨機存取時建索引，以及寫入時順手建」。實作時發現這對
`-mid` 與 `-tail` 的答案不同：

| 操作 | 有索引 | 沒有索引 |
|---|---|---|
| `-mid a,b` | seek 到格點 | 掃描並在第 b 筆提前停止，**不建索引**——為此做一次全掃描會抵銷掉提前停止的全部意義 |
| `-tail N` | seek 到 `總筆數 - N + 1` | 本來就必須讀完整個檔案才知道結尾，**順手建索引**，不花額外成本 |
| 編輯（重寫全檔） | — | 邊寫邊記下偏移量，寫完 rename 之後才寫索引 |
| `-append` 快路徑 | O(1) 更新 | **不建立**，理由同 `-mid` |

`-append` 的索引必須在**寫入之前**載入。驗證比對的是當下的檔案，因此追加之後才載入
的索引永遠看起來是過期的、也就永遠無法更新——sidecar 會在第一次追加時靜默失效，
之後每次讀取都退回掃描。這是實作時才發現的，測試 T46 就是為它而寫。

### 七、平行化只套用在定位報告上

平行的區塊會先在記憶體裡組出各自的輸出片段，再依區塊順序寫出——順序正是「與單執行緒
逐位元相同」的來源。定位報告每個命中只有一行短文字，因此片段很小；而 `--filter`
輸出的是完整紀錄，最壞情況等於整個檔案的副本。

那是拿記憶體上界去換速度，而在一台只有 2–4 GiB 的機器上那是錯的交換。因此
`--filter`、`-A/-B/-C`、`-head/-tail/-mid` 與欄位轉換一律走單執行緒。

### 對測試 T9 的一項調整

計畫要求「以大於記憶體的輸入驗證 RSS 有上界」。回歸測試造不出那種輸入，也不需要：
真正要證明的性質是**記憶體不隨輸入變大而變大**。改以兩個相差一個數量級的輸入量測
峰值 RSS 並斷言其成長小於兩倍——同一個性質，幾秒鐘就跑完。

為此 `-debug` 新增一行 `metrics:`，回報讀取位元組數與峰值 RSS。少了它，T9、T12、T13
只能停在 SKIP：「它是以環狀緩衝寫的」不構成記憶體有上界的證據。

## 第 6 階段實作時定案的事，以及它抓到的兩個缺陷

第 6 階段的價值不是「多一個平台能跑」，而是它**在第一次執行時就抓到兩個 macOS 上
永遠不會顯現的缺陷**。兩個都不是打錯字，都是看起來完全正常的程式碼。

### 缺陷一：`getrusage` 的參數型別兩個平台不同

```swift
guard getrusage(RUSAGE_SELF, &usage) == 0 else { return 0 }
```

Darwin 宣告 `getrusage(Int32, ...)`，glibc 宣告 `getrusage(__rusage_who_t, ...)`，
而 `RUSAGE_SELF` 本身被匯入為 `__rusage_who`。同一行在 macOS 上編譯得過，在 Linux 上
是型別錯誤，**連編都編不過**。

計畫原本預測的是「`ru_maxrss` 在 Darwin 是 bytes、在 Linux 是 KB」——那個預測是對的，
但問題還更早一步。

### 缺陷二：`--in-place` 在 Linux 上什麼也沒做，卻回報成功

`ByteSink.close()` 原本用 `FileManager.replaceItemAt`。它在 Linux 的
swift-corelibs-foundation 中是**另一份實作**，結果是目的檔維持不變——`--in-place`
安靜地什麼也沒改，然後以 0 結束。

這正是本專案最怕的形狀：成功回報、檔案沒改。macOS 上沒有任何東西會發現它。

改用 POSIX `rename(2)`。那本來就是這份設計指定的原語（「寫暫存檔 → 成功後 rename」，
同一檔案系統內原子），而且兩個平台行為一致。`replaceItemAt` 做的事比 rename 多
（備份項目、屬性保留），而那些多出來的事正是兩份實作分歧的地方。

### 原始碼清單只能有一份

兩支建置腳本各自維護一份 `SOURCES` 清單，於是它們分岔了：`compile_csv2_linux.zsh`
漏了 `src/Parallel.swift`，Linux 建置以 `cannot find 'runParallelSearch' in scope`
失敗——那個訊息指出的是一個「符號」而非缺少的「檔案」，會把人導向錯的方向。

一開始寫的是「比對兩份清單並警告」的防護。警告只能回報分岔。改為
[`src/sources.list`](../src/sources.list) 一份清單、兩支腳本都讀它——**根本沒有東西
可以分岔**。

### 原始碼怎麼進到 guest

以 `debugfs` 在開機前把 payload 直接寫進 workspace ext4 image。另一條路——用
`mke2fs -d` 從 staging 目錄重建 image——會刪掉所有在 guest 內建置的執行檔並迫使完整
重建。寫入的對象是 `guestvm.zsh` 建立的「每次執行一份」APFS 複本，共用的那份不會被碰到。

**一個必須先做的步驟：先 `e2fsck -f -y`。** workspace image 帶著上次非乾淨關機留下的
髒 journal，而 guest 掛載時會重播它——那會把 debugfs 剛改的 metadata 復原回去。第一次
執行時 payload「寫入成功」、`debugfs` 回傳 0，而檔案在 guest 內根本不存在；主控台 log
裡的 `EXT4-fs (vdb): recovery complete` 就是原因。

並且：**`debugfs` 即使寫入沒生效也回傳 0**，因此寫完要回頭問檔案系統那個檔案在不在，
而不是相信它的結束碼。

### guest 內三個 SKIP 的原因

| 案例 | 為什麼在 guest 內略過 |
|---|---|
| T25 | 判準是 `iconv`，而 guest 的 busybox 沒有可用的版本。工具缺席不等於性質失敗 |
| T42 | `getconf _NPROCESSORS_ONLN` 在 busybox 上取不到，測試因此無法確認有多核可用 |
| T47 | 它本身就是由 host 端的 `run_csv2_test.zsh` 驅動的，在 guest 內自然略過 |

## 收尾時定案的三件事

這三項來自「拿程式碼對照計畫」而發現的缺口，不是來自 code review。

### 一、`--a1` 的形狀：附加在位址之後

計畫規定了 `--physical` 的 `12:6@L34`，卻沒有規定 A1 那一段長什麼樣。實作時選了在其後
附加 ` [F12]`，而那是一個**沒有任何東西可以對照的選擇**。

決定：**`record:field` 為基底，`--physical` 附加 `@L<行號>`，`--a1` 再附加 ` [<A1>]`。**

```
1:1@L2 [A2]	pkg_name	busybox
```

**A1 的「列」取物理行號，不是紀錄號。**（2026-08-18 更正。）試算表所稱的「列」就是
檔案裡的物理行，因此一列標頭的 CSV 其第 1 筆在實體第 2 行，任何試算表都會叫那一格
`A2`。原本用紀錄號會讓 csv2 對一個試算表叫 A3 的儲存格印出 `[A1]`，並對標頭印出
`[E0]`——而 A1 記法根本沒有第 0 列。這一項的測試原本斷言了錯的那個。

兩者都是「額外輸出」，預設都不啟用——A1 尤其不能作為預設，因為 CSV 未必有標頭、欄數也
未必一致，在那些檔案上它會變成謊言。

之所以先訂形狀才寫測試：針對一個沒有人選擇過的形狀寫測試，只會把一次偶然固化下來。

順帶補上一個從未被執行過的路徑：A1 在第 26 欄之後變成 `AA`、`AB`。`a1Column()` 一直
都有處理，但本 repo 最寬的素材只有 10 欄，所以那段程式碼從來沒有被跑過。

### 二、`-debug=trace`：先有值得記的東西，才有旗標

計畫定義了 `ERROR > WARN > INFO > DEBUG > TRACE` 五級，但 CLI 只實作到 DEBUG，TRACE
無法達到。

一開始的判斷是「先不要加」——因為當時沒有任何東西以 TRACE 記錄，先加旗標只會得到一個
什麼也不做的選項。因此順序是：**先找到第一件值得寫成 TRACE 的事，再一起加上。**

那件事是「為什麼第 N 筆不在我的輸出裡」——逐筆的選取決定。它的量會把 DEBUG 淹沒，
正好是 TRACE 存在的理由。

### 三、`--build-index`：索引不能只以副作用出現

原本索引只在兩種情況下出現：寫入路徑邊寫邊建，以及 `-tail` 因為本來就要讀完整個檔案
而順手建。**於是只用 `-mid` 讀大型 `.csv2` 的人永遠不會得到索引。**

那不是疏漏，是每個操作各自正確的結果：`-mid` 的設計就是提前停止，在那裡建索引會抵銷掉
提前停止的全部意義。但兩個正確的決定加起來，留下一個使用者無從要求索引的狀態——而
`--verify-index` 已經存在，「有旗標可以驗證、卻沒有旗標可以建立」讓缺口一目了然。

決定：新增 `--build-index`，並守住那條規則——**索引維持是最佳化，永遠不是必要條件**：

- 它不改變任何輸出（T51 對此斷言）
- 目錄不可寫時只警告、不失敗
- 與 `--no-index` 併用即為錯誤，因為那兩件事互相矛盾

## 定位報告的跳脫：由一個只讀 README 的 agent 發現

`-contains` 的報告是 TAB 分隔、每個命中的儲存格一行，而「值」是任意的 CSV 內容。
兩者相撞：值含有 TAB 或換行時，報告就破壞了自己承諾的格式。

實測：三個命中的儲存格產生**四**行，`cut -f1` 在該是位址的地方回傳一段散文，而
csv2 以 **0** 結束。

**那正是本專案的招牌失敗**——看似合理但錯誤的結果以成功回報——而且發生在兩個最不該
發生的地方：工具自己在 README 裡推薦的腳本介面，以及 `status_notes` 這種帶引號的散文，
也就是當初引發事故、催生這支工具的那個欄位型別。

決定：值與欄名都以 **`.csv2` 既有的反斜線慣例**跳脫，另加 `\t`（因為 TAB 是這個格式
自己的分隔符）。沿用既有慣例而非發明新的：看得懂檔案格式的人不必再學一套就能讀報告。

### 它為什麼逃過了當時的 88 項測試

因為每一個餵給報告的測試值，恰好都不含 TAB 也不含換行。素材是我挑的，斷言也是我寫的
——兩者一起漏掉同一件事。

抓到它的是一個**只讀 README、讀不到程式碼**的全新 agent。它照著 README 自己寫的
「`cut -f1`、`cut -f2`、`cut -f3`」去做，然後自己造了一份含 TAB 與換行的探測檔。
那是「測試由寫程式的人自己寫」這件事的系統性盲點，而換一個讀不到程式碼的對象，正是
繞過它的方法——與第 6 階段換一個平台抓到兩個缺陷是同一個道理。

## `-hash` 承諾了它做不到的事

計畫在「`-encrypt` / `-decrypt` / `-hash`」一節寫著 `-hash` 的用途是「遮蔽。把欄位換成
雜湊值，之後仍可比對『是否為同一個值』，**但取不回原文**」。

**最後那半句在低基數欄位上是假的。**

無金鑰的 SHA-256 是確定性的——那正是「相等的值仍然相等」的來源——而確定性也正是它
可被字典攻擊的原因。`license`、`status`、`category` 這種只有少數幾種可能值的欄位，
任何拿到雜湊後檔案的人，把一份詞表拿去雜湊就能把該欄讀回來。

一次盲測（見下）**僅憑雜湊後的輸出**、沒有原始檔、只用一份 SPDX 識別碼清單，就還原了
`TARGET_PACKAGES.csv` 中 21 個 license 裡的 3 個。

而計畫在同一節裡就寫著：「一個名字承諾了安全性、行為卻做不到的功能，是最糟的一類。」
那句話原本是在講「用 SHA-256 加密再解密」的荒謬；它同樣適用於當時的 `-hash`。

### 決定：`-keyfile` 讓它變成 HMAC-SHA256

不能同時擁有這三件事：**確定性**（相等的值相等）、**無秘密**、**抗字典攻擊**。任何
兩個都可以，三個不行。既然確定性正是選 `-hash` 而不選 `-encrypt` 的理由，能讓的只有
「無秘密」。

- `-hash COLS` —— 純 SHA-256，維持原樣。值空間夠大時（長的自由文字、不透明識別碼）
  這是合理的，而且不需要金鑰。
- `-hash COLS -keyfile K` —— HMAC-SHA256。仍是確定性的，但摘要取決於一份秘密。

**檔案要記錄用的是哪一種**：標頭標記為 `:hash` 或 `:hmac:<指紋>`。少了它，讀者分不出
「可被字典攻擊的欄位」與「受保護的欄位」——而那個分別正是這次修正的全部重點。

沒有讓「有 `-keyfile` 就自動變 HMAC」成為隱形的行為切換：標記讓它在檔案中可見，
`--json` 的 metadata 也會列出受保護的欄位。這份設計一直在避免的正是看不見的例外。

### `--json` 原本看不見這件事

CSV 標頭有 `license:hash`，但 `--json` 的鍵是乾淨的 `license`——標記被剝掉了。於是
JSON 的消費端分不出被遮蔽的欄位與一般欄位。

那直接抵觸了首行 metadata 存在的理由：計畫說它的用處是「下游可以據此斷言 `headers`
是否符合預期，而不是默默接受一個猜錯的解析」。現在 metadata 多一個 `protected` 鍵，
沒有受保護欄位時完全不出現。

## temp+rename 少了 fsync：兩個保證被當成同一個

計畫在「為什麼追加是安全的，而就地覆寫不是」一節寫著：**「這個專案的資料檔正是靠
temp+rename 的『要嘛全新、要嘛全舊』在支撐的。」**

那句話把兩個不同的保證混為一談，而 csv2 只實作了其中一個：

| 保證 | 單靠 rename(2) |
|---|---|
| **並行讀者**看到完整的舊檔或完整的新檔 | ✅ 成立——讀者持有的是舊 inode |
| **當機／斷電後**檔案要嘛全新、要嘛全舊 | ❌ 不成立 |

第二個需要在 rename 之前把暫存檔的資料 flush 下去。沒有它，rename 可能已經落地而資料
區塊還沒有——留下一個**存在、名字正確、內容是空的或被截斷的**檔案。而那第二個，正是
「資料檔靠它在支撐」那句話的意思。

**修正（2026-08-18）：** `ByteSink.close()` 在 rename 之前呼叫
`Platform.flushToDisk`。在 Darwin 上用的是 `F_FULLFSYNC` 而非 `fsync`——後者只把資料
推給磁碟，磁碟仍可能將它留在揮發性快取中；用比較弱的那個然後宣稱「已持久」，正是這份
設計一直在避免的半真陳述。

flush 失敗時**警告並繼續**，不使操作失敗：另一個選擇是丟棄呼叫端已經成功產生的資料。

代價已量：最小編輯 0.019 秒／次（含行程啟動與解析），也就是計畫要求的第三項數字。

## 索引宣告了一個沒有任何東西推導過的性質（2026-08-19）

第 36 回合的盲測讀者要求「讓重複搜尋變快，然後說服自己那個加速可信」。他做到了前半，
而後半讓他找到一件我們沒看見的事。驗證時發現的比他報告的更嚴重。

索引檔頭帶著 `no_embedded_newlines`。平行路徑用它來斷定「一行就是一筆」——那是整條快
路徑的前提。設定它的呼叫點有三個，其中兩個傳的是常數：一個直接寫 `spansLines: false`，
另一個寫 `rec.line != r.line || false`，而 `r` 是只改了 `number` 的 `rec`，那個比較
永遠不可能為真。**於是 `--build-index` 寫出的每一份索引，都宣稱自己有這個性質。**

後果不需要竄改、也不需要特殊檔案。一份引號內含散文的合法 CSV——`TARGET_PACKAGES.csv`
的 `status_notes` 就是，而那正是本專案存在的理由——只要某一格裡有一個換行：

```
--build-index    index built
--verify-index   index OK                                  rc=0
-contains        150001:2   （並宣稱 300001 筆）             rc=0
強制單執行緒      150000:2
python3 csv      record 150000，300000 筆
```

錯的紀錄號、rc=0，而文件指名用來排除這件事的那個工具說索引沒問題。

### `--verify-index` 為什麼漏掉它，而那個理由值得留著

它檢查格點偏移量與紀錄筆數。**在這個失敗下，那兩者都完好無損**——在引號欄位裡放一個
換行不會移動任何一筆的起始位元組，也不會改變筆數。變的只是檔頭裡那個沒有任何東西重新
推導過的宣稱，而它恰好就是快路徑真正取用的那一個。

「證明」證明了本來就對的兩件事，跳過了錯的那一件。這不是檢查做得不夠深，是檢查對錯了
對象——而那個差別，只有把「索引宣稱了什麼」逐條列出來才看得見。

### 逃生口也逃不掉

`--no-index` 的文件寫的是「絕不讀寫 `.index` sidecar」。它確實沒有寫，但平行資格檢查
仍然載入了一份，而且從來沒看過 `o.noIndex`。它不從索引取出任何東西來印或來寫——**它只
讓索引決定走哪一條路**，而那正是沒有東西抓到它的原因：那個旗標的作用，除了紀錄號之外
看不見。於是因為懷疑 sidecar 而伸手去拿 `--no-index` 的人，拿到的還是 sidecar 的答案。

### 修法定案的四件事

**一、「這一筆有沒有跨行」由一個函式回答。** 三個呼叫點各自回答，其中兩個答錯——而它們
答的是同一個問題。`recordSpansLines(_:format:)` 是那個唯一的答案。`.csv2` 恆為 false：
它跳脫換行、依建構方式就是一筆一行，那裡的值中出現真正的 LF 完全不代表檔案的排版。

**二、CR 與 LF 一樣算，那是刻意悲觀。** 引號內單獨的 CR 不會把以 LF 斷行的檔案切成兩行，
所以把它算成跨行是過度保守——但悲觀付出的是一條快路徑，樂觀付出的是一個錯的答案。

**三、`--verify-index` 只對危險的方向失敗。** 索引說檔案跨行而其實沒有，只是放棄一條快
路徑、答案不變。為那種情況以非零結束，等於叫人去重建一份本來就不會害到他的 sidecar。

**四、`INDEX_VERSION` 推進到 3。** 已經寫在磁碟上的那些 v2 sidecar 帶著錯誤的旗標，而
索引內部沒有任何檢查抓得到——它們的檢查碼是對的、戳記是對的、偏移量也是對的。**只有版本
抓得到。** 版本不符本來就處理得對：以 INFO 忽略，取而代之的掃描是正確的。

### 這一條也改了一個訊息

索引存在、但它記錄了「這個檔案有內嵌換行」時，原本仍回報「沒有能證明一筆一行的索引；
用 `--build-index` 建一個」。那是無效的建議——重建會得到完全相同的結論。兩種情況現在
分開：沒有索引才叫人去建，索引已經說了的則指名它說了什麼。單執行緒在那裡不是退而求其次，
它就是正確答案。

### 測試 fixture 的第一版是錯的，而反向對照抓到了

第一版把 needle 放進跨行的那一筆裡，**結果在未修正的建置上也通過**。原因是跨行的紀錄
自己仍然從一個行邊界開始，所以它自己的號碼在誤數中存活下來；被推移一格的是它「之後」的
每一筆。needle 因此必須放在跨行那一筆之後。

抓到這件事的不是測試通過，是「把 `src/` 還原成修正前再跑一次」。**一個新測試會通過，
不代表它抓得到那個缺陷**——那兩件事要分開驗證。修正前 7 條失敗、修正後 11 條全過，
兩個數字都是這條記錄的一部分。

## `csv2view`：SwiftUI 的可捲動檢視器，以及它向 csv2 要的三件事（2026-08-19）

需求是「範圍查詢，好讓 UI 能以一個環狀佇列呈現可見的那幾列」，而 UI 使用原生 SwiftUI。
**範圍查詢已經在了，而且已經是 seek 而非掃描**——缺的不是查詢，是三件讓查詢能被安全地
重複呼叫的東西。

### 先量測，再設計

| 量到的 | 值 |
|---|---|
| `-mid 150000,150003` on 19.5 MB，有索引 | `index hit: grid point 149761 at byte 9661962`，`read_bytes=65536` |
| 同一個查詢，檔案含引號內換行 | `read_bytes=9699328`——**沒有 index hit**，從頭掃到那裡 |
| 40 列視窗查詢 ×100，含行程啟動 | 0.558 s，即**每次 5.6 ms** |

第三個數字決定了整個架構：**5.6 ms 遠低於一格 16 ms**，因此「捲動一次、呼叫一次 csv2」
是可行的，不需要常駐的伺服器行程，也不需要在檢視器裡放第二份解析器。

第二個數字是這份設計裡唯一的效能缺口，見下方第四項。

### 一、它是獨立的 SwiftUI app，不是 csv2 的一個模式

**定案：`csv2view` 是一個原生 SwiftUI 應用程式，csv2 一個位元組都不為它改變輸出行為。**

被否決的是「在 csv2 加一個 `--tui` 或 `--gui`」。理由不是分層潔癖：本專案的規則是「正常
路徑上不得輸出任何訊息，本工具必須能放進管線」，而一個 UI 是那條規則的反面——它要畫面、
要事件迴圈、要在使用者面前佔住行程。把兩者放進同一個執行檔，等於讓那條規則變成「除非你
給了某個旗標」，而一條有例外的規則在幾個月後就不再是一條規則。

**這一項也決定了平台範圍：SwiftUI 是 Apple 平台的，因此 `csv2view` 只在 macOS 上。**
csv2 本身不受影響——它仍然是平台中立的，仍然在 aarch64 Linux guest 內建置與測試（T47）。
**檢視器不進 rootfs、不進 workspace 映像、不成為任何建置流程的相依**，這與 csv2 自己
「目前不進 rootfs」的決定是同一條理由。第 6 階段的跨平台承諾說的是 csv2，不是檢視器。

### 二、資料怎麼進到 SwiftUI：呼叫 CLI，不連結函式庫

csv2 是 Swift 寫的，SwiftUI app 也是 Swift，所以「把 `src/` 當成 library target 連進去」
在技術上完全可行，而且沒有行程啟動成本。**仍然定案為：以 `Process` 呼叫 `csv2` 執行檔。**

理由是「被測到的是哪一個表面」。**csv2 的契約是它的 CLI**——314 個測試測的全部是命令列
的行為、輸出的位元組、結束狀態與錯誤訊息。它的內部型別（`RecordParser`、`Record`、
`CSVIndex`）沒有任何一項是被當成 API 測試的，也從來沒有承諾過穩定。連結進去，等於讓檢視器
依賴一組「沒有測試釘住、可以隨時改」的介面，而本專案在第 36 回合剛剛付過的代價，正是
「一個沒有東西重新推導的內部宣稱」。

第二個理由：連結會讓 app 內嵌一份 csv2 的**複本**。使用者機器上安裝的 `csv2` 與 app 裡的
那一份會分岔，而檢視器顯示的內容與他在終端機下同一個查詢得到的內容不同時，沒有任何東西
會說出來——那正是本專案定義的那種失敗。呼叫執行檔則保證兩者是同一個。

第三個理由是量測給的：**5.6 ms 已經在預算內**，所以這裡沒有需要用正確性去換的東西。

**這個決定可以被量測推翻，但不能被偏好推翻。** 若日後某個互動形式真的把每格的查詢次數
推到讓 5.6 ms 變成瓶頸，屆時的答案也不是連結內部型別，而是先讓 csv2 有一個「被測試釘住的
library 表面」。那是另一份設計。

實作上的細節，記下來以免重新推導：`Process` 的呼叫必須離開 main actor（`@MainActor` 的
view model 以 `Task.detached` 或 async 包裝），輸出以 `--json` 讀取而非人類可讀格式
（JSON Lines 每筆一行，正好對應一列），錯誤路徑讀 stderr 並保留 **rc**——rc 是這支工具
表達「你的位址是錯的」的方式，吞掉它就等於把第三項的整個修正丟掉。

### 三、它需要的第一件事：便宜地知道總筆數

**現況：沒有任何查詢路徑會告訴你檔案有幾筆。** `--json` 的 meta 印的是
`{"meta":{"records":150003,...}}`，而那是「到目前為止讀了幾筆」，不是總數。索引裡明明
存著 `records`，`--build-index` 與 `--verify-index` 都會印出來，但那兩個是管理動作。

這在 SwiftUI 下不是「好有更好」而是**必要**：`List` / `LazyVStack` 要先知道有多少列才能
決定捲動範圍與捲軸比例。一個「邊捲邊發現還有多少」的模型會讓捲軸在使用者手裡改變長度。

**定案：新增 `-count`，一個明確的動詞。** 印一行到 stdout，有索引時 O(1)，沒有索引時
O(n)（並照既有規則順手建一個）。

**被否決的是「在 `--json` 的 meta 加一個 `total` 欄位」**，而否決的理由值得記下來：那個
欄位只有在索引存在時才知道，於是它會**時有時無**。一個有時候出現的欄位，正是本專案一路
在消滅的那種歧義——呼叫端讀不到它時，分不出「這個檔案是空的」與「這次沒有索引」。明確的
動詞沒有這個問題：`-count` 一定會回答，只是有時候比較慢。

### 四、它需要的第二件事：`-mid` 越過檔尾不得靜默回傳空的

**現況：`-mid 300005,300010` 在一個 300000 筆的檔案上輸出空的，rc=0。**

對捲動的 UI，這正好是繞回時會發生的那一次呼叫，而空輸出**與「這幾列真的是空的」無法
區分**。在 SwiftUI 裡那會顯示成幾列空白儲存格，看起來完全像資料。

這是已經被判過一次的問題：`-get` 越界是錯誤而不是空輸出，理由寫在 T70f–T70h 那一節——
「若兩者都給空輸出，呼叫端就分不出『這一格是空的』與『你的位址是錯的』」。

**定案：`a` 超過總筆數是錯誤，`b` 超過總筆數維持現狀（輸出到檔尾，不報錯）。**

兩者不同，而那個差別是刻意的：`-mid 299998,300010` 的意思是「從這裡到之後 12 筆」，
檔案在中途結束是一個合理的答案；`-mid 300005,300010` 的**起點**就不存在，沒有任何一種
讀法能讓它有答案。T14 已經定了 `a>b` 與 `a<1` 失敗、`b` 超出不失敗；`a` 超出從來沒有被
指定過，這裡把那個缺口補上。

### 五、它需要的第三件事：含內嵌換行的檔案也要能 seek

**現況：`.csv` 只要有一筆跨行，`-mid` 就完全放棄索引，從頭掃到起點。** 上表的
9,699,328 bytes 對 65,536 bytes 就是這件事——而**引號內含散文的 CSV 正是最想要檢視器的
那一種**（`TARGET_PACKAGES.csv` 的 `status_notes` 就是）。

拒絕的理由本身是對的，記在 `planIndex` 裡：索引存的是位元組偏移量而不是行號，跨行之後
紀錄號不再等於行號，恢復解析會讓 `--physical` 回報一個「完整掃描不會給出的行號」——而
有無索引的輸出必須逐位元相同。

**定案：每個格點同時存行號，索引版本推進到 4。** 那個限制的根源是「索引不知道行號」，
不是「跨行不能 seek」。存下來之後，恢復解析可以帶著正確的行號起跳，`--physical` 的輸出
就與完整掃描相同，限制自然消失。成本是每個格點多 8 bytes——以 stride 256 計，一個
300000 筆的檔案多 9.4 KiB。

**這一項排在最後，而且是唯一可以先不做的。** 沒有它，檢視器在跨行的檔案上仍然正確，只是
慢；有了它才是快的。先做前兩項就能有一個能用的檢視器，那是本計畫一貫的排序方式。

### 六、環狀佇列由前端繞回，csv2 不繞

**定案：csv2 沒有「繞回」的查詢形式。** `-mid 299998,300005` 不會給你 299998–300000
接著 1–5。要繞回的檢視器發兩次查詢，並自己把兩段接起來。

理由與 `-delete -col` 拒絕同名欄位是同一個：**繞回會創造一個資料裡不存在的相鄰關係。**
第 300000 筆與第 1 筆在檔案裡不相鄰，是「檢視器決定讓它們在畫面上相鄰」。那個決定屬於
檢視器，把它放進 csv2 會讓一個回報「300000, 1」的輸出看起來像是資料本身的順序。而
csv2 的整條規則是不發明資料。

前端要繞回很容易——它已經有 `-count` 給的總數了，那正是第三項存在的理由之一。

### 七、檔案在捲動途中被改寫

檢視器會在幾秒內對同一個檔案發出幾十次查詢，而那個檔案可能正在被別的東西寫。

**定案：檢視器每次查詢都獨立，不快取跨查詢的狀態；偵測改變的責任在檢視器，不在 csv2。**
csv2 的索引戳記（大小、mtime、首尾雜湊）已經會在資料檔改變時丟棄索引並退回掃描——那保護
的是「答案正確」，不是「兩次查詢看到同一個版本」。後者是檢視器要的。

第 36 回合已經證明那個 O(1) 戳記擋不住「大小與 mtime 都不變的原地改寫」。因此檢視器若
需要**保證**它顯示的是一致的一份，唯一誠實的做法是先複製一份再看，並把這件事說出來。
**不要在 csv2 裡加一個假裝能偵測的東西**，也不要在檢視器裡用 `NSFileCoordinator` 之類的
機制假裝那是同一個問題——它偵測的是「有沒有人寫」，不是「我剛才顯示的那一份還在不在」。

### 八、畫面本身：它顯示什麼，以及它拒絕做什麼

前七項是資料怎麼進來。這一項是使用者看到什麼——而這裡的每一個決定，都是為了讓畫面上的
東西**能被帶回命令列**。那是這個檢視器存在的理由：csv2 的定址能力目前只能靠人去讀
`12:6` 這種文字，而一個表格是人類找到那個位址最快的方式。

**一、每一列都顯示它的紀錄號，而且那個號碼可以複製。** 不是「第幾列畫面」而是 csv2 的
紀錄號——與 `-get r:c`、`-update r:c`、`-delete -cell r:c` 用的是同一套。選中一格時，
狀態列顯示 `12:6`，並提供「複製為 csv2 指令」。**檢視器不編輯任何東西；它產生你要打的
那一行。** 這一條同時決定了下一條。

**二、第一版是唯讀的，而那是決定不是進度。** 一個能改格子的 GUI 必須自己處理並行寫入、
復原、以及「畫面上的值與磁碟上的值不同」的那段時間——本專案已經記錄過那個「後寫者全贏、
且兩邊都回報成功」的並行缺口。唯讀的檢視器沒有那個問題，而且**它產生的 csv2 指令會走
`--in-place` 的 temp+rename**，那條路徑已經有測試撐著（T28）。把編輯做進 UI，等於在一個
沒有測試的地方重做一件已經做對的事。

**三、兩列標頭是表頭的兩行，不是被合併掉的一行。** `.csv2` 的英文列與中文列都顯示，
上下疊在同一個表頭儲存格裡。`-md` 用 `<br>` 合併它們是因為 Markdown 只有一列表頭——那是
輸出格式的限制，不是資料的形狀。SwiftUI 沒有這個限制，所以不要繼承那個妥協。單列標頭的
`.csv` 就只顯示一行，**不要為了對齊而發明一列空的中文標題**。

**四、欄寬用 csv2 已經有的那張表，不要用 `String.count`。** `--pretty` 的 UAX #11 寬度
表是為了「`套件名稱` 是 12 bytes、4 個 code point、4 個 grapheme cluster、而顯示寬度是
8」這件事存在的（T48）。SwiftUI 會自己量測文字，所以初始欄寬用那張表估、之後交給
SwiftUI——但**排序與截斷的界線仍以 grapheme cluster 為準**，理由與 T25 相同：截在中間會
產生不是合法 UTF-8 的東西。

**五、被加密的欄顯示為密文，並標出它是密文。** 標頭上的 `:enc` 後綴是檔案自己的宣告，
檢視器照著顯示，**不提供「在 UI 裡解密」**。解密需要金鑰，而把金鑰路徑放進一個 GUI 的
設定裡，等於把「金鑰不經過命令列、不出現在 `ps`」那條規則繞過去。要看明文的人跑
`csv2 -decrypt` 產生一份，再開那一份——那一步是刻意的摩擦。

**六、非 UTF-8 的位元組照樣顯示，不換成 U+FFFD。** csv2 以位元組為單位處理，正是為了
不做這個替換（T8）。檢視器必須有一個「這一格不是合法 UTF-8」的呈現方式（例如以
`<0xFF>` 之類的形式逐位元組顯示），而不是讓 `String(decoding:as:)` 靜靜地把它變成問號。
**那是這棵樹上最典型的那種靜默替代**，不要在最後一哩把它加回來。

**七、錯誤是可見的一列，不是空白。** 任何查詢的非零 rc 都在畫面上呈現 csv2 的 stderr
第一行原文。第四項把「起點越界」變成錯誤，就是為了讓這裡有東西可以顯示；把它吞掉會讓
整個修正白做。

**八、鍵盤操作優先於滑鼠。** 上下鍵移動一列、PageUp/PageDown 移動一頁、`g`／`G` 到頭尾、
`/` 開搜尋（背後是 `-contains`，跳到它回報的位址）。理由是這支工具的使用者本來就在
終端機裡；一個非得用滑鼠的檢視器會讓人退回 `less`。

**這一節裡沒有任何一項需要 csv2 改變。** 第三到第五項要的資訊，`--json` 的 meta 與標頭
已經全部提供了。

## 串流的記憶體宣稱是假的，而斷言它的測試什麼都沒在測（2026-08-19）

第 37 回合的盲測讀者量了 `-si`／`-so`，並回報 peak RSS 是整條串流的 1.02 倍。**他是對的，
而這份測試套件已經斷言相反的事好幾個月。**

### 兩個缺陷，形狀不同

重現後拆出來的是兩件事，而且只有一件在「比大小」時看得見。

**一、輸入端：每一塊讀進來的 `Data` 都沒有被釋放。** `ByteSource.next()` 以 64 KiB 為單位
呼叫 `FileHandle.readData`，而整個讀取迴圈裡沒有任何 `autoreleasepool`。那些 Foundation
物件一路累積到行程結束，於是 RSS 正比於「讀了多少位元組」。修法是把 `next()` 的本體包進
一個 pool。

**二、輸出端：一行永遠不會被輸出的 TRACE，每一筆都被完整建構。** `emitRecord` 無條件組出
`"select: record N line L emitted…"`，然後交給 `Logger.log(.trace, …)`；而 `log` 自己**也是
先**組出時間戳與整行、**之後才**判斷層級。預設門檻是 WARN，所以在一次普通的執行裡，那兩次
字串建構每一筆都發生、而且一個字都不會被印出來。

第二項是靠一個特定的量測認出來的：**同樣的位元組量、二十分之一的紀錄數**。

| 輸入 | 紀錄數 | peak RSS |
|---|---|---|
| 79.6 MB | 2,000,002 | 123 MB |
| 90.3 MB | 100,002 | 15.9 MB |

位元組幾乎相同而 RSS 差八倍——被留住的東西是「每一筆」一份，不是每個位元組。單看大小的
比較永遠分不出這件事。

修正後，79 MB／90 MB／181 MB 三種輸入、10 萬到 400 萬筆紀錄，peak RSS 全部停在 9.5 MB。

### 為什麼 T9 通過了

T9 的斷言是 `r_big < r_small * 2`，fixture 是 77 KB 與 3.3 MB。**行程與 Foundation 的地板
就有 9 MB**，因此一個「保留每一個位元組」的實作，在 3.3 MB 的輸入上是 17.7 MB——仍然小於
9.4 MB 的兩倍。**它通過的餘裕是 6%。**

那不是一個寬鬆的門檻，是一個**被地板淹沒的量測**。當基準值遠大於變數時，任何比例式的斷言
都在測那個基準值。

這與第 36 回合那個 fixture 錯誤是同一課的兩面：**一個測試會通過，不代表它在測那件事。**
差別在於那一次是新測試（反向對照抓到了），這一次是一個存在已久的測試——而沒有任何東西會
定期去問「這個測試現在還抓得到它當初要抓的東西嗎」。

### 加強後的 T9

- **T9a**（原本的）保留，不改。它測的是「不隨輸入大小成長」，那條仍然值得測。
- **T9b**：15.5 MB 的串流上，peak RSS 必須**低於輸入大小**。那是「不整檔緩衝」最弱、但仍然
  算數的形式，而一旦輸入遠大於地板，光靠地板滿足不了它。修正前量到 48 MB，失敗。
- **T9c**：同樣的位元組、二十分之一的紀錄數，兩者的 RSS 必須相當。**這一條指名真正的缺陷**，
  也是唯一一條在「比大小」時看不見的。修正前是 48 MB 對 26 MB，失敗。

反向對照：把 `src/` 還原成修正前，T9b 與 T9c 失敗、T9a 照樣通過。**T9a 在壞掉的建置上通過，
正是它原本的問題。**

## 每一條寫入捷徑都跳過了慢路徑的驗證，並回報成功（2026-08-19）

第 37 回合驗證出三條缺陷，記在 `todo/known-defects.md` 為 W、X、Y。修它們的時候發現，
三條是同一句話的三種說法：**每一條抄了近路的寫入路徑，都略過了完整路徑會做的檢查，
然後以 rc=0 回報成功。** 這正是 README「Why this exists」所描述的那起事故，在一支為了
防止它而寫的工具內部重現。

### W：遮蔽保護了一個根本不該被寫下去的值，並因此掩蓋了損害

對標頭為 `secret:enc:<指紋>:<salt>` 的檔案下 `-update 1:secret NEW`，會以 rc=0 被接受。
明文寫了進去，而 `-decrypt` 接著停在那一格——**於是第 2、3 筆也一起讀不回來**，儘管它們的
密文完好、且那次編輯從未碰過它們。

而稽核紀錄寫的是：

```
INFO  update 1:secret: <redacted> -> <redacted>
```

**遮蔽在此變成掩蓋。** 遮蔽的規則（第 25 回合定的）是「依檔案的宣告」，而這裡檔案宣告該欄
是加密的——所以被寫進去的那個**明文**，正因為它落在「秘密該在的地方」而被藏了起來。
日後讀這行 log 的人，看到的是一次正常的加密欄位更新。

**這道保護在一個不該存在的操作上運作得完美無缺，而它是那次損害唯一的紀錄。**

#### 第一版的修正是不完整的，而發現它的是「換一個動詞再試一次」

第一版只涵蓋 `-update` 與 `-delete -cell`。**`-append` 直接走過去**，造成一模一樣的破壞：

```
csv2 -append 'zstd,1.5.7,PLAINTEXT' -i pae.csv --in-place    # rc=0
csv2 -decrypt all -keyfile k.bin -i pae.csv                   # record 3: not a valid encrypted cell
```

會寫入原始值的動詞有四個，四個都必須關上。而 `-append --in-place` 還需要**第二處**守衛：
它走的是 `runAppendFast`，根本不經過 `runEdit`——放在 `runEdit` 裡的檢查對它毫無作用，
而那正是最可能被用在一個大型受保護檔案上的路徑。

**定案：**

**一、單格與整列分成兩個不同的拒絕，訊息不同。** `-update`／`-delete -cell` 是「你瞄準了
那一欄」；`-insert`／`-append` 是「你沒有瞄準它，但那一列剛好有它的一欄」——而後者**沒有
任何呼叫者給得出的值會是對的**，因為轉換需要金鑰，而標頭裡只有指紋。

**二、加密與雜湊的訊息不同，出路也不同。** 加密欄位失去的是整欄；雜湊欄位不失去任何東西，
卻多了一個「永遠沒有東西能發現」的明文。而對雜湊欄位說「先解開再改」是**做不到的事**——
雜湊是單向的。叫人把雜湊倒回去，比什麼都不說更糟：他會去找那個做得到這件事的旗標。

**三、「同一次執行裡轉換並編輯」仍然允許。** `-encrypt secret -update 1:secret NEW` 是
說得通的——被加密的就是那個新值——因此檢查是對「輸入的」標頭做的，而不是對加上標記之後的。
由 T90k–T90l 釘住：解回來必須是 `NEW`。

### X 與 Y：追加快路徑對 `.csv` 什麼都沒驗證

```
printf 'pkg,ver,note\nbusybox,1.37.0,core\nzlib,1.3' > b.csv   # 結尾少一欄、無換行
csv2 -append 'zstd,1.5.7,compression' -i b.csv --in-place      # rc=0
csv2 -r -t -i b.csv                                            # record 2 has 2 fields... rc=1
```

**同一份輸入，換成 `-o` 就被正確拒絕。** 同一個動詞、同一份資料、相反的結果，而兩者的差別
在 README 裡只是一個 O(1) 的括號註記。`runAppendFast` 只在格式是 `.csv2` 時呼叫
`checkTornAppend`；`.csv` 缺少結尾換行被當成「只是不整齊」，而一筆欄數不足的結尾紀錄
根本沒有被檢查。

Y 是同一個原因的另一種後果：檔案結束在未閉合的引號裡時，追加的那一筆會被**吸進那個欄位
內部**——它不是一筆紀錄，於是一次回報成功的寫入其實沒有發生。

**定案：檔案未以換行結尾時，追加之前先完整解析一次。**

那是唯一「結尾可能只寫了一半」的狀態，因此正常結尾的檔案（幾乎全部）仍然是 O(1)——
由 T91h 斷言，而它斷言的方式是「那行說明 O(n) 的 debug 訊息**不出現**」。

**更便宜的檢查考慮過，而且不成立。** 讀回一段有界的視窗、解析最後一個換行之後的部分，
分不出「半筆」與「一筆含內嵌換行的完整紀錄」——兩者看起來都是碎片，而答案取決於該紀錄
開頭處的引號狀態，那只有從檔案前面解析才知道。在唯一可能出錯的那個情況上付 O(n)，
好過安靜地弄錯。

### 修這件事時，我自己造出了同一類缺陷的一個新案例

第一版讓 `validateBeforeAppend` 接受 `--truncate-partial`。結果是：解析器把不完整的紀錄
從**解析**中丟掉、驗證通過、追加照常進行——而那筆不完整的紀錄**仍留在檔案裡**，後面接著
一筆完整的，rc=0，下一次讀取就壞掉。

**追加只會加上位元組，它移除不了任何東西。** 因此 `-append` 一律嚴格驗證，並在使用者確實
給了 `--truncate-partial` 時，明說它無法被履行，並指出走得通的那條路（先以
`-r -t --truncate-partial -o` 寫出乾淨複本）。由 T91i–T91m 釘住——**包括那條「走得通的路」
本身必須真的走得通**，否則那個訊息比沉默更糟。

### 一個被推翻的決定：T73d

**T73 曾經斷言「該次編輯會成功」，而現在它被拒絕。** 依本計畫的規則，被推翻的決定要寫回來。

第 25 回合的結論——遮蔽依據「檔案的宣告」而非「本次執行在做什麼」——**仍然正確，仍然被斷言**。
被推翻的是它旁邊那一條：「遮蔽針對的是 log，不是拒絕該次編輯」。

而那從來不是任何人做過的決定。看那行測試的註解就知道它的來歷：它是一道防線，**防止 T73a
因為「寫入失敗」而空洞地通過**。它記錄的是「當時的行為」，不是「當時的判斷」。

第 37 回合顯示那次寫入實際上做了什麼，於是這兩者不再相容。防止空洞通過的那道防線移到一般
欄位上——在那裡寫入仍然必須發生、也仍然必須被記錄（T73d–T73e）。

**這件事值得單獨記下來的理由**：一個為了「讓別的斷言不會空洞通過」而寫的輔助斷言，會在
無人察覺的情況下，把「當時碰巧是這樣」固化成「這就是規格」。它與那個真正的決定寫在同一個
測試裡、同樣的格式、同樣的份量——而只有註解說得出兩者的差別。

## 稽核軌跡不得丟資料，而「不丟」的代價是另一個缺陷（2026-08-19）

第 38 回合發現 README 承諾「一般欄位的新舊值**完整記錄**；那正是稽核軌跡的意義」，而 log
在**第 40 個字元**把新舊值都切斷。`TARGET_PACKAGES.csv` 的 `status_notes`——這個專案存在的
理由就是那一欄被改壞——在真實素材裡長達 878 bytes，因此**恰恰對那一欄，log 保留不下任何
可用的舊值**。

使用者的裁決是「不應截斷」，而在動手之前先問「移除它會付出什麼代價」——**那個問題翻出了
該回合沒有找到、而且必須先修的另一個缺陷。**

### 先跳脫，再解除上限——順序不能反

`Logger.redact()` 把值加上引號後直接寫進 log，**完全沒有跳脫**，而 log 是一行一筆的格式。
於是值裡的一個換行就會開啟新的一行，**而那一行的全部內容由值決定**：

```
…INFO  update 1:note: "harmless" -> "x"
2020-01-01T00:00:00+00:00 INFO  nothi…[+11 more chars]"     ← 偽造，時間戳由值挑選
…INFO  wrote 1 records, 2 fields, atomic rename OK
```

**那 40 字元的截斷沒有擋住這件事，它只是把偽造的那一行剪短。** 兩者的關係決定了修法的順序：
**若只移除上限而不先跳脫，偽造會從「一眼看得出被截斷」升級成「完整且可信」。**

跳脫用的是既有的 `reportEscape()`——它處理 `\`、TAB、`\n`、`\r` 四個字元，正好是「讓一筆
紀錄留在一行內」所需的全部。這一步同時修掉了一個盲測沒有找到的缺陷。

### 定案的三件事

**一、無界，不設上限。** 一個會安靜丟掉資料的上限，正是這一整條要修的東西。真實資料撐得住：
`TARGET_PACKAGES.csv` 共 147 格、最長 878 bytes、全部加起來 10 KB。

**二、超過 1 MiB 發 WARN，但仍完整寫出。** 那不是拒絕，也不是上限，而是「有人該當場知道
自己的稽核軌跡剛剛長了一 MB」——而不是事後在磁碟用量圖上發現。訊息同時說明「log 仍會完整
保留它」，否則那個警告會被讀成拒絕。

**三、只有「舊值」到得了那個門檻。** 那麼大的新值傳不進來——`ARG_MAX` 會先拒絕整條命令列
（實測 1.1 MB 的參數即 `argument list too long`）。這一點寫進測試的註解，否則下一個人會為
一條「碰不到的路徑」寫測試。

### 範圍是收斂的，而確認這件事花的力氣是值得的

`echoValue()` 只有兩個呼叫點：log（原本 `limit: 40`、無跳脫）與**定位報告**（`limit: 200`，
而且**本來就有跳脫**）。報告有它自己的上限與自己的理由——**報告是報告，不是稽核軌跡**——
因此它不動，並由 T92n 釘住「它仍然依自己的上限截斷」。

若沒有先查這件事，很容易把 `echoValue` 的預設值改掉了事，而那會連帶把定位報告變成無界的。

### 調查途中撞到的另外兩條

**JJ**（上述的 log 偽造）與 **II**（`-update` 把命令列上的非 UTF-8 位元組靜默換成 U+FFFD）
都不是盲測 agent 找到的，而是「改之前先問代價」問出來的。兩條都已依規則記入
`todo/known-defects.md`。**II 尚未修**——它需要一個決定（保留原始位元組，或偵測到無效 UTF-8
就拒絕），而它今天做的是第三種：安靜地改掉。

第 38 回合另有 CC、DD、EE、FF、GG、HH 六條已驗證而尚未修，同樣記在該檔案。

## 錯誤訊息裡的號碼是一個位址，而它解不出來（2026-08-19）

第 38 回合，缺陷 CC。儲存格層級的錯誤印的是 `recordsEmitted + 1`，而那個計數**含標頭列**。
在 `.csv2` 上偏移恰好是二：

```
csv2: record 4, field 2: undefined escape sequence \q     ← 壞掉的是資料第 2 筆
csv2 -get 4:2 -i f.csv2   →  no such record; the file has 2 records
csv2 -get 2:2 -i f.csv2   →  那一格
```

同一支工具的**紀錄層級**錯誤本來就是對的（`record 1 (line 3)`，兩個數字都給），因此錯誤通道
裡並存兩套差了標頭列數的編號——而 README 自己的範例示範的正是壞掉的那一套，儘管它同時寫著
「`N` 自始至終數的是紀錄，不是行」。

**要緊的不是「號碼不一致」，是那個號碼的用途。** 這支工具用來取代查詢語言的東西，就是
「位址可以組合」：`-contains` 找到位址、`-get`／`-update` 用它。**錯誤訊息裡的號碼也是一個
會被人打回去的位址**，而一個解不出來的位址比沒有更糟——它會把讀者送到另一格，或送到一個
「讀起來像是檔案有問題」的拒絕，而檔案其實沒問題。

### 定案的兩件事

**一、與紀錄層級錯誤同一個形狀：`record N (line L), field M`。** 資料紀錄號給呼叫端用，
物理行號給文字編輯器用。兩個都給，因為兩個都有人要。

**二、標頭列給 `0a` / `0b`，不給紀錄號。** 標頭列沒有紀錄號，發明一個會產生「解得出來、
但解到錯的東西」的位址。`0a`／`0b` 是定位報告本來就在用的名字（見上方 `--include-headers`
那一節），因此不是新發明的詞彙。修正前那裡印的是字面的 `record header`。

### 又一個把缺陷釘成規格的測試

**T60a 斷言的是 `record 3, field 2`**——那個 3 是物理行號。它在「儲存格錯誤要同時指出紀錄與
欄位」上是對的，錯的是那個號碼的意思；而它以「釘住印出來的字串」的方式，把缺陷凍結成了規格。

這是同一個 session 內第二次遇到（前一次是 T73d）。**共同的形狀是：一條斷言為了驗證 A，
順手把當時的 B 也一起釘住了，而 B 從來沒有人決定過。** 分辨的方法只有一個——去讀那條斷言的
註解，看它說的是「我們決定這樣」還是「當時就是這樣」。

## 四個節點：它裝在哪裡，以及「同一個版本」不等於「同一個檔案」（2026-08-20）

multissh 的節點升級（`helper/upgrade_nodes_csv2.zsh`）會在每個節點上 clone、建置、執行
`install.zsh`，再確認 csv2 可達。第一次對 Windows 跑，它回報 `reachable: csv2 0.1.0`
——**而那是另一個執行檔**。

| 依設計每次重建 | **我把兩台 guest 搞混了**——`run_csv2_test.zsh` 開的是 `workspace.ext4` 的 per-run 複本，與這個常駐節點是不同的機器 |
| `GIT_SSH_COMMAND` 用不上 | 用得上。git 接受 multissh 當傳輸，一路走到選金鑰才停 |

**推論之所以危險，不是因為它會錯，是因為它讀起來與量測一模一樣。** 上面那張表寫成事實的
語氣，而它的來源只是「我想它應該是這樣」。這與本專案一路在修的那些缺陷是同一個形狀——
一個回答不了問題的東西，看起來與能回答的東西沒有分別。

### 那個節點為什麼不 pull，而是收 bundle

實測到底之後，擋住 `git pull` 的東西是可以一層層說清楚的：

```
git 接受 multissh 當 SSH 傳輸        ✅  GIT_SSH_COMMAND 有效
multissh 金鑰                        ✅  /workspace/multissh/multissh_keys/generated/
埠號                                 ⚠️  multissh 預設 16888，GitHub 要 22
KEX 協商                             ❌  no common key exchange algorithm
```

最後那一條是設計使然：multissh 預設用後量子的 `mlkem768x25519-sha256`，GitHub 不支援；
而它**只有在「PQ identity 不可用、且 `~/.ssh/id_ed25519` 存在」時**才切換到 stock OpenSSH
profile。也就是說，要讓 guest 從 GitHub pull，就得在裡面放一把 GitHub 認得的私鑰。

**而那正是 `linux_kernal_vm_interactive/README.md` 記載的設計所要避免的**：「prebuilt 的
存在意義就是建置可以離線完成；在此走網路等於悄悄把 token 與可用連線變成建置的前提」。

**定案：以 git bundle 經 multissh 更新。** 從 Mac 的工作樹產生 bundle、經「此刻已經在用的
那條連線」送進 guest、`git fetch` 該 bundle 再 fast-forward。

**它一樣走網路**——那條連線就是網路。差別不在「有沒有網路」，而在**依賴的形狀**：它不新增
對外相依、不需要憑證、也不在映像裡留下秘密。（初稿把它寫成「不走網路」，那是第四個錯誤。）

### Windows 的位置是「shim 指著的那個」，不是我們挑的

那台機器上的慣例是 scoop 的：執行檔在 `%LOCALAPPDATA%\csv2`，`~/scoop/shims` 裡的 shim
指向它，而 `scoop/shims` 在 PATH 上。**裝到 shim 本來就指著的位置**，shell 就會解析到新的
建置，而 `install.zsh` 完全不必往 scoop 自己的目錄裡寫東西——**建立 shim 是 scoop 的事，
不是我們的**。這也是為什麼 `install.zsh` 只加了一個目標位置，沒有去碰 `.shim` 檔。

### 真正的教訓：版本字串證明不了身分

`install.zsh` 早就想到「shell 跑到的可能是別的 csv2」，而且有一條專門的檢查——但它比對的是
**版本字串**。兩個都是 `csv2 0.1.0`，於是那條檢查通過了，而跑的是另一個檔案。

**這是 T69 那些過期數字的鏡像。** 那裡的問題是「數字會過期」；這裡的問題是「數字**永遠不變**」
——而那正是它分不出東西的原因。同一個形狀的兩種失敗：**一個回答不了它被拿來回答的問題的東西，
看起來與一個能回答的東西一模一樣。**

驗證改用雜湊之後才說得清楚：三個節點上「PATH 解析到的檔案」與「剛建好的執行檔」sha256 相同。
記為 NN，尚未修——修法是讓那條檢查比對身分而不是版本。

`install.zsh` 本身沒有說謊：它印了警告，並說「已安裝，但**未以名稱驗證**」。說得過頭的是
外圍那支升級腳本，而它屬於 multissh。

## 盲測的污染是結構性的，而這次量到了（2026-08-20）

第 39 回合我自己派出 agent，並在 prompt 最前面要求它先回答一件事：**在執行任何指令之前，
它的 context 裡有沒有那張已經被刪除的缺陷表。**

它逐字引用了那張表，兩個檔案都引到。而磁碟上：

```

/Volumes/LinuxCS/CLAUDE.md          缺陷表 0 筆匹配
```

**因此那條規則不再是推論。** subagent 收到的是**母 session 啟動時**的指令檔快照，不是磁碟上
的內容。從一個已經在跑的 session 派出的盲測，會被餵進那個 session 啟動當下的所有東西——
**包括之後才被刪掉的**。

而 agent 自己指出了最要命的地方：**它沒完成的那一項任務（金鑰指紋不符），正是那張表最會
污染的一項**——表上有一列就是關於 `-encrypt` 丟失 `:enc` marker 的。它拒絕在那個狀態下給出
結論，那是對的。

**這一段之所以值得留著，是因為它示範了「怎麼測一件關於測試本身的事」**：把「你看到了什麼」
做成受測者必須先回答的第一個問題，而那個答案在兩個方向上都有用——看得見表，規則成立；
看不見，規則該刪。

## 一個永遠不變的數字，證明不了兩個檔案是同一個（2026-08-20）

同一天出現三次，三個不同的地方，同一個形狀：

| 哪裡 | 用什麼判定 | 為什麼判不出來 |
|---|---|---|
| `install.zsh` 安裝後的驗證（NN） | `csv2 --version` | 兩個建置都說 `csv2 0.1.0` |
| multissh 的節點升級腳本 | `csv2 --version` | 同上；它在 Windows 上回報成功，而 shell 跑的是一年前的執行檔 |
| `:enc:` 指紋當「這是不是我的金鑰」（TT） | 標頭裡的指紋 | 它含 salt，同一把金鑰每次執行都不同 |

前兩者的毛病是「數字永遠不變」，第三者是「數字每次都變」——**而兩種毛病造成的是同一件事：
一個回答不了那個問題的東西，被拿來回答了那個問題。**

這與 T69 那些過期的 PASS 數量是同一族。那裡的數字會衰減，這裡的數字不會——但**「不會變」並不
使它成為身分**，正如「會變」並不使它成為錯誤。要問的一直是同一句：**這個值能不能區分我要
區分的那兩個東西？**

### 三處的修法

**NN**：`install.zsh` 改為比對檔案。遇到 shim 是「跟著它走」而不是對它算雜湊——shim 自己的
位元組不是那支程式的，對它算雜湊會比到錯的東西、並以錯的理由失敗。實測：一個「回報相同版本
的不同檔案」，新檢查會 die，**舊的版本檢查會放行**。

**TT**：程式不動，改文件。程式碼給了答案——`fingerprint()` 取的是**推導後金鑰**的雜湊，
而 `-hash` 以固定 salt 推導、`-encrypt` 每次抽新 salt 並存進標記。**那個指紋一直都在正確地
識別「推導後的金鑰」**，而加密的推導後金鑰依設計就是每個檔案一把——那正是解密能重新推導的
原因。錯的是那句用同一個說法涵蓋兩種指紋的描述。

**UU**：`-decrypt` 成功時記下它用了哪一把金鑰。指紋在那條路徑上本來就算好了（不算就無法拒絕
錯的金鑰），所以這件事除了「注意到」之外沒有任何困難——而稽核軌跡原本記下了每一次上鎖、
沒有記下任何一次開鎖。

| CSV → Markdown (`-md --pretty`) | works |
| Markdown → edit → write back | **cannot be read at all** |

That asymmetry is the whole feature. A Markdown table is the shape a person
hands you — pasted out of a document, a wiki, a pull request — and csv2 can
render one and then cannot take it back.

**What must be decided before any code:**

1. **What declares it.** A `.md` suffix is the obvious answer and it is not
   enough: most `.md` files are prose that HAPPENS to contain a table, or
   several tables, or none. Options: refuse an `.md` with anything but one
   table; take the first table and say so; require `--headers` to disambiguate
   as `-si` does. The rule this tree already holds is that a file whose shape
   cannot be determined is refused, loudly, naming the record — not guessed at.
2. **How many header rows.** `-md` renders a `.csv2`'s two header rows joined
   with `<br>`. Reading that back means splitting on `<br>` — and a cell whose
   VALUE contains a literal `<br>` is then indistinguishable from a joined
   header. The write side already escapes `|` and newlines; whatever it does
   with `<br>` decides whether this round-trips, and it must be decided on the
   WRITE side first.
3. **The separator row.** `-md` output already trips csv2's own reader with a
   named refusal ("record 2 (line 2) is a Markdown separator row"). That
   refusal becomes the detection: the thing that made reading fail is the thing
   that says what the file is.
4. **Alignment colons.** `|:---|---:|` carries alignment. It is presentation,
   not data, and reading it back discards it. Say so rather than let someone
   discover a `-md` round-trip is lossy.
5. **`--pretty` padding.** Rendered cells are space-padded to a column width.
   Reading back must strip that padding — and then a value that genuinely
   begins or ends with a space cannot survive a Markdown round-trip at all.
   That is a real loss and belongs in the docs beside the feature, not in a
   defect log later.

**The test that decides it is done:** a `.csv2` rendered with `-md -t`, read
back, and written out again is byte-identical to the original — for a fixture
that contains a quoted comma, an embedded newline, a `|`, a `<br>`, and a value
with leading and trailing spaces. If any of those cannot survive, the
documentation says which BEFORE the feature ships.

**在寫任何程式碼之前必須定案的事：**

1. **是什麼宣告了它。** `.md` 副檔名是顯而易見的答案，而它不夠：大多數 `.md` 是散文，裡面「剛好」
   有一張表、或好幾張、或一張都沒有。選項：只有一張表時才接受、取第一張並說出來、或像 `-si` 那樣
   要求 `--headers` 來消除歧義。這棵樹已經在守的規則是：形狀判斷不出來的檔案要「大聲拒絕並指名
   紀錄」，不是用猜的。
2. **幾列標頭。** `-md` 會把 `.csv2` 的兩列標頭用 `<br>` 接起來算繪。讀回來就意味著要對 `<br>`
   做切分——而一個「值」裡本來就含有字面 `<br>` 的儲存格，屆時與一個「被接起來的標頭」無法區分。
   寫出去那一側已經跳脫了 `|` 與換行；它對 `<br>` 怎麼處理，決定了這件事能不能 round-trip，
   而那必須**先**在寫出去那一側定案。
3. **分隔列。** `-md` 的輸出本來就會撞上 csv2 自己的讀取器，並得到一句具名的拒絕（「第 2 筆
   （第 2 行）是一列 Markdown 分隔列」）。那句拒絕正好成為偵測：讓讀取失敗的那個東西，就是說出
   「這個檔案是什麼」的那個東西。
4. **對齊用的冒號。** `|:---|---:|` 帶著對齊資訊。那是呈現、不是資料，讀回來會把它丟掉。要說出來，
   而不是讓人自己撞到「`-md` 的 round-trip 是有損的」。
5. **`--pretty` 的補白。** 算繪出來的儲存格會被空白補到欄寬。讀回來必須把那些補白去掉——而一個
   「本來就以空白開頭或結尾」的值，屆時在 Markdown 的 round-trip 裡根本活不下來。那是真的損失，
   它該寫在這個功能旁邊的文件裡，而不是日後出現在缺陷紀錄裡。

**判定完成的那個測試：** 一個 `.csv2` 以 `-md -t` 算繪、讀回來、再寫出去，與原檔逐位元相同——
而那個 fixture 要含有一個引號逗號、一個內嵌換行、一個 `|`、一個 `<br>`，以及一個前後都有空白的值。
其中任何一項活不下來，文件要在這個功能出貨**之前**說出是哪一項。

- [ ] decide 1-5 above, in the plan, before writing code / 上面 1–5 在計畫裡定案，然後才寫程式
- [ ] `-md` write side settles `<br>` and padding / `-md` 寫出去那一側把 `<br>` 與補白定案
- [ ] read a Markdown table as records / 把一張 Markdown 表讀成紀錄
- [ ] round-trip test with the hostile fixture / 用那個「刁難的」fixture 做 round-trip 測試
- [ ] the losses named in both READMEs / 那些損失在兩份 README 裡被指名

### 8b. No suffix means one column / 8b. 沒有副檔名就是一欄

Requested in the same breath: **a file with no suffix is treated as a
one-column `.csv2`.** A plain list of lines — package names, paths, a `find`
dump — is a table with one column, and today csv2 refuses it because nothing
declares a format.

同一次提出的：**沒有副檔名的檔案，視為一欄的 `.csv2`。** 一份純粹的行清單——套件名、路徑、一次
`find` 的輸出——就是一張只有一欄的表，而今天 csv2 會拒絕它，因為沒有東西宣告格式。

This is a smaller change than 8a and a sharper one, because it changes what a
REFUSAL means. `Format.from(path:)` returns nil for a suffix-less path today,
and several messages name the rule — the gzip refusal ends "the new name has to
keep a `.csv` or `.csv2` suffix, because the suffix is what declares the
format". That sentence stops being true.

這個改動比 8a 小，但更尖銳，因為它改變了一句**拒絕**的意思。`Format.from(path:)` 今天對沒有副檔名
的路徑回傳 nil，而好幾則訊息說著那條規則——gzip 那句拒絕的結尾是「新的名字必須保留 `.csv` 或
`.csv2` 副檔名，因為副檔名才是宣告格式的東西」。那句話會不再為真。

**Decisions this needs, and they are not obvious:**

1. **Does a suffix-less file have header rows at all?** `.csv2` means two.
   A `find` dump has none — its first line is data. Treating line 1 and line 2
   as titles would silently eat two records from every such file, and that is
   exactly the class of failure this tool exists to refuse. The likely answer
   is that it behaves as a `.csv2` in ESCAPING and one-record-per-line, and
   takes `--headers 0` semantics that do not exist yet.
2. **Then `--headers 0` has to exist**, and every message that says
   `--headers 1 or --headers 2` has to learn a third value.
3. **What does `-o` write?** If the input had no suffix and the output has
   none either, the same rule applies and it round-trips. If `-o` names a
   `.csv`, one column becomes one column and nothing is lost. The interesting
   case is a `.csv2` input written to a suffix-less output with more than one
   column: refuse, rather than drop columns.
4. **Escaping.** A one-column `.csv2` still cannot hold a raw newline, so a
   line containing `\n` in the file is one record with an escaped newline —
   which means a plain text file whose lines contain literal backslashes
   changes meaning when read this way. That has to be measured on a real
   `find` dump before it is called a feature.
5. **What is still refused.** A directory, a device, a gzip, a UTF-16 file.
   None of those becomes readable because the suffix went away; the suffix-less
   rule must not become a way to bypass the refusals that are about CONTENT.

**這需要的決定，而且它們都不顯然：**

1. **沒有副檔名的檔案到底有沒有標頭列？** `.csv2` 的意思是兩列。一次 `find` 的輸出一列都沒有
   ——它的第一行就是資料。把第 1、2 行當成標題，會從每一個這種檔案裡安靜地吃掉兩筆紀錄，而那正是
   這個工具存在所要拒絕的那一類失敗。可能的答案是：它在**跳脫**與**一筆一行**上表現得像 `.csv2`，
   而採用一套「目前還不存在」的 `--headers 0` 語意。
2. **那麼 `--headers 0` 就必須存在**，而每一則說著「`--headers 1` 或 `--headers 2`」的訊息，都得
   學會第三個值。
3. **`-o` 寫出去的是什麼？** 如果輸入沒有副檔名、輸出也沒有，同一條規則適用，它就 round-trip 得起來。
   若 `-o` 指的是一個 `.csv`，一欄還是一欄，什麼也沒少。有意思的是：一個「多於一欄」的 `.csv2` 輸入
   要寫到一個沒有副檔名的輸出——那應該**拒絕**，而不是把欄位丟掉。
4. **跳脫。** 一欄的 `.csv2` 仍然不能含有原始換行，因此檔案裡一行含有 `\n` 的內容，會是「一筆帶著
   跳脫換行的紀錄」——這表示一個「行裡含有字面反斜線」的純文字檔，用這種方式讀會**改變意思**。
   那件事必須在一次真實的 `find` 輸出上量過，才能叫做功能。
5. **有哪些仍然被拒絕。** 目錄、裝置、gzip、UTF-16 檔案。它們不會因為副檔名消失就變得可讀；
   「沒有副檔名」這條規則不得成為繞過那些「關於內容」的拒絕的一條路。

- [ ] decide 1-5 above / 上面 1–5 定案
- [ ] `--headers 0`, and every message that names the valid values / `--headers 0`，以及每一則指名合法值的訊息
- [ ] suffix-less input reads as one column / 沒有副檔名的輸入讀成一欄
- [ ] the content refusals still fire / 那些「關於內容」的拒絕仍然會觸發
- [ ] measured on a real `find` dump with backslashes in it / 在一次「裡面有反斜線」的真實 `find` 輸出上量過
- [ ] the sentence "the suffix is what declares the format" corrected everywhere it appears / 「副檔名才是宣告格式的東西」那句話在每一處都更正

### Why these two are one phase / 為什麼這兩件是同一個階段

Both are the same question asked twice: **what may csv2 read, and what says
so?** Today the answer is a closed set of two suffixes, and every refusal
message repeats it. Adding either one alone would leave that sentence half
true, which is worse than either state — this tree has recorded that exact
shape more than once (a rule applied to only part of where it holds).

兩者是同一個問題被問了兩次：**csv2 可以讀什麼，而什麼東西說了算？** 今天的答案是一組封閉的、兩個
副檔名的集合，而每一則拒絕訊息都在複述它。單獨加入其中任何一個，都會讓那句話變成「一半為真」，
而那比任何一種完整狀態都糟——這棵樹記錄過不只一次同樣的形狀（一條規則只套用到它成立範圍的一部分）。

## 同名欄位：為什麼 `-delete -col` 也拒絕（2026-08-18）

盲測第 29 回合提了一個好問題，而它不是缺陷回報：**`-delete -col note` 在有兩個 `note` 的
檔案上，其實有一個沒有歧義的讀法——「把每一個叫 note 的欄位都移除」。** `-update`／`-hash`
必須「挑一個存活者」，因此非拒絕不可；但刪除不必。那為什麼也拒絕？

**因為有歧義的不是「結果」，是呼叫者的「認知」。**

會打出 `-delete -col note` 的人，幾乎必然相信那裡只有一個 `note`。刪掉兩個，會給他一個
「在結果上沒有歧義」的產物，**卻讓那個錯誤的認知原封不動地留著**——而他接下來寫的每一行
指令，都建立在那個認知上。拒絕是唯一會去更正它的回應。

換句話說：`-delete -col note` 刪掉兩欄，在「這一道指令」的尺度上是對的，在「這個人接下來
要做的事」的尺度上是錯的。而本專案一貫的判準是後者——那正是「一支腳本改錯了東西並回報成功」
之所以是一起事故、而不只是一次不便的原因。

**出路存在且不折衷**：訊息會指出是「第 1、3 欄」，而以欄號定址兩者都到得了——
`-delete -col 1 -delete -col 3` 兩欄都刪、`-delete -col 3` 只刪一欄。使用者拿回了完整的
表達力，只是必須先看見那個檔案真實的樣子。由 T75l–T75m 斷言。

## `-get r:c`：由一位只讀 README 的讀者提出（2026-08-18）

**問題是讀者發現的，不是我們。** 第 14 回合的任務是「取出一個已知位址的儲存格」，它照著
README 自己建議的兩條路走，然後指出一件我們沒看見的事：

> `record:field` 被 README 當成「讓尋找與編輯能組合」的核心賣點，但它只與**寫入**組合
> （`-update`、`-delete -cell`）。要把一個已知位址的值讀回來，沒有對稱的指令。

而最強的理由是那個我們自己想不到的：**位址可能來自外部。** 有人從 bug 回報裡把 `12:6`
打進來，或是上一次執行留下的。`-contains` 完全無法服務那個情境——它只能找「你已經知道
在裡面」的值。一支工具若只能找到你已經知道的東西，就不能算是有定址能力。

證據就在這棵樹裡：本專案自己的測試套件為了取出一格，得用**兩次 csv2 呼叫加一個暫存檔**
實作 `cell()`（先 `-delete -col` 投影掉其餘每一欄，再 `-mid`）。那個輔助函式的存在本身
就是缺口的證明。加了 `-get` 之後，它塌縮成一行。

### 定案的五件事

**一、名稱是 `-get`，由讀者提議。** 與 `-update r:c VAL` 對稱，而 `-r` 已被讀取動詞佔用。

**二、輸出是原始值，不是 CSV。** 只有一格的 CSV 列，在值含逗號時仍得加引號，於是呼叫端
又得回頭解碼——那正是第 14 回合抱怨的那條彎路。`$(csv2 -get …)` 就應該是那個值。

**三、越界是錯誤，不是空輸出。** 空輸出正是「一個確實存在的空儲存格」的樣子。若兩者都給
空輸出，呼叫端就分不出「這一格是空的」與「你的位址是錯的」——而那正是本專案要消滅的那種
歧義。T70f–T70h 兩邊都斷言。

**四、標頭儲存格不可定址。** 定位報告稱它們為 `0a`／`0b`，但沒有任何動詞能作用其上，
`-update` 也不行。`-get 0a:3` 的拒絕訊息說的是「那是標頭儲存格」，而不是「需要 r:c」
——位址的**格式**是對的，只是它指的東西不能被動作。

**五、實作就是 `-mid r,r` 換一個輸出器。** 同樣的 seek、同樣的停止點、同樣使用索引。
另外寫一份，只會讓它多出一個屬於自己的差一錯誤。

## `-delete -col` 實作時定案的四件事（2026-08-18）

**一、修飾詞屬於一個動詞，而不是屬於整行指令。** 這是實作時抓到的一個既有缺陷：
`o.cellModifier` 一旦設起來就不會清除，於是 `-delete -col b -delete 1` 中的第二個
`-delete` 繼承了 `-col`，移除了「第 1 欄」而那筆紀錄還在——在兩個方向上都錯，且 rc=0。
`-cell` 有同樣的缺陷，只是被 `r:c` 的形狀檢查擋住（純紀錄號會被拒），而 `-col` 接受
任何欄位標記，因此沒有東西攔得住。修法是每個動詞取用後即清除修飾詞；T57l–T57o 以
「兩種順序」斷言，因為一個只在「帶修飾詞的動詞排前面」時才成立的修正不算修正。

**二、所有欄位索引都對「輸入」解析，一次套用。** 與 `-delete 3 -delete 4` 同一個道理：
逐一移除會讓第二個索引指向第一次移除之後的那一列。

**三、對正被移除之欄位的編輯是拒絕，不是排序。** `-delete -col notes -update 1:notes X`
不會有任何效果，卻會在日誌裡回報「該格已更新」——本專案的招牌失敗。與其替它定一個
「先更新再移除」或「先移除再報錯」的順序，不如直接拒絕。

**四、不與 `-insert`／`-append` 併用。** 那一列字面值必須符合某個形狀——是輸入的，
還是少一欄的輸出的？兩種讀法都說得通，因此無論選哪一個，對寫下這行的人裡有一半而言
都會是靜默的錯。分成兩道指令，各自只有一個形狀。
