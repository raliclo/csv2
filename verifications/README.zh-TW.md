# verifications

- **English: [README.md](README.md)**

這裡放的是「量測」，不是「測試」。沒有任何東西會通過或失敗；它印出數字並寫在自己旁邊，
讓日後的執行能與先前的比較。通過／失敗的測試在
[`../test/test_csv2.zsh`](../test/test_csv2.zsh)。

```zsh
./measure.zsh                    # 結果寫入 measure_output.txt
RECORDS=20000 ./measure.zsh      # 較小的語料，供較慢的機器使用
CSV2=/path/to/csv2 ./measure.zsh
```

| 檔案 | 從哪裡來 |
|---|---|
| `measure_output.txt` | host——直接執行本腳本 |
| `measure_output_linux.txt` | aarch64 guest——由 `sos/test_submodules/run_csv2_test.zsh` 在 VM 內執行同一支腳本並將輸出擷取回來 |

旋鈕是 `RECORDS` 而不是 MB：語料是一列一列產生的，能被真正控制的是筆數。以大小為單位
只能是估計值，並會與腳本印出的實際位元組數不一致。

## 為什麼有這個目錄

`plan/plan.md` 有一節叫「寫程式之前應該先量的」，列出三個數字，並以這句話結尾：
*本專案有過「開機時間結論錯誤、事後要更正並修一輪文件」的紀錄。這幾項要在寫程式之前量，
不是事後。*

它們是在第 1–6 階段全部完成「之後」才量的。這個目錄就是在還那筆債，而結果值得直說：

| | 計畫的假設 | 實測 | |
|---|---|---|---|
| 完整 RFC 4180 解析 | 2900 MiB/s（`memchr`），預期「慢一個數量級」 | **45 MiB/s** | **慢 64 倍**，不是 10 倍 |
| 平行解析 | 未預測 | **124 MiB/s、2.76×**（10 個 worker） | 遠非線性 |
| 重寫整檔 | 39 MiB/s | **38 MiB/s** | 準確 |
| 1 GiB 改一格 | 26 秒 | **26.9 秒** | 準確 |
| 最小的落地編輯 | 未量 | **0.019 秒** | — |

**寫入端的預測是對的，讀取端差了 64 倍。** 計畫自己那句警告——真正的解析器會慢
「一個數量級」——方向正確，幅度低估了六倍。

## 門檻變得更站得住腳，但理由換了

16 MiB 的索引與平行門檻，是對著 2900 MiB/s 挑的。在那個速率下掃描 16 MiB 只要
0.0055 秒，為此維護一個 sidecar 很難說得過去。在實測的 45 MiB/s 下是 0.355 秒，
那個門檻就合理了。

**答案是對的，推理是虛的。** 那正是計畫那段警告要防的事：一個從錯誤數字推出的正確
結論，情境一變就不再正確。現在它下面有實測撐著了。

## guest 的數字，以及其中兩個為何是反的

`sos/test_submodules/run_csv2_test.zsh` 會在 aarch64 guest 內跑同一支腳本，並將輸出
擷取到 `measure_output_linux.txt`。與相同筆數的 macOS 執行相比：

| | macOS（2 萬筆） | guest（2 萬筆） | |
|---|---|---|---|
| 完整解析 | 41 MiB/s | **37 MiB/s** | 只慢一成 |
| 重寫整檔 | 28 MiB/s | **33 MiB/s** | guest 較快 |
| 最小落地編輯 | 0.0192 s | **0.0045 s** | guest 快 4 倍 |
| 平行（強制開啟） | 2.7× | **0.94×**——比單執行緒還慢 | |

解析只慢一成，是因為 guest 跑在 `-accel hvf` 下：Apple Silicon 上的 aarch64 是硬體
虛擬化，不是指令模擬。

**那兩個寫入數字不是它們看起來的意思。** guest 顯得比較快，是因為它做的事比較少。
QEMU 的 `-drive` 沒有指定 `cache=`，預設為 `writeback`；guest 的 flush 到達 host 之後
是 `fsync(2)`，而在 macOS 上 `fsync` **不會**強制磁碟清空自己的揮發性快取——那需要
`F_FULLFSYNC`，也正是 csv2 在 Darwin 上直接呼叫的東西。所以 0.0192 秒與 0.0045 秒量的
是不同的事件：一個是資料抵達碟片，另一個是資料離開 guest。**guest 的持久性數字受限於
host 的 QEMU 設定，與 Linux 本身無關。**

**平行在 guest 上是淨損失（0.94×）**——而那正是門檻在發揮作用。2.6 MB 的語料遠低於
16 MiB，量測是用 `CSV2_PARALLEL_MIN_BYTES=1000` 強制開啟的；在預設門檻下它根本不會
啟動。因此門檻在這裡擋掉的，正是一次會讓事情變慢的平行化。這是實測第二次支持這個門檻，
而且是從它「說不」的那一側。

## 誠實地讀這些數字

- 它們是 **N 次取最快**，不是平均：最快的那一次受其他負載污染最少。比較時要比同一種。
- **只能與相同 `RECORDS` 的執行相比。** 在 20000 筆時整份語料只有 2.6 MB，行程啟動與
  flush 這兩項固定成本佔了總時間的一大部分，因此 MiB/s 會低估穩態速率。同一個執行檔在
  20000 筆時量到 28 MiB/s，在 200000 筆時是 39 MiB/s。腳本在低於 100000 筆時會自己
  印出這個警告。
- 語料刻意使用「含逗號的引號欄位」——拿 `a,b,c` 去量解析器，量到的是它不必費力的那個案例。
- 解析吞吐量是用「不可能命中的 `-contains`」量的，所以數字是解析器而不是寫出端。
  改用 `-r` 計時會量到「解析＋編碼＋寫出」，得到一個沒有人在做的事情的數字。
- 平行那一行的工作者數量取自 csv2 自己的 `-debug`，而非 `getconf _NPROCESSORS_ONLN`。
  busybox 沒有 `getconf`，在 guest 上那個呼叫會失敗，退回值會安靜地宣稱「單核」——把
  一次量測變成一個長得像數字的猜測。
- 平行效率依構造就遠低於 100%：找紀錄邊界的那一遍是單執行緒的。印出這個數字，是為了
  不讓人把「平行」讀成「快 P 倍」。
