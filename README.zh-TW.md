# csv2

以 Swift 撰寫的命令列 CSV 解析器與編輯器，目標為
[LinuxCS](https://github.com/raliclo/LinuxCS) 專案的 aarch64 Linux guest，
以及建置它的 macOS host。

English: [README.md](./README.md)

## 狀態

**第 1–6 階段已實作並通過測試；第 7 階段（出貨）是刻意暫緩。**

```zsh
./compile_csv2.zsh       # 建置 release/csv2
./test/test_csv2.zsh    # 0 失敗。在 macOS 上唯一的 SKIP 是 T47——它比對的是兩個
                        # 平台，因此由母專案執行。其他平台會多幾個，每一個都會印出
                        # 理由；那個數量由測試自己檢查。
```

| 可用 | 尚未做 |
|---|---|
| RFC 4180 解析、引號、內嵌逗號與換行、CRLF、BOM | 隨 rootfs 出貨（第 7 階段） |
| `-r`、`-contains`、`-A`/`-B`/`-C`、`-head`/`-tail`/`-mid`、`-rownum` | |
| `.csv2` 兩列標頭、`--json`、`-md`、`--pretty`（顯示寬度） | |
| `-insert`/`-append`/`-delete`/`-update`、`-delete -cell`、`-delete -col` | |
| `-hash`、`-encrypt`、`-decrypt`、`-keyfile`、`-debug`、`-log` | |
| `-append` 快路徑——寫入的位元組數是 O(1)，讀取的位元組數是 O(n) | |
| `.csv.index` / `.csv2.index` sidecar、`--verify-index` | |
| 平行搜尋，且與單執行緒逐位元相同 | |
| 可在 aarch64 Linux 上建置執行，且與 macOS 逐位元相同 | |
| 可在 x86_64 Linux（WSL2）與 Windows（MSVC）上建置並通過測試 | |

**以及它「完全不做」的那些**——因為一張十一勝、外加一項「部署待辦」的表，讀起來會像是一個
只剩一件事沒做的工具。下面每一項在本文後面都有描述；這是讀者應該最先看到的那份清單：

| 不提供 | 改用什麼 |
|---|---|
| 欄位投影（`-cols`） | `--json` 加 `jq`，或逐格 `-get` |
| 不分大小寫的比對 | `--json` 加你自己的一次處理——見 `-contains` 那一節的說明 |
| 不讀檔就計數（`-count`） | `--json` 結尾那行 meta 的 `records` |
| 在 `.csv` 與 `.csv2` 之間轉換 | 刻意拒絕；請把紀錄寫出去，再讀回來 |
| 安全的並行寫入 | 請自己把寫入者排成序列；兩個寫入者會靜默地弄丟其中一次編輯。兩個並行的 `-append --in-place` 是例外：兩筆紀錄都會完整落地，而「後完成的那一個」會警告自己無法更新索引 |
| 以程式分辨不同的拒絕 | 每一種都只有結束狀態 1 與一段英文散文 |

`install.zsh` 會把執行檔放到「該平台的 shell 真的會去找」的地方：有 Homebrew 時是
`$(brew --prefix)/bin`，使用者層級的後援是 `~/.local/bin`，而 Windows 上是
`%LOCALAPPDATA%\csv2\csv2.exe`——也就是 scoop 的 shim 本來就指著的位置，因此 shell 會解析到
新的建置，而這支腳本不必往 scoop 自己的目錄裡寫東西。**要確認你拿到的是哪一個 csv2，
請比對檔案而不是版本**：兩個建置都說自己是 `csv2 0.1.0`，`csv2 --version` 分不出來。

若那個目錄不在 PATH 上，`install.zsh` 會把它加上去——寫進「**這個帳號的**登入 shell 會讀」
的那個檔案，而那不一定是執行安裝程式的那個 shell。zsh 寫的是 `~/.zshenv` 而不是 `~/.zshrc`，
因為經 ssh 執行的腳本不是互動的，只讀得到前者；bash 寫的是 `~/.bashrc`，外加一個會去
source 它的登入檔。該區塊以 `# >>> csv2 install.zsh >>>` 標記界定，裝兩次不會多出第二個，
而 `--uninstall` 會把它們全部收回。`--no-rc` 則完全不做這件事，只把那一行印出來給你自己加。

接著它會說出「哪幾種 shell 找得到這個執行檔」——每一種（包含經 ssh 的腳本）、只有登入 shell、
或只有互動終端機。這個問題是問一個「從零開始建立的環境」所啟動的 shell，因此答案不會來自
「執行安裝程式的那個東西」的 PATH。

進度以核取方塊記在 [plan/plan.md](./plan/plan.md) 文末，且**只有在
[test/test_csv2.zsh](./test/test_csv2.zsh) 中對應的案例通過時才打勾**。
工具尚未能滿足的案例會回報為 SKIP 並附原因，不會安靜地略過。

**已設計但尚未實作：`csv2view`，一個原生 SwiftUI 檢視器。** 底下沒有任何一段在描述它，
因為它還不存在——設計寫在 [plan/plan.md](./plan/plan.md)，並指名 csv2 必須先補上的兩件事：
一個 `-count` 動詞；以及在索引裡存行號，使含引號換行的檔案仍然能 seek。**第二件已於
2026-08-21 完成**——索引 v4 在每個格點旁存了行號，因此一個「有紀錄跨行」的 `.csv`，現在
seek 得與 `.csv2` 完全一樣（T157）。
（第三項「`-mid` 的起點越過檔尾時要報錯而不是回傳空的」原本也在這張清單上，
2026-08-20 之後不在了：它已經是一則指名兩個數字的 WARN，見上面的 `-mid`。）在 19.5 MB 的檔案上，一次 40 列的視窗查詢實測 5.6 ms，
那正是檢視器會「呼叫這個執行檔」而不是「內嵌一份它的解析器」的理由。**那個數字需要一份
sidecar，而 `-mid` 永遠不會建立它**——請先跑 `--build-index`，否則你量到的會是 277 ms，
並據此認定那個數字是編的；而那正是「完全照著這份文件做」的讀者會得到的結果。它背後的檔案是
45 萬筆、每筆約 40 bytes；形狀是有影響的，同樣大小但每筆是長文的檔案，量出來是另一回事。
**不要照著上面任何一項寫腳本；那是計畫，不是介面。**

目前**不**隨 LinuxCS 的 guest rootfs 出貨——需要它的腳本都在 macOS host 上執行。
但測試在 **macOS 與 aarch64 Linux 兩個平台**上都做，且要求兩邊輸出逐位元相同：
Linux 上的 Foundation 是另一份實作，「在 macOS 上會過」對 Linux 不構成證據。那就是
案例 T47，由母專案的 `test_submodules/run_csv2_test.zsh` 驅動——它在 guest 內建置
csv2，並逐一以 sha256 比對十二組呼叫。

## 為什麼要做

不是因為世界上缺少 CSV 工具，而是因為**這個專案已經被天真的逗號切割咬過**，而且是
同一天兩次。

`TARGET_PACKAGES.csv` 的 `status_notes` 欄含有帶引號、內有逗號的敘述文字。一支用
`${line%,*}` 切欄位的腳本改寫了那些註記的中段。它以 0 結束，並印出它改了哪些東西；
那份清單裡的「舊值」是半句話。檔案是從 git 還原的。

同一天，`artifacts.csv` 把一個 commit 字串寫進了 `built_utc` 這個時間戳欄位，
沒有任何東西報錯。

這兩次都不是因為 CSV 難懂，而是因為**手邊沒有工具**，於是每個人都改用 `cut -d,` 和
`${line%,*}`。csv2 的目的，是讓「正確處理 CSV」比「隨手切逗號」更方便。

因此第一個需求不是效能，也不是功能數量：

> RFC 4180 的引號、內嵌逗號、內嵌換行、CRLF、BOM 必須全部正確處理；
> 其餘情況一律大聲失敗，而不是安靜地產生一個半對的檔案。

輸出的紀錄分隔符在任何平台上一律為 `\n`，且不偵測作業系統——否則「macOS 與 Linux 輸出
逐位元相同」這項要求無法成立。輸入則接受同一檔案中混用 LF 與 CRLF，以逐筆判斷而非整檔
偵測。引號內的位元組一個都不動，因此「只用 LF」指的是紀錄分隔符，不是檔案裡的每一個
位元組。

**csv2 讀到而沒有更動的欄位，會照它到達時的原樣寫回去，連引號一起。** 而它**有**更動的
欄位會重新序列化，此時套用 csv2 自己的規則：值裡含逗號、引號、CR 或 LF 時加引號；值的
開頭或結尾是空白或 tab 時，也加引號。後面那一條 RFC 4180 並不要求，它存在的理由是：那些
空白是資料，而且是那種會安靜消失的資料——試算表與好幾種解析器會把未加引號欄位前後的空白
去掉。因此對一個存著 `"   "` 的儲存格做 `-update`，寫回去的仍然是 `"   "`；而你給的、
結尾帶空白的值，落地時會被加上引號——透過 `-update` 是這樣，透過 `-insert` 與 `-append`
也是，那兩個寫出去的是「你打進來的一列」，不是它們讀到的一列。到 2026-08-25 之前，那兩個
會保留那一列的字面位元組，於是 `-append 'r2, leading'` 寫出的 ` leading` 沒有引號，而
`-update 1:2 ' leading'` 對同一個值加了引號：csv2 自己兩種都讀得回來，而這條規則所為之存在
的那些試算表不行。

**這條規則有一件事不做：它不會替試算表擋下一條公式。** 一個以 `=`、`+`、`-`、`@` 開頭的值，
對 Excel、LibreOffice 與 Sheets 而言就是一條公式，而 csv2 把它當成它本來的樣子——文字——存下來：
`=1+1` 會照你打的樣子、不加引號地落地，因為「為了討好下游的讀者而竄改一個值」正是這個工具唯一
不會做的事。如果你的輸出會被試算表打開、而它的值來自你控制不了的地方，那件事得由你來處理。

由此可推得：一次編輯之後，沒被動到的欄位逐位元相同，被動到的那些帶的是 csv2 的引號規則，
而不是上一個寫入者當初的選擇。一個「每一欄都加引號」的檔案，在你編輯過的那些格子上不會
維持那個樣子。由 T133 斷言。

## 兩種格式，由副檔名宣告

| 副檔名 | 標頭列數 |
|---|---|
| `.csv` | 1 —— 標準 CSV |
| `.csv2` | 2 —— 第一列英文標題，第二列繁體中文標題 |

格式**由副檔名宣告，永不偵測**。偵測是猜測，而猜錯會把第一筆資料當成標頭——且是靜默地。

**`--headers 1|2` 在 `-si` 時是必要的**——stdin 沒有副檔名可以宣告格式。搭配 `-i` 時，
只有在它與副檔名**一致**才會被接受；牴觸即拒絕：

```console
$ csv2 -r --headers 1 -i vs-sqlite.csv2
csv2: vs-sqlite.csv2 declares 2 header row(s) by its suffix, but --headers says 1. The suffix declares the format; --headers is for input with no suffix to declare it. Drop --headers to read the file as it is. Renaming it instead makes the suffix agree with --headers, which is NOT the same thing: a header row then becomes data record 1, at rc=0, and nothing afterwards can tell it was one
csv2：vs-sqlite.csv2 的副檔名宣告了 2 列標頭，但 --headers 說 1 列。副檔名宣告格式，--headers 是給「沒有副檔名可宣告」的輸入用的。請拿掉 --headers，照這個檔案原本的樣子讀它。改檔名是讓副檔名去遷就 --headers，那不是同一件事：一列標頭會因此變成第 1 筆資料，rc=0，而事後沒有任何東西看得出它曾經是標頭
$ echo $?
1
```

副檔名就是宣告；`--headers` 只為「沒有副檔名可宣告任何事」的輸入而存在。它為何是「檢查」
而非「信任」，見 [todo/known-defects.md](todo/known-defects.md)。

基於同樣的理由，csv2 不會在兩種格式之間轉換：把一列標頭的輸入寫進 `.csv2` 路徑會被
拒絕，而不是靜默地因為缺少第二列標頭而少掉一筆（T56d）。

兩列標頭的形式之所以存在，是因為本專案的資料檔是雙語的；把中文欄位標題放在檔案裡，
勝過放在另一份會逐漸失真的文件中。

`.csv2` 除此之外就是一份普通的 CSV——第二列只是第二列標頭，沒有標記、也沒有分隔：

```csv
pkg,ver,note
套件,版本,備註
zlib,1.3.2,first record
zstd,1.5.6,second record
```

那個檔案有**兩**筆紀錄，不是三筆。`csv2 --json` 的第一行會說明這件事，那是確認 csv2
讀成你要的格式最快的方法：

```console
$ csv2 -r --json -i example.csv2 | head -1
{"meta":{"format":"csv2","headers":2,"fields":3}}
```

兩列標頭的欄數必須與資料相同。`.csv2` 的儲存格內不得含原始換行——一筆永遠是一行——
因此值裡的換行寫成 `\n`、CR 寫成 `\r`、反斜線寫成 `\\`。

## 介面

```
選取
  -r                    讀取。完全不給動詞時就是這個，因此 `csv2 -i f.csv` 與
                        `csv2 -r -i f.csv` 是同一個指令
  -get r:c              印出「一格」的值，原樣——與 -update r:c VAL 對稱的那個讀取。
                        要寫腳本就用這個動詞：能組合的是「位址」，而這是值從報告
                        走到編輯的那條路
  -contains S           輸出每個含有 S 的「儲存格」，形式為 紀錄:欄位
  --filter              與 -contains 併用時，改為輸出命中的紀錄
  --include-headers     一併搜尋標頭列（回報為紀錄 0a／0b）
  --normalize           以 NFC 比對；已儲存的內容絕不正規化
  -A N  -B N  -C N      以「筆」為單位的上下文，如 grep；區塊之間以 -- 分隔。
                        只要給了其中任何一個，輸出就切成紀錄形狀，值是 0 也一樣
                        ——形狀跟著旗標走，不跟著數字走。重複給時後者勝出，而 -C
                        會同時設定兩邊，因此 `-C 1 -A 3` 與 `-A 3 -C 1` 不同
  -head N               前 N 筆              （筆，不是行）
  -tail N               後 N 筆
  -mid a,b              第 a 到第 b 筆，含兩端；`a,` 與 `,b` 為開放端，而單獨一個 `,`
                        是「兩端都開放」，也就是每一筆——與 `-r` 相同。
                        超出結尾的範圍會被「截到邊界」，不會被拒絕；而起點超過結尾時
                        會在 rc=0 下輸出空的——但它會說出來：stderr 上一行 WARN，
                        指名你要的起點與那裡實際的最後一筆。無論要求的是哪一種輸出
                        形狀，那行 WARN 都走 stderr，包括沒有 meta 行可放的 -md
                        ——它是「每次執行一行」，不是「每種形狀一行」。它在「有標頭、
                        沒有紀錄」的檔案上也會發出，那裡每一個視窗都在結尾之後；
                        2026-08-21 之前，那正是它唯一漏掉的情況。若呼叫端寧可剖析
                        而不是讀 stderr，--json 結尾那行 meta 的 `records` 回答
                        同一個問題——但前提是你拿它去比對「你要求的起點」：一個
                        落空的視窗、與一個命中後被截到邊界的視窗，回報的都是
                        「檔案自己的紀錄數」加上 `matched:0`；而在空檔案上兩者
                        都讀作 0。能說出「發生的是哪一種」的，是那行 WARN。
                        -head 與 -tail 以同樣方式截斷，而且不出聲，因為「截斷終點」
                        正是被要求的事
  -t                    輸出帶上標頭列（預設不帶）。它只作用於「選取」——一次編輯
                        會重寫整個檔案，且無論有沒有 -t 都一定會寫出標頭列
  -rownum               最前面加一欄紀錄號。它不會重新編號任何東西：見下方
                        「兩套編號」。搭配 -o 或 -so 時，那一欄會連同標頭一起被
                        寫出去，於是那個「檔案」裡的每一個位址都比輸入大一——
                        對它下 `-get 1:1` 得到的是列號，不是第一個欄位。下方那條
                        「位址穩定」的規則講的是「讀取時的顯示旗標」，而這裡寫出的
                        是一個檔案。與 -get、--json 併用會被拒絕，那兩者都會忽略它
  --physical            額外輸出該紀錄起始的物理行號，形如 `record:field@Lline`；
                        與 --a1 併用時兩者合成 `13:6@L14 [F14]`。那兩個數字在那裡
                        相同，只是因為那個檔案沒有任何一筆紀錄跨行：一旦有內嵌換行，
                        它們就會分開，例如 `2:2@L4 [B3]`——實體第 4 行、試算表第 3 列。
                        兩個都是對的，它們回答的是不同的問題。它加在「定位報告」上，
                        因此需要 -contains 且不得搭配 --filter/-md/--json
  --a1                  額外輸出試算表的 A1 記法。限制同 --physical，且它會把
                        標頭列算進去：第 1 筆資料在 .csv 是 A2、在 .csv2 是 A3

輸入／輸出
  -i FILE  -o FILE      檔案路徑；-o 會寫暫存檔再 rename
  -si  -so              由 stdin 讀／寫到 stdout，且不整檔緩衝
  --headers 1|2         搭配 -si 時為必要：stdin 沒有副檔名可宣告格式；而與 -i 併用時，
                        只要路徑不是以 .csv 或 .csv2 結尾就也是必要的——這個檢查
                        而副檔名的比對「不分大小寫」，因此 `DATA.CSV` 會被當成
                        `.csv` 讀，不需要 --headers。到 2026-08-25 之前，這個判斷在
                        「讀取」那一側區分大小寫、在「寫出」那一側不區分，而那個分裂同時
                        產生了一則假的訊息（`-o x.CSV2` 以「它宣告了一個帶標頭的格式」被拒絕，
                        而 `-i x.CSV2` 以「它什麼都沒宣告」被拒絕），以及一次靜默的紀錄遺失：
                        「絕不轉換格式」那道守衛讀的是「讀取」那一側的判斷，於是把一個單列標頭的
                        輸入寫進 `.CSV2` 會成功——而在大小寫不敏感的檔案系統上，那個檔案「就是」
                        你之後讀回來的那個 `.csv2`，其中一筆紀錄被當成第二列標頭吃掉。
                        不分大小寫的比對，讀的仍然是「名字」在宣告格式；那不是偵測。與 -i
                        併用時，只有在它與副檔名「一致」時才被接受，不一致
                        即拒絕——宣告格式的是副檔名。見上方警告。這個條目原本以
                        「絕不要與編輯動詞併用」結尾，而那句話禁止的正是它自己
                        第一行所要求的事：要編輯一條串流就得用 -si，而 -si 就得給
                        --headers。「不一致」的那個情況本來就已經是一條拒絕；
                        那句話並沒有在守著別的東西

                        「讀取端」不是原子的，而追加途中當機可能留下半筆紀錄，那是其他每一種
                        編輯都不會發生的事；`-r -t --truncate-partial` 可以寫出那種檔案的
                        乾淨複本。是「編輯」：沒有編輯動詞的
                        執行會被拒絕，因此一個「選取」不能被寫回它自己的輸入。

COLS 是以逗號分隔的清單，可用欄名、1-based 欄號，或兩者混用：
`-hash license`、`-hash 7`、`-hash 6,license`。與它相伴的有四條拒絕，全都是
「猜比停下來更糟」的情況：

- **空的清單會被拒絕。** `-hash ""` 原本會以 0 結束、而什麼也沒保護；「一個欄位都不指」與
  「某個變數算成了空字串」無法區分，而其中一種會留下一個未受保護的檔案，同時每一項檢查
  都回報成功。
- **一個「同時是欄號、也是欄名」的 token 會被拒絕。** 在欄名為 `2` 與 `1` 的檔案上，
  `-hash 2` 不猜就解不出呼叫端指的是哪一個。請改名，或改用一個不同時是名字的欄號。
- **名字裡的逗號沒有跳脫語法**，因為這份清單就是以逗號分隔的。這樣的欄位請用「欄號」抵達，
  或用 `-delete -col`——它收的是「恰好一個」名字，因此會把那個逗號一起收下。
- **一個「匹配到不只一欄」的名字會被拒絕**，並指出兩個位置而不是替你挑一個——那是下文
  「重複欄名」那條規則，它在這裡同樣適用。這一段到 2026-08-21 之前都寫著「三條」，
```

每個旗標兩種寫法都接受：`-contains` 與 `--contains` 等價。**未知**旗標一律報錯——
multissh 已經被「未知選項被當成主機名稱吞掉」咬過一次。

刻意不提供 `-key`。命令列上傳遞的秘密，在 `ps` 中對本機每個行程都可見，也會留在
shell 歷史裡。

全篇的 `N` 數的都是**筆數，不是行數**。含引號換行的紀錄會跨多行，數行只會得到半筆資料。

位址一律為 `紀錄:欄位`，1-based——這正是 `-contains` 輸出的格式，因此尋找與修改可以
直接銜接：

```sh
csv2 -contains "舊的值" -i a.csv2     # → 12:6 status_notes …
csv2 -update 12:6 "新的值" -i a.csv2 -o b.csv2
```

### 各種模式實際輸出什麼

這支工具會吐出四種不同的形狀，而挑錯是最容易犯的錯：**`-contains` 印的是「報告」，
不是 CSV。**

```console
$ csv2 -contains busybox -i TARGET_PACKAGES.csv
1:1	pkg_name	busybox
1:4	source	fork raliclo/busybox branch develop; upstream git.busybox.net
1:6	status_notes	CORRECTED 2026-08-10 after reading the generated…
6:6	status_notes	Added 2026-08-09. Fills the busybox zstd gap.…
13:6	status_notes	Required because compile.zsh is zsh-only (${0:A:h}…
```

五行，因為有五個**儲存格**命中——過長的值以 `…[+N more chars]` 截短，**而截它的正是 csv2**：
報告是一行一個命中，否則一個 400 bytes 的儲存格會把格式整個帶走。截斷有標記，絕不靜默。
這表示**第三欄是預覽**：要完整的值請用 `-get`，或用 `--json`（它完整承載）。

**那個截斷限制的是「值」，不是「那一行」。** 它保留值的 200 個字元，而 `N` 數的是被丟掉的
字元數——兩者都在「跳脫之前」計算。跳脫發生在之後，因此一個由控制字元組成的值仍然會產生很長
的一行：200 個原始字元可以變成 800 個寫出來的字元。`\xNN` 的十六進位是大寫。若你要從這一欄
量長度，請把 `preview` 與 `N` 以「原始字元」相加，不要去量那一行的位元組。

**這裡的「字元」指的是「字素叢集」（grapheme cluster）**——與 `--pretty` 量的是同一個單位，
也是「一個家庭 emoji 算一個」的原因。五個那樣的 emoji 落在截斷之後，回報的是
`[+5 more chars]`，不是 35（Unicode 純量）也不是 55（UTF-16 單元），而截斷永遠不會落在
一個叢集的中間。

三個欄位以 **TAB** 分隔：位址、欄名、值。每個命中的**儲存格**一行，因此同一筆有兩欄
命中就印兩行，而同一格內出現兩次只印一行。在腳本裡就是 `cut -f1`、`cut -f2`、`cut -f3`。

**值會被跳脫**，使用與 `.csv2` 相同的反斜線慣例再加上 `\t`：字面的 tab 變成 `\t`、
換行變成 `\n`、CR 變成 `\r`、反斜線變成 `\\`。少了它，含 tab 或換行的儲存格會破壞
報告自己承諾的格式——而「同時含有這兩者的帶引號散文」正是這支工具當初為之而寫的資料。
**其餘每一個控制字元都會變成 `\xNN`**，因為這份報告是印到終端機上的，而控制字元在那裡不是
文字：一個存著 `ESC [ 3 1 m` 的儲存格，原本會從第三欄裡面把輸出重新上色；而 ESC 也能抹掉
它正被印出的那一行——也就是承載那個位址的那一行。由 T149 斷言。

**因此第三欄是拿來「讀」的，不是拿來「餵回去」的。** 它是一種顯示形式：經過跳脫，好讓報告
維持一行一個命中。`-update` 收的是**邏輯值**、並會替你做跳脫，因此把那段已跳脫的文字交給它，
寫進去的會是那些反斜線本身——`X⏎Y\Z` 變成 `X\nY\\Z` 這七個字元，rc=0，而且沒有任何東西
會說。**能組合的是「位址」。** 要把值帶過去，請用 `-get` 讀它，它回傳的是儲存的位元組：

```sh
set -o pipefail                                              # 否則那條拒絕會消失
addr=$(csv2 -contains -- "old" -i f.csv2 | head -1 | cut -f1)   # 12:6
val=$(csv2 -get "$addr" -i f.csv2)                           # 值本身
csv2 -update "$addr" -- "$val" -i f.csv2 --in-place          # 可以 round-trip
```

**第一行裡有兩樣東西是承重的。** `| head -1` 會讓整條管線的結束狀態變成 `head` 的——於是一次
「被拒絕」的 csv2，對腳本而言是以 0 結束，而 `addr` 是空的，與「沒找到」無從分辨；而多數維護
腳本會把「沒找到」當成「沒事要做」而跳過。`pipefail`（或先把輸出接起來再切）才是讓那條拒絕
活下來的東西。另外，搜尋字串和其他東西一樣坐在「資料位置」上：`-contains --in-place` 會因為
「旗標出現在資料位置」而被拒絕，因此一支「資料可能等於某個旗標名稱」的腳本，`--` 不只要加在
值上，也要加在搜尋字串上。這兩樣到 2026-08-22 之前都不在這份配方裡，而一個逐字照做的回合，
對一個第 3 筆正是 `--in-place` 的檔案，回報了「沒有任何一格含有 --in-place」。

由 T96 斷言——**那是對「這個工具」而言。中間那個 shell 才是會弄丟資料的那一段**：`$( )`
會把結尾的換行全部吃掉，因此一個以換行結尾的值回來時會少一個位元組，並就這樣被寫回去，
rc=0，什麼也看不出來。csv2 交出去的是對的位元組，收回來的是另一組。當一個值可能以空白結尾時，
請改用檔案把它帶過去，或把結尾釘住：

```sh
val=$(csv2 -get "$addr" -i f.csv2; printf x)   # 用 x 護住值自己的結尾
val=${val%x}                                   # 拿掉那個護欄
val=${val%$'\n'}                               # 拿掉 -get 自己加上的那個換行
```

三行都需要，而第三行是最容易漏掉的那一行：這份配方 2026-08-21 在這裡發表時就漏了它，
於是把結果寫回去時，一個以換行結尾的值會每寫一次就多一個換行，rc=0。`-get` 與其他每一個
指令一樣，會在輸出結尾加一個換行；`printf x` 護住的是「值自己的那個換行」，連同 `-get`
的那一個一起護住了。

**而中間還有第二個東西，上面那三行救不了它：命令列本身。** 一個 shell 變數裝得下 NUL，
`execve` 傳不了。引數會在第一個 NUL 處結束，因此一個中間帶 NUL 的值抵達 csv2 時就已經被剪短，
而 csv2 忠實地寫下它收到的東西：

```console
$ printf 'pkg,note\nzlib,before\x00after\n' > nul.csv
$ val=$(csv2 -get 1:2 -i nul.csv; printf x); val=${val%x}; val=${val%$'\n'}
$ csv2 -update 1:2 "$val" -i nul.csv --in-place; echo $?
0
$ csv2 -get 1:2 -i nul.csv | od -t x1 | head -1
0000000 62 65 66 6f 72 65 0a               # "before"——六個位元組不見了，rc=0
```

**csv2 看不到這件事。** 截斷發生在行程啟動之前，而一個變短的值與一次有意的編輯無從分辨。
這與拒絕表已經守著的那條界線是同一條——「不是合法 UTF-8 的值」——補救方式也相同：
**把值放進檔案帶過去，位元組在那裡活得下來。** 那條拒絕存在，是為了「會弄壞一個字元」的情況；
而「把值的其餘部分整個丟掉」的情況，沒有東西可以拒絕。`-log` 記下的是實際被寫下去的東西
（`"before\x00after" -> "before"`），那是這次遺失唯一看得見的地方。

**報告裡的值是拿來讀的，而這是第三個理由：** `-get` 是唯一會把「儲存的位元組」交給你的形狀，
而即使是它，也擋不住你把那些位元組倒進什麼容器裡。

**一個位址只跟它來源的那個檔案一樣新，而它有「兩種」會錯、卻沒有任何東西會說的可能。**

第一種是過期的 sidecar。若檔案旁邊有一份 `.index`，而資料後來被改成 O(1) 戳記看不出來的
樣子——大小相同、mtime 相同、首尾位元組也相同——搜尋就會信任它，回報的紀錄號可能是偏掉的。
那三行於是全部以 0 結束，而那次編輯落在隔壁那一筆上。有兩個做法可以讓它不可能發生，而它們的
價錢不一樣：

```sh
csv2 --verify-index -i f.csv2          # O(n)：先證明那份 sidecar，不成立就以 1 結束
csv2 -contains "old" --no-index -i f.csv2   # 或者，根本不要用它
```

在 17.7 MB / 450,000 筆上：證明那份 sidecar 要 451 ms，其後那次搜尋 204 ms，合計 655 ms；
不用索引則是 528 ms。**只搜一次的話，先證明它是兩者中比較貴的那個。** 大約從第二次搜尋起它
才划算，因為那次證明只付一次。2026-08-21 之前這裡說兩者「都很便宜」，而那是在做數字撐不住的事。

**第二種更單純，而上面兩個都碰不到它：有人在你的兩個指令之間改了那個檔案。** 那個位址在
`-contains` 印出它的當下是對的，而等到 `-update` 執行時，它描述的已經是另一筆。csv2 看不見
這件事——每個指令都重新開啟那個檔案，而那正是它能安全地被執行的原因——因此若一個檔案可能在
你手下改變，要嘛把寫入者排成序列，要嘛帶著「值」而不是「位址」走。

`--no-index` 就是那個「拒絕信任 sidecar」的旗標；它列在索引相關旗標裡，而在這裡點名，
是因為這份配方正是它要緊的地方。

**一次寫入會順手修好 sidecar，而那會抹掉證據——在「大到會建索引」的檔案上。** 若一份過期的
索引把一次編輯送到錯的那一筆，那次編輯會重寫整個檔案、並在過程中建出一份正確的 sidecar——
於是事後的 `--verify-index` 會說 `index OK`、以 0 結束，而它說的是你剛剛弄壞的那個檔案。
在 `CSV2_INDEX_MIN_BYTES` 以下，那次寫入不會建索引，於是那份過期的 sidecar 留在原地，
`--verify-index` 仍然以 1 結束——**證據在小檔案上活著，在大檔案上不會**。兩種情況都一樣：
請在編輯「之前」驗證，不是之後。

**`-contains`、`-mid` 與 `-tail` 會讀 sidecar；`-get` 與各個編輯動詞是掃描的。** 因此一份
過期的索引可以讓配方的任何一半出錯，而是哪一半取決於你怎麼找到那個位址：搜尋回報的紀錄號可能
偏掉，`-mid` 的視窗也可能從錯的那一筆開始；而你把位址交給的 `-get` 或 `-update`，會在「那個
位址現在指向的那一筆」上完美地工作。每個指令都沒有做錯，而兩者彼此矛盾。

*（這一段在 2026-08-21 之前寫的是「只有 `-contains`」。那句話出自一份盲測報告，而我沒有量過；
下一個回合量了，發現 `-mid` 會走索引。教訓就是這個檔案一再記錄的那一個：一句關於行為、
取自報告而沒有執行過的話，是一個猜測。）*戳記看得見與看不見什麼，見下方「索引 sidecar」那一節。

比對是**區分大小寫**的，且沒有旗標可以改變。**要折疊大小寫，做法是 `--json` 加自己掃一遍**，
不是把各種拼法列舉一遍：窮舉 `mbedtls`／`mbedTLS`／`MbedTLS`／… 是 2ⁿ 次執行，七個字母就是
128 次，二十個字母是一百萬次。

```sh
csv2 -r --json -i f.csv2 | python3 -c '
import json,sys
for line in sys.stdin:
    o=json.loads(line)
    if "fields" not in o: continue
    for k,v in o["fields"].items():
        if "mbedtls" in v.lower(): print(o["record"], k, v)'
```

掃一遍、涵蓋所有拼法，而且回來的紀錄號可以直接拿去定址。

**`--normalize` 也會作用在「搜尋字串」上**，不只是儲存格——因此以 NFC 打出來的搜尋字串，
找得到以 NFD 儲存的儲存格。儲存本身仍然絕不正規化，被正規化的只有那次比較。

`--normalize` 只影響 Unicode 正規化，
與大小寫無關。

**`--normalize`管的是儲存格「值」，不是欄位「名稱」。** 欄位名稱一律以正規等價比對：在命令列
打出 NFC 的 `café`，找得到以 NFD 儲存的標頭，給不給那個旗標都一樣——因為對每一個讀到它的人
來說，那就是同一個名字。而「值」預設逐位元組比對，除非你另外要求；因為值是資料，改變「什麼
算相等」等於改變檔案裡有什麼。

其中一個後果值得直說：**一個名稱若匹配到超過一個欄位，會被拒絕，而不是依位置解析。** CSV
並未禁止重複的欄位名稱，而試算表就會產生；因此在一個有兩個 `note` 欄位的檔案上下
`-update 1:note X` 會是一個錯誤，並指出那兩個位置——請改用欄號定址。兩個只差在 Unicode
形式的欄位會以同樣的方式相撞，而那兩者在 hex dump 裡看起來並不相同。由 T75 斷言。

### 對只有一列標頭的檔案使用 `--zh`

`--zh` 會退回到「僅有的那一列標頭」，而且不說話。那是刻意的，而且它是這支工具裡唯一一處
靜默的替代，因此這裡寫的是理由，不只是行為。

`--zh` 是一種**顯示偏好**，不是對資料的選取。拒絕它，會為了一件純屬美觀的事而弄壞任何
「走遍 `.csv` 與 `.csv2` 混合檔案」的腳本，逼它為了要求一項修飾而先分支判斷格式。而這個
退回也不會被誤認為成功：你要求的是中文欄名，而輸出裡明顯是英文欄名——那是「不一樣」，
不是「看起來對但其實錯」。

**若你真正想做的是「斷言這個檔案是雙語的」，`--zh` 是錯的工具，`--json` 才是對的：**

```console
$ csv2 -head 1 -t --json -i pkgs.csv | head -1
{"meta":{"format":"csv","headers":1,"fields":2}}
$ csv2 -head 1 -t --json -i pkgs.csv2 | head -1
{"meta":{"format":"csv2","headers":2,"fields":2}}
```

那一行的存在，正是為了讓呼叫端能「斷言自己讀到的是什麼」，而不是接受一個猜錯的解析。

**但要分清楚它哪些部分是「觀察到的」。** `fields` 與 `records` 是從檔案數出來的；
`format` 與 `headers` 是那個**宣告**——它們覆述檔名說了什麼，因為「由副檔名宣告、絕不偵測」
就是這個意思。因此 `.csv2` 上的 `headers:2` 並不是「第二列標頭存在」的證據，而是
「csv2 把第二行當成標頭處理了」的證據。

**這件事對「不是你產生的檔案」很要緊。** 把一份只有一列標頭的 `.csv` 改名成 `.csv2`，
csv2 會把它的第一筆資料讀成標頭列 `0b`——rc=0、少一筆，而且沒有任何檢查抓得到，因為
「一列標題」與「一列資料」在形狀上並無分別。格式本身救不了這件事，只有「去看」可以：

```console
$ csv2 -head 1 -t -i handed-to-me.csv2       # 兩列標頭，接著第 1 筆
pkg,ver,note
zlib,1.3.2,first                             ← 是資料不是標題：一個戴錯名字的 .csv
zstd,1.5.7,second

$ csv2 -head 1 -t -i vs-sqlite.csv2          # 真正的 .csv2 長這樣
dimension,csv2,sqlite,advantage,basis,note
比較項目,csv2,SQLite,優勢方,依據,說明
"storage, text at scale",…
```

**寫出**這樣的檔案會被拒絕（csv2 不會替你在兩種格式之間轉換）；**讀取**則無法拒絕，
而那個不對稱是刻意的——csv2 相信檔名，因為發明一個偵測器就等於去猜，而那正是副檔名規則
存在的目的所要防止的事。由 T97 斷言。

**另一個方向是同一次改名、同一種損壞**，而這份文件到 2026-08-21 之前只寫了其中一邊。
一份 `.csv2` 被交到你手上時叫做 `.csv`，它不會少東西，而是多一筆：那列中文標題成為第 1 筆
資料，搜尋得到、也定址得到，rc=0。`--json` 的 meta 那一行幫不上忙——它會說
`{"format":"csv","headers":1}`，那句話對「檔名」為真，對「內容」什麼也沒說。同樣地，
唯一的檢查是「去看」：

```console
$ csv2 -mid 1,1 -t -i handed-to-me.csv       # 第 1 筆是一列標題嗎？
pkg,ver,note
套件,版本,備註                                <- 標題坐在資料裡
```
由 T78 斷言。

### UTF-8 的 BOM 會被剝除；UTF-16 的會被拒絕

以 UTF-8 BOM 開頭的檔案——典型上就是 Excel 匯出的那些——在讀取時會被移除，也不會被寫回去。
**只移除一個**：第二個 BOM 是第一欄名字裡的一個零寬不斷空格，那是資料，因此它會留在輸出裡。
不過用來「定址」的那個名字會把它剝掉，這正是為什麼在這種檔案上 `-get 1:a` 仍然可用，而寫出去
的標頭仍然帶著它。

**UTF-16 的 BOM 是另一種檔案，得到的是另一個答案：拒絕，並指出該用的轉換。** `FF FE` 與
`FE FF` 不可能出現在 UTF-8 檔案的開頭，因此這不是在猜。csv2 讀的是位元組、不做編碼轉換；
放著不管的話，它會以「位元組透明」的方式讀一個 UTF-16 檔案——那對一個承諾位元組原樣往返的
工具是正確的，而對拿著這個檔案的人毫無用處：每隔一個位元組就是 NUL、欄名裡帶著它們，而整份
東西會在 rc=0 下解析成一堆沒有意義的紀錄。

**這道守衛看的就只有 BOM，也只能是 BOM。** 一個「沒有 BOM 的 UTF-16 檔案」，**可能**會在
rc=0 下解析成一堆沒有意義的紀錄，而 csv2 沒有任何「不會同時誤傷合法資料」的判斷依據可以
偵測它。它也同樣可能以一則「欄數不符」的訊息失敗——那些 NUL 位元組會讓欄位數變得不齊——
而那是巧合，不是檢查：不要把那個錯誤讀成「csv2 察覺了編碼」。若有人交給你一個 UTF-16 檔案，請自己轉換，不要指望被告知。

**任何位置的空白行都會被拒絕——在「兩欄以上」的檔案裡**，包含「以兩個換行結尾」的檔案所帶的那一個：
`record 2 (line 3) is a blank line, and a blank line is not a record with 2 empty fields;
remove it`。其他每一個 CSV 讀取器在這裡都有自己的看法，而且彼此不同——跳過它、回傳一個空欄位、
回傳 N 個空欄位——而其中每一種都會悄悄改變「第 3 筆是什麼」。

**在「單欄」的檔案裡沒有東西可以拒絕：** 一個空白行與「一筆只有一個空欄位的紀錄」是同一組
位元組，因此它會被讀成一筆紀錄。若你希望檔案自己說清楚是哪一種，請在那一行寫 `""`——它讀起來
完全一樣，而且不會被誤認成別的東西。

**`.csv2` 必須以換行結尾；`.csv` 不必。** 「一筆一行」正是 `.csv2` 的意思，因此一個「停在
行中間」的檔案，最後那一筆是撕裂的，會被拒絕，並指名 `--truncate-partial` 是丟棄它的方式。
一個沒有結尾換行的 `.csv` 很平常——很多工具就是那樣寫的——它會照原樣被讀。

**未加引號的欄位裡的裸 CR 是資料，而這正是 csv2 與多數解析器不同的地方。** `1,x<CR>y` 是
一筆、值為 `x<CR>y`；Python 的 `csv` 模組會把它讀成兩列。兩者都不算錯——RFC 4180 把紀錄
分隔符定義為 CRLF，對「欄位中間的單獨 CR」什麼也沒說——但一支跨這兩者比對數量的腳本會看到差異。
在「引號內」，CR 到哪裡都是資料。這個承諾對「一筆紀錄帶著幾個 CR」都成立——2026-08-21 之前，第三個 CR 會把一個數量壓過去，同樣的紀錄就被拒絕了——而它對「紀錄」成立、對「欄名」不成立：標頭列裡的一個裸 CR，正是一個以 CR 結尾的檔案的樣子，會被拒絕（見上文）。把那個欄位加上引號，那個 CR 就又是名字了。

**NUL 與其他控制位元組在檔案內容裡會被原樣接受**：它們是資料、可以原樣往返，而定位報告會為了
顯示把它們跳脫。**「在檔案內容裡」就是這個承諾的全部**：NUL 根本沒辦法經由「引數」抵達 csv2，
因為命令列在第一個 NUL 處就結束了——見上文那個組合配方。

**零位元組的檔案同樣會被拒絕**，訊息是 `expected 1 header row(s), found 0`——一個沒有標頭的
檔案不會宣告自己的形狀，而替它猜一個，正是「一筆資料變成標頭」的發生方式。「整個檔案就是一個
UTF-16 位元組順序記號」的那種檔案也是——那正是編輯器把一份空文件存成 UTF-16 時寫出來的東西：
兩個位元組、語意上同樣是空的，而 2026-08-21 之前它會被接受，成為一個「欄名就是那兩個位元組」
的單欄 CSV（T162）。

```console
$ csv2 -r -i export.csv
csv2: this file begins with a UTF-16LE byte-order mark; csv2 reads bytes and
does not convert encodings, so it would parse as records that mean nothing.
Convert it first with: iconv -f UTF-16LE -t UTF-8 file > converted.csv -- the
new name has to keep a .csv or .csv2 suffix, because the suffix is what
declares the format
```

**gzip 檔案得到同樣的處理。** `1f 8b` 與 `ff fe` 一樣，都不可能是一個 UTF-8 CSV 的開頭；
而一個叫做 `.csv` 的壓縮檔，到 2026-08-25 之前都會以 rc=0 被讀成「一筆二進位紀錄」——
`-contains` 在裡面搜尋，然後回報什麼也沒找到，而那正是這個工具存在所要避免的答案。
那條拒絕會指出 `gunzip -c`。

**CR 行尾得到同樣的處理**——那是 OS X 之前的 Mac 慣例，CSV 不支援它。**它有兩個判斷，
因為它有兩種樣子。** 第一個是「標頭列裡有一個裸 CR」，而它是精確的、不是近似的：一個以 CR 結尾的檔案沒有 LF 去結束它的第一行，
因此它的全部內容都落在第一筆紀錄裡，而欄名正是證據永遠所在的地方。

這個判斷錯過兩次，方向相反，而兩次都值得知道，因為它們說出了「這條規則不是什麼」：

- 一開始它問的是「有沒有『完全沒有』LF」，而一個結尾的 LF 就足以讓它閉嘴：那個檔案於是以
  **rc=0 讀成零筆紀錄**。
- 接著它問的是「裸 CR 有沒有比 LF 多」，那是一個數量，不是一件關於行尾的事實。
  `a,b⏎1,x␍␍␍y⏎`——一筆紀錄、以 LF 結尾——被一則說它「使用 CR 行尾」的訊息拒絕，而那則訊息
  指定的 `tr '\r' '\n'` 會把那一筆變成 csv2 讀不回來的檔案。另一個方向上，
  `col␍"L⏎L⏎L⏎L"␍zz␍`——一個真正以 CR 結尾的檔案——有三個 CR、三個 LF，於是那個數量從未觸發：
  它以 rc=0 被讀成三筆紀錄，欄名是 `col␍"L`，引號欄位沿著它自己的換行被撕開，stderr 上
  一個字也沒有。

第二個是**檔案的最後一個位元組是一個裸 CR**，而那正是「一段以 CR 分行的內文、配上一個正常結束
的標頭」的樣子——也就是 `(echo a; cat old_mac_body) > f.csv` 會產生的東西。標頭那個判斷看不見
這種檔案，而到 2026-08-25 之前，它會以 rc=0 被讀成「一筆」紀錄、meta 上寫著 `records:1`：
那個檔案裡的每一個計數都錯了，錯的倍數就是它的行數，而文件指定的那個「有沒有」的檢查，會很有
把握地回報一個錯的數字。

**紀錄**裡的裸 CR 仍然是資料、仍然能原樣往返、仍然不受影響——一個以換行結尾的檔案永遠不會被
拒絕，不論它的紀錄裡裝了什麼。如果那個 CR 確實是你最後一個值的最後一個位元組，請讓檔案以換行
結尾，它就會被當成資料讀進去。而一個確實屬於「欄名」的 CR
必須加上引號——一對引號，意圖就變成明說的。由 T115 與 T180 斷言。

但比這兩件事都要緊的是它「不會」落在哪裡：第一欄的名稱是 `pkg_name`，永遠不會是
`\ufeffpkg_name`。

那個區別才是重點。一個被吸進第一列標頭的 BOM，會讓 `-update 1:pkg_name` 解析不到一個
明明就在眼前的欄位——而「以名稱定址」正是這支工具要你拿來寫腳本的東西。由 T7 斷言。

**沒有欄位投影**：沒有任何東西可以「只取 license 那一欄」。若你手上已經有一個位址、
想取出那一個值，用 `-get`：

```console
$ csv2 -get 12:6 -i pkgs.csv
fork raliclo/busybox, branch develop
```

它只印出那一格，別的什麼都不印——沒有引號、沒有分隔符、沒有標頭、沒有位址——因此
`$(csv2 -get …)` 就是那個值。刻意不是 CSV：只有一格的 CSV 列，在值含逗號時仍得加引號，
於是呼叫端又得回頭解碼。它用的位址與 `-update` 相同，而那正是讓「搜尋、讀取、寫入」
能夠組合起來的東西：

```console
$ csv2 -contains "old value" -i pkgs.csv    # -> 12:6
$ csv2 -get 12:6 -i pkgs.csv                # 先看看現在是什麼
$ csv2 -update 12:6 "new value" -i pkgs.csv --in-place
```

位址越界是**錯誤**，不是空輸出——空輸出正是「一個確實存在的空儲存格」的樣子，兩者必須
能夠區分。標頭儲存格不可定址：定位報告稱它們為 `0a`／`0b`，但沒有任何動詞能作用其上，
`-update` 也不行。

**`-get` 結尾一律恰好一個換行，而那是「終止符」不是資料。** 因此，一個「本身就以換行結尾」
的值取回來會有兩個換行，且沒有任何東西標示哪個是哪個——此時 `$(csv2 -get …)` 會把兩個都吃掉，
因為命令替換剝除的是「全部」的結尾換行，不是一個：

```console
$ csv2 -get 1:2 -i pkgs.csv | od -c            # 該格是 "value ends here\n"
0000000   v   a   l   u   e       e   n   d   s       h   e   r   e  \n
0000020  \n
0000021

$ csv2 -mid 1,1 --json -i pkgs.csv                 # 同一格，明確無歧義
{"record":1,"line":2,"fields":{"a":"x","b":"value ends here\n"}}
```

值「內部」的換行沒有問題——它們會原樣回來。唯獨「結尾」的換行無法與終止符區分。當這個區別
有意義時，`--json` 才是承載得了它的形狀。由 T71 斷言。

`-get` 回傳的是**邏輯值**，不是磁碟上的位元組。`.csv2` 檔以 `\n` 兩個字元儲存內嵌換行；
`-get` 交給你的是那個換行，與從一個存著真實換行的 `.csv` 檔取得的結果相同。兩種格式的差別
在於「如何儲存一個值」，不在於「那個值是什麼」。

要一次取出多個值，請用 `--json` 以欄名讀取，或取定位報告的第三欄：

```console
$ csv2 -contains busybox -i pkgs.csv | cut -f1      # 位址，完整
$ csv2 -contains busybox -i pkgs.csv | cut -f3      # 值，是「預覽」——見上
```

### `--a1` 會把標頭列算進去

`--a1` 以試算表定址一格的方式印出位置，因此列號取決於該格式有幾列標頭——`.csv` 一列、
`.csv2` 兩列。同一筆資料紀錄在兩者中因此落在不同的試算表列：

```console
$ csv2 -contains zlib --a1 -i pkgs.csv       # 一列標頭
1:1 [A2]	pkg	zlib
$ csv2 -contains zlib --a1 -i pkgs.csv2      # 兩列標頭
1:1 [A3]	pkg	zlib
```

兩者都是第 1 筆資料。`A2` 與 `A3` 才是你實際會點下去的那一格。欄位字母也以同樣方式由欄號
換算而來：第 3 欄是 `C`。

**過了 Z 之後，字母的進位方式與試算表相同**，而那與普通的 26 進位不一樣：它沒有代表零的
位數，因此第 27 欄是 `AA` 而不是 `BA`，第 52 欄是 `AZ`、第 53 欄是 `BA`，第 702 欄是 `ZZ`、
接著是 `AAA`。上述每一個邊界都由 T103 斷言——實作一開始就是對的，只是沒有東西守著它，也
沒有東西說出來，於是要處理寬表的人只能用猜的。

`--a1` 與 `--physical` 是加在**定位報告**上的，因此需要 `-contains`，並且與 `-r`、
`--filter`、`-md`、`--json` 併用會被拒——那些不產生位址，沒有東西可以加上去。

### `-log` 會寫什麼、不會寫什麼

`-log FILE` 會附加一筆帶時間戳的操作紀錄。**多個 csv2 行程可以共用同一個 log 檔**：追加
發生在核心裡，因此並行的寫入者不可能落在別人的位移上把它蓋掉。這件事值得寫出來，因為它並非
一直都成立——原本的做法是「以寫入開啟檔案並 seek 到尾端一次」，那在一個行程下是同一件事，
兩個行程下就不是。八個行程各記錄 25 次操作，200 筆只剩 98 筆，沒有一筆是壞的，每一次都以
0 結束。由 T104 斷言，而它在 Windows 上也會執行——這段文字第一次寫下時，它在那裡是失敗的：
120 筆只剩 110 筆。Windows 路徑現在使用 `FILE_APPEND_DATA`，也就是作業系統層級的不可分割
追加，而不是 C runtime 的「先 seek 再寫」。**沒有任何平台還有窗口。**

它是一份稽核軌跡，因此會記下「改了什麼」——
也正因如此，它必須明確說出它「不會」記下什麼：

| | 是否進入 log |
|---|---|
| 呼叫的指令列 | 會，但值會被置換：`-update 1:6 <value>`、`-insert 3 <row>` |
| 金鑰**位元組** | 絕不 |
| 金鑰檔的**路徑**與金鑰指紋 | 會——絕不記錄金鑰本身。但見下方：兩種標記的指紋意思並不相同 |
| **一般**欄位的新舊值 | 完整記錄、絕不截斷；那正是稽核軌跡的意義。`-update` 與 `-delete -cell` 一體適用——清空一個儲存格會記下它原本裝著什麼 |
| 被刪除的**紀錄** | 逐欄記下它的內容：`delete record 2: "a"="4", "b"="5", "c"="6"`。那是這個工具銷毀得最大的東西，因此那則紀錄要說出裡面有什麼。**欄名同樣有引號**——一個名字裡可以有逗號或 `=`——而這個範例到 2026-08-22 之前都印成沒有引號的樣子，那足以讓一個照著它寫成的剖析器把那一行切錯 |
| 被刪除的**欄位** | 記欄名，不記各筆的值——整次執行一則，而不是每筆一則，因為那些值就是整個欄位 |
| `-hash` 與 `-encrypt` | 哪些欄位、用哪一把金鑰。無金鑰的雜湊會明講：`hashing columns notes with NO key (unsalted SHA-256)` |
| 這次執行寫出的 sidecar | `wrote index /path/to/f.csv.index: N records, stride 256, M entries`——唯一帶著絕對路徑的一行 log，也是唯一一行講「輸入以外的另一個檔案」的 |
| 該次執行的結果 | `wrote N records, M fields, atomic rename OK`——那一行說明「寫入完成了」，也是「想知道一次編輯有沒有落地」時該找的那一行。**`M` 是「一列有幾欄」，不是「寫出了幾個欄位」**：一個 3 筆 3 欄的檔案說 `3 records, 3 fields`，而一個 22×7 的說 `22 records, 7 fields` |
| **受保護**欄位的新舊值 | `<redacted>`，包含出現在一筆被刪除的紀錄裡時 |

**一筆紀錄就是一行，而「每一行」都會被跳脫以維持這件事。** 換行、TAB、CR 與反斜線分別
寫成 `\n`、`\t`、`\r` 與 `\\`，而**其餘每一個控制字元都會變成 `\xNN`、十六進位用大寫**
——與定位報告用的是同一套約定，只是到 2026-08-21 之前只寫在其中一處。一個帶著 ESC 的值，
在這裡是 `\x1B`。沒有這道跳脫時，含換行的文字會開啟新的一行，而那一行的
全部內容由該文字決定——一筆時間戳由它自己挑選的偽造紀錄，就這樣以 rc=0 落進稽核軌跡。
截斷擋不住那件事，它只是把偽造的那一行剪短。

**「每一行」並非一直都成立，而那個缺口值得知道**，因為它說明了這個保證現在建立在什麼上面。
原本這道跳脫只套用在記入 log 的「值」，別的地方都沒有。另外兩條路徑因此未經跳脫就進入
log：一是「呼叫」那一行，它**每一次執行**都會寫——於是單靠 `-contains` 就能偽造出一筆紀錄，
完全不需要對資料有寫入權限；二是任何把輸入引述回來的錯誤訊息，例如 `no column named "…"`
裡的那個名字。跳脫現在只發生一次，就在「建構 log 行」的那一點，而那也是唯一涵蓋得到
「還沒有人寫出來的訊息」的地方。由 T102 斷言，其中包含「恰好跳脫一次」：兩個各自都正確的
修正曾讓呼叫那一行被跳脫兩次，把換行變成再也還原不回去的字面 `\\n`。

**它的文法，好讓腳本讀得懂。** 一筆是一行：`時間戳 層級 訊息`，以單一空白分隔，層級補齊到
五個字元。在一筆 `update` 紀錄裡，新舊兩個值各自以 `"` 包住，而值「裡面」的 `"` 會被
**加倍**，與 `.csv2` 及 RFC 4180 的做法完全相同——因此 `INNOCENT" -> "ALSO INNOCENT`
會寫成 `"INNOCENT"" -> ""ALSO INNOCENT"`，看得懂這個格式的人不必再學一套。沒有這個加倍，
一個值就能在一行本身合法的紀錄「內部」改寫「哪一半是舊值、哪一半是新值」，而沒有任何正規
表示式救得回來。由 T106 斷言。剖析時先解開整行的跳脫（`\n`、`\t`、`\r`、`\\`，**以及
`\xNN`**），再讀那些帶引號的欄位。照著較短的那份清單寫成的讀取器——也就是這一段在 2026-08-21
之前給的那一份——會把一個帶 ESC 的值重建成六個字面字元，然後回報一個並不存在的不一致。

**「完整」沒有上限，而超過 1 MiB 時它會說出來。** 比這更大的值仍然完整寫出，並附一行 `WARN`
指名它的大小：設上限等於一份會丟資料的稽核軌跡，而那正是這一條要避免的東西；但一份安靜地
長了一 MB 的 log，應該當場說出來。只有「舊值」到得了那個大小——新值傳不進來，命令列會先被
`ARG_MAX` 拒絕。

**`:hmac:` 的指紋標識「金鑰」。`:enc:` 的指紋標識「金鑰**與這個檔案的 salt**」，因此每次
執行都不同。** 兩者都是「推導後金鑰」SHA-256 的前四個位元組，而分歧就在那裡：`-hash` 以固定的
salt 推導，因此同一把金鑰檔永遠得到同一個數字；`-encrypt` 每次執行抽一個新的 16 bytes salt
並存進標記裡，因此推導後的金鑰——以及指紋——是每個檔案一個。

這兩個迴圈**什麼都不會印**——csv2 在正常路徑上不輸出任何東西（唯一的例外是 `WARN`，而它是
一張封閉的六項清單，見「結束狀態」一節）——因此那些標記必須事後從檔案裡讀出來：

```console
$ for i in 1 2 3; do csv2 -encrypt secret -keyfile k.bin -i s.csv -o e$i.csv -t; done
$ for i in 1 2 3; do csv2 -contains ':enc:' --include-headers -i e$i.csv | cut -f3; done
secret:enc:d88cdbf1:…      # 一把金鑰檔，
secret:enc:e16b394a:…      # 三次執行，
secret:enc:869e54ce:…      # 三個指紋

$ for i in 1 2 3; do csv2 -hash secret -keyfile k.bin -i s.csv -o h$i.csv -t; done
$ for i in 1 2 3; do csv2 -contains ':hmac:' --include-headers -i h$i.csv | cut -f3; done
secret:hmac:9acc9081       # 每次都是同一個數字；換一把金鑰檔才會變
```

本節的舊版本把那些標記寫成「迴圈的輸出」。它們是檔案的**標頭**；照著逐字執行的讀者會得到
一片空白，而且無從判斷到底有沒有發生任何事。這與本文件在 `-log` 那一節坦承過的是同一個錯誤，
在這裡又犯了兩次，而它一直活到有人「去執行」那個迴圈、而不是「去讀」它為止。

**因此不要把 `:enc:` 的指紋帶到另一個檔案去比對。** 在「同一個檔案內」比對它完全正確，
拒絕時做的正是那件事——csv2 會用該檔案存下的 salt 重新推導再檢查。把它抄下來當成
「我的金鑰指紋」再拿去比對第二個檔案，會對**同一把金鑰**得到不符，讀起來就像金鑰換過了。

一個欄位是否「受保護」，依據的是**檔案自己的標頭這麼說**——標頭寫著 `secret:hmac:d6c8da42`
或 `secret:enc:…` 就是標記——而不是「本次執行剛好正在加密或雜湊它」。因此，即使這一次執行
自身完全沒有做任何轉換，編輯一個已受保護欄位的儲存格仍然會被遮蔽：

實務上你不會看到一筆被遮蔽的 update，因為那次編輯根本走不到那一步——瞄準「檔案宣告為已轉換」
欄位的編輯會被直接拒絕：

```console
$ csv2 -update 1:secret "new value" -i pkgs.csv -o out.csv -log app.log
csv2：-update 1:secret 指向一個「本檔案宣告為已轉換」的欄位；寫進去的原始值會待在一個
雜湊欄位裡、看起來就像一個雜湊，而沒有任何東西能發現它……
$ echo $?
1
$ grep update app.log
INFO  csv2 -update 1:secret <value> -i pkgs.csv -o out.csv -log app.log
```

那個拒絕是更強的防線：它阻止那次寫入，而不是把它藏起來——那也正是下方拒絕表所描述的。
**遮蔽仍然保留為最後一道防線**——若日後有任何路徑把受保護欄位的值寫進 log，它會是
`<redacted>`——但今天沒有任何記錄在案的途徑到得了那裡。本節的舊版本把「被遮蔽」的形式當成
一次普通操作展示，而那段文字在拒絕被加入之後仍留在原地，於是讀者會去試一個不可能成功的
指令。由 T40 與 T73 斷言。

**log 是一個具有一般權限的磁碟檔案。** 遮蔽讓秘密不進入它，但那不構成「可以把 log 放在
隨便什麼地方」的理由。

**log 不會記下、而第二個讀者也還原不出來的東西：**

| 不在軌跡裡 | 為什麼有影響 |
|---|---|
| 工作目錄，以及「絕對路徑形式的 `-i`」 | 從兩個不同目錄各跑一次 `csv2 -update 1:2 X -i f.csv --in-place`、寫進同一份 log，得到的是同樣的三行。`-log` 的路徑「是」絕對的；輸入路徑則照你打的樣子被引用 |
| 行程編號，或任何排序用的鍵 | 兩個並行的寫入者各自記下 `wrote N records … rename OK`，而其中一次編輯不在檔案裡。那些行無法與它們自己的 `update` 行配對 |
| 一次寫入的目的地 | `wrote N records` 沒有指名任何檔案，而 `-o` 寫到一個「已被占用」的路徑會毀掉原本在那裡的東西，軌跡讀起來卻與「寫到一個新檔案」完全相同 |
| 「某份索引被相信了」 | 那條唯一可能靜默出錯的分支（見 sidecar 那一節）只在 `-debug` 下、只在 stderr 上說得出來，別無他處 |
| 一次搜尋找到了什麼 | 一次 `-contains` 只記下它的呼叫，因此之後 `-update` 所消費的那個位址，在軌跡裡沒有來歷 |

單獨看，其中沒有一項是缺陷；合起來，它們正是「這份軌跡回答的是『這次執行做了什麼』，
而不是『這個檔案發生過什麼』」的原因。

### 兩套編號，以及它們不一致的地方

`-rownum` 會在最前面加一欄。其餘一切維持原本的編號：

```console
$ csv2 -contains busybox -i pkgs.csv
1:1	pkg_name	busybox
1:3	source	fork raliclo/busybox, branch develop
$ csv2 -contains busybox -rownum -i pkgs.csv
1:1	pkg_name	busybox
1:3	source	fork raliclo/busybox, branch develop

$ csv2 -r -t -rownum -i pkgs.csv
rownum,pkg_name,version,source,license
1,busybox,1.37.0,"fork raliclo/busybox, branch develop",GPL-2.0
```

（兩個命中，因為那一列的 `source` 欄位裡也有這個詞——這個區塊到 2026-08-21 之前都只印一個，
而那份 fixture 自己印出來的內容說的是另一回事。）

位址 `1:1` 在兩次執行中都仍然代表 `pkg_name`。但在印出來的那一列裡，`pkg_name` 現在是
**第二個**實體欄位。**只要開了 `-rownum`，位址編號與實體欄位位置就差一格**，而輸出裡沒有
任何東西會告訴你這件事。

位址保持穩定是刻意的：你先前找到的位址、或從 bug 回報裡抄下來的位址，必須不論後續執行用了
哪些顯示旗標都仍指向同一格。`-update 1:1` 編輯的都是 `pkg_name`，與找到它的那次執行有沒有
給 `-rownum` 無關。

代價在另一個方向。**任何「依欄位位置」讀取輸出的東西——另一支程式、試算表匯入、`cut`——
看到的是位置 1 是 `rownum`，其餘全部往右位移一格。** 因此不要把兩者混用：位址對位址、
位置對位置。

rownum 那一欄也**永遠不會被搜尋**：`-contains 4` 不會只因為某筆「是第四筆」就命中它。
它的值是由顯示產生的，不是你檔案裡的資料；讓它可被比對，等於讓一次執行的輸出改變那次執行
找得到什麼。由 T15 斷言。

標頭列預設**對搜尋是不可見的**，即使它們的儲存格和其他儲存格一樣是文字。
`--include-headers` 會把它們納入。在有兩列標頭的 `.csv2` 上，第一列定址為 `0a`、第二列為
`0b`，如此一來「命中英文標題列」與「命中中文標題列」才能區分。在 `.csv` 上只有一列標頭，
它就是單純的 `0`——**用 `^0[ab]:` 去比對的腳本，會漏掉 `.csv` 的每一個標頭命中**：

```console
$ csv2 -contains note --include-headers -i pkgs.csv2
0a:3	note	note
$ csv2 -contains 備註 --include-headers -i pkgs.csv2
0b:3	note	備註
$ csv2 -contains 備註 --include-headers --zh -i pkgs.csv2
0b:3	備註	備註
```

```console
$ csv2 -contains name --include-headers -i pkgs.csv     # 只有一列標頭
0:1	name	name
```

在 `--json` 裡，同一個區別是一個 `header_row` 鍵——`"0a"`、`"0b"` 或 `"0"`——只在「命中標頭」
時出現。到 2026-08-21 之前，兩列都輸出 `"record":0`，唯一剩下的分辨依據是實體行號——在那個
「給程式看的」輸出形狀裡，而且就在「分得出來」被當成那兩個標籤存在理由的那句話底下。

**命中標頭不算一次 match。** `--json` 結尾那行 meta 的 `matched` 數的是「相符的紀錄」，而
標頭列不是紀錄——因此一次印出 `0a:3 note note` 的執行，回報的是 `"matched":0`。那與 csv2
在其他每一處劃線的方式一致，但它也表示：文件指定的那個「有沒有」的檢查（讀 meta 行的
`matched`），對一個它剛剛印出來的命中回答「沒有」。用了 `--include-headers` 時，請改數命中行數。

「標頭列不是紀錄」還有兩個後果：`-A`/`-B`/`-C` 的上下文永遠不會進入標頭列；而
`--filter --include-headers` 會把一列相符的標頭**當成一筆紀錄**輸出——搭配 `-t` 時，那列標頭
會在輸出裡出現兩次，一次作為標頭、一次作為資料。csv2 讀得回來，但在把它接到別的地方之前，
這件事值得先知道。

這些位址沒有任何一個是動詞可以作用的，不論怎麼拼：`-get`、`-update` 與 `-delete -cell`
對 `0:`、`0a:`、`0b:` 都以同一句話拒絕，而那句話說的是「為什麼」，不是去挑剔一個 csv2
自己印出來的位址的形狀。由 T132 與 T186 斷言。

中間那一欄是該欄位**在你所要求的語言下**的名稱，而不是「命中的那一列標頭」的名稱。這正是
第二行寫著 `note` 而旁邊的值是中文的原因：命中的是 `0b` 那一列，但這份報告並沒有被要求用
中文名稱。`--zh` 只改變名稱，不改變其他任何東西。由 T66 斷言。

**那個 `cut -f3` 沒有 `-d`，而少掉的正是重點。** 它切的是 TAB，因為定位報告是 TAB 分隔、
值有跳脫的。不要對 `--filter` 或 `-mid` 的輸出動用 `cut`：那是 CSV，值裡可能有逗號，而
`cut -d, -f3` 會交給你其中一段碎片——靜默地，以 0 結束。在本專案自己的 fixture
（`test/fixtures/TARGET_PACKAGES.csv`）上，對第一筆資料列下 `cut -d, -f3` 得到 7 個位元組，
而 `-get 1:6` 得到的那一格是 513 個位元組。那個失敗正是 csv2 存在的理由；從 csv2 自己的輸出
上再遇到它一次，會是個很差的笑話。這裡的數字到 2026-08-21 之前是「一個 515 位元組的儲存格
裡取回 104 位元組」，而且沒有指名 fixture——不可重現，出現在一段「不要相信看起來合理的碎片」
的文字裡。由 T65 斷言。

```console
$ csv2 -contains busybox --filter -i TARGET_PACKAGES.csv
busybox,fce9d7f35ea3 (submodule),896 KiB,fork raliclo/busybox branch develop,…
```

`--filter` 改為輸出命中的**紀錄**，形式為 CSV。要一併帶出標頭請加 `-t`——`-t` 在哪些
情況下不是選用的，見下方的「會被拒絕的組合」。

`-A`、`-B`、`-C` **隱含 `--filter`**：上下文紀錄沒有命中的儲存格，儲存格報告對它無話
可說。不相鄰的區塊之間以 `--` 分隔，與 grep 相同。

**「和 grep 一樣」指的是 `--` 分隔線，不是 grep 的 `-`／`:` 行標記。** grep 會把上下文行
與命中行標示成不同樣子；CSV 輸出做不到，因為在 CSV 列裡加標記就等於多一個欄位，而多一欄
的列是一筆壞掉的紀錄。因此加了 `-A`／`-B`／`-C` 之後，CSV 輸出是命中與上下文的混合，沒有
任何東西能區分它們——而 `-contains` 存在的目的正是給你 `record:field` 位址；若你需要位址，
就跑兩次：一次不帶上下文取得位址，一次帶上下文讀它周圍。

`--json` 沒有這個限制，因此它會標記，但只在有上下文時才標——沒有上下文時，送出的每一筆
都是命中，那個鍵會是個常數：

```console
$ csv2 -contains zstd -C 1 --json -i pkgs.csv
{"meta":{"format":"csv","headers":1,"fields":2}}
{"record":2,"line":3,"match":false,"fields":{"pkg":"zlib","ver":"2"}}
{"record":3,"line":4,"match":true,"fields":{"pkg":"zstd","ver":"3"}}
{"record":4,"line":5,"match":false,"fields":{"pkg":"ncurses","ver":"4"}}
{"meta":{"records":4,"matched":1}}
```

末行的 `matched` 是「計數」而不是「索引」：它告訴你有幾筆命中，而不是上面哪幾個物件是命中的。
那是 `match` 這個鍵的職責。由 T63 斷言。

```console
$ csv2 -contains busybox --json -i test/fixtures/TARGET_PACKAGES.csv
{"meta":{"format":"csv","headers":1,"fields":7}}
{"record":1,"field":1,"header_en":"pkg_name","value":"busybox","line":2}
{"record":1,"field":4,"header_en":"source","value":"fork raliclo/busybox …"}
{"meta":{"records":21,"matched":3}}
```

此處把路徑寫全，因為那些數字取決於它。母專案自己保有一份該檔案的工作複本，而它已經往前走了
——撰寫本文時是 22 筆——因此拿這個範例去跑那一份的讀者會得到不同的數字，而且無從知道範例
指的是哪一份。由 T113 斷言：這一段裡的筆數，每一次執行都會與 fixture 比對。

JSON Lines。**第一行**是 metadata，帶出 csv2「認為」自己正在讀的格式，讓呼叫端可以
斷言 `headers` 是否符合預期，而不是默默接受一個猜錯的解析。**最後一行**帶總數：它們
無法放進第一行，除非先讀完整份輸入才開始輸出，而那正是串流保證的反面。

**在 `.csv2` 上，每個物件會多帶一個鍵 `header_zh`**，內容是該欄在第二列標頭裡的名字——上面
那個範例是 `.csv`，只有五個鍵。`--en` 與 `--zh` 改變的是「定位報告」中間那一欄，在這裡什麼
也不改：`--json` 一律兩個名字都帶著，因為只要其中一個的消費端挑得出來，而想要另一個的那一端
沒辦法無中生有。

**不是合法 UTF-8 的值會被拒絕，而不是被替換。** JSON 是定義在文字之上的，那些位元組載不進去：
解碼器會在它們的位置放上 U+FFFD，而那一行仍然是合法的 JSON——那是一種「看起來與成功完全相同」
的資料遺失，而且發生在本文件「值本身才是重點」時所推薦的那個形狀上。`-get` 與各種 CSV 形狀交還的是位元組，
定位報告會把它們寫成 `<non-UTF-8: 63 61 66 e9>`。**`-md` 會換成 U+FFFD，而且什麼也不說**，
那是刻意的：它是一種算繪、不是一次來回，`--pretty` 甚至會照「被替換之後的寬度」去補欄寬。
不要從 `-md` 把一個值讀回來——T136 對 `<br>` 說的是同一句話。由 T158 與 T164 斷言。

**串流被中途切斷時，最後那一行不存在**——讀取端提早離開（結束狀態 141），或一次 `-so` 編輯
在已經吐出紀錄之後才失敗。那件事沒有帶內建標記：若那些總數對你有意義，請檢查「你收到的最後
一行是不是一個 meta 物件」，不要預設它是。

那兩個數字要精確理解。`records` 是**抵達的最大資料紀錄編號**，不是檔案裡有幾筆，也不是
解析了幾筆——在 21 筆的檔案上 `-mid 5,5` 會回報 5，因為它讀到那裡就停了。在會用到索引的
路徑上，這個差別很要緊：在一個 600,000 筆的檔案上，`-tail 1` 會在 seek、讀了幾 KB、只解析
一筆之後回報 `records:600000`。它是「到達的位置」——而那正是它能回答「我要的視窗存不存在」、
卻不能回答「做了多少工」的原因。`matched` 數的是命中的**紀錄**數，而兩個
metadata 之間的每一行對應一個命中的**儲存格**——因此只要有紀錄在多欄命中，兩個數字就
不一樣。

「選取」而非「搜尋」時輸出的是另一種物件，每筆一個：

```console
$ csv2 -mid 5,5 --json -i TARGET_PACKAGES.csv
{"meta":{"format":"csv","headers":1,"fields":7}}
{"record":5,"line":6,"fields":{"pkg_name":"zlib (libzlib)","version":"1.3.2…",…}}
{"meta":{"records":5,"matched":0}}
```

`fields` 以欄名為鍵，那是「不必數欄位就能取出某一欄」的方式——而基於同樣的理由，**標頭中有
兩個同名欄位的紀錄無法以這種形狀輸出**：一個 JSON 物件無法在同一個鍵下放兩個值，而實際
使用中的每一個解析器都會留下最後一個、丟掉第一個。csv2 選擇拒絕，而不是輸出一行「被解析
之後就會遺失資料」的內容。請不加 `--json` 讀取，或改用 `-contains --json`——它的報告形狀
讓每一個命中各自成行，不受影響。由 T75 斷言。

`-md` 產生 Markdown 表格，且是單向的——csv2 無法把它讀回來。用 `-o` 寫進 `.csv`／`.csv2`
路徑會被拒；若你以 `-so` 加 shell 重導繞過那條拒絕，讀回來時同樣會被拒：一個「單欄、且其中
一筆是 Markdown 分隔列」的檔案是 `-md` 的輸出而不是 CSV，而訊息會直說這件事，不會拿欄數
來搪塞。由 T74 斷言。

### 在管線裡

`-si` 與 `-so` 和每一個動詞都能組合；管線沒有任何特別之處，只差在 stdin 沒有副檔名，
因此必須由 `--headers` 說明格式：

```console
$ cat packages.csv | csv2 -si --headers 1 -contains busybox --filter -so
busybox,1.37.0,"fork raliclo/busybox, branch develop",GPL-2.0
```

**它確實是串流的，但 stdout 以 64 KiB 為單位緩衝，不是逐行。**「不緩衝整個檔案」講的是
記憶體，而那句為真：在持續湧入的串流上，第一批輸出立刻就出現，記憶體也保持平坦。但只要
輸出不足 64 KiB，就要等到整個執行結束才會出現——因此把 csv2 接進一個你正在盯著看的東西，
看起來會像是卡住了，實際上只是還沒有東西可以 flush。若你需要「每產生一筆就拿到一筆」，
你需要的是一支逐行緩衝的工具；csv2 是為管線中的吞吐量而寫的，不是為互動式即時觀看。
這是量出來的、不是假設的：輸出 8000 筆時，第一批位元組在 0.01 秒抵達而輸入持續 3 秒；
輸出 2000 筆時，直到結束前什麼都沒有。由 T61 斷言。

### 結束狀態

成功為 `0`，任何錯誤為非零。**在 `-o` 與 `--in-place` 上，csv2 不會「部分成功」**：輸出寫的
是暫存檔，一切都成功之後才 rename，因此一次失敗的執行不會在目的地留下任何東西。

**`-so` 是例外，而且不是小的例外。** 一條串流收不回來。一個「位址其實在結尾之後」的編輯，
要到讀完檔案才會發現，而在那之前，它前面那些紀錄早就寫到 stdout 了：實測，一次會失敗的
`-update` 在 19.5 MB 的檔案上寫出了 198,349 筆有效紀錄才以 1 結束；同一個指令在 12 KB 的
檔案上一筆也沒寫，因為一切都還留在緩衝區裡。所以一次以非零結束的 `-so` 執行**可能已經產生
輸出**，而產生了多少取決於檔案大小。若這件事要緊，請寫到 `-o`，再自己把檔案搬過去。

**有一個結束狀態兩者皆非，而管線會不斷遇到它：141。** 當 `-so` 的下游先離開時——`| head -1`、
或任何提早停止的讀取端——csv2 死於 `SIGPIPE`，以 `128 + 13 = 141` 結束。它不印任何東西、
不留下任何東西，也不會先把輸入讀完：在一條 400 MB 的串流上，`| head -1` 是 0.04 秒，而
`| wc -c` 是 9.7 秒。那是正確的 Unix 行為，**不是 csv2 的錯誤**——因此**一個把「非零」一律
當成「csv2 失敗了」的呼叫端，會把一個完全正常的 `| head` 誤報成錯誤**。若你的腳本在意這件事，
請明確檢查 141——但要注意 141 是「輸出大小」的性質，不是「指令」的性質：同一條管線在小檔案
上會給 0（因為全部塞得進 64 KiB 緩衝區、在讀取端離開之前就寫完了），在大檔案上才給 141。

**141 只表示那一件事；因為其他任何理由而失敗的寫入，都是錯誤。** `-so` 遇到磁碟寫滿時
過去同樣會給 141，stderr 上一個字也沒有，磁碟上留著寫到一半的檔案——與上述那個無害的情況
分不出來，而且正好落在本節叫你不必理會的那個狀態上。現在，因為目的地已滿、描述子已關閉、
或裝置出錯而失敗的寫入，會以 `1` 結束，並以慣常的兩行指出是哪一個目的地。由 T131 斷言；
磁碟寫滿的重現步驟在 `todo/known-defects.md`（DV）。

**每一種拒絕都以 `1` 結束，而且沒有別的東西可以用來分辨它們。** 實測 28 種不同的拒絕：
每一次都是結束狀態 `1`、每一次都是恰好兩行 stderr、stdout 什麼都沒有、沒有錯誤碼、沒有
分類記號、沒有穩定的文法。**那個「兩行」是「不帶 `-debug`」時的行數。** 一個「在參數解析
之後才被發現」的拒絕，會排在 `-debug` 已經印出的那些之後，因此
`csv2 -update 99:1 X -i f.csv -so -debug` 的 stderr 是三行，執行得越久越多。`metrics:`
是唯一一行「拒絕永遠不會印」的，因為它屬於「真的做了事」的執行。若你的腳本會去數那兩行，
就不要餵它 `-debug`。一個必須對不同拒絕做不同反應的腳本，只能去比對
英文散文，而今天沒有任何受支援的替代做法。此處明說而非暗示，是因為假設有別的辦法的讀者
還是會把比對寫下去，然後在很久以後才發現。

**被訊號結束時，結束狀態是 `128 + signo`，不是 `1`。** 排程器送來的 `SIGTERM` 是 143、
`SIGINT` 是 130、`SIGKILL` 是 137——八種訊號實測。那些不是 csv2 的「拒絕」，也沒有在說
那個檔案怎麼了：在那八種情況下，檔案都是完好的。一個把「不是 0、也不是 141」當成
「csv2 拒絕了我的輸入」的腳本，會把一次排程逾時誤讀成拒絕——正如本節警告過它會誤讀
一個 `head` 那樣。

**一個什麼都沒找到的搜尋，以 `0` 結束。** `-contains` 回報的是它找到了什麼；沒找到不是錯誤。
因此 `if csv2 -contains X -i f.csv` 不是「存在性」的判斷——兩種情況它都成功。要問那個問題，
請讀 `--json` 結尾那行 meta 的 `matched`：

```sh
set -o pipefail
n=$(csv2 -contains -- "$needle" --json -i f.csv | tail -1 |
    sed -n 's/.*"matched":\([0-9]*\).*/\1/p')
[ "${n:-0}" -gt 0 ] || { echo "not found" >&2; exit 1; }
```

用 `tail -1` 是因為那行 meta 在最後；用 `pipefail` 是因為沒有它時，一次拒絕會以 0 穿過管線、
而 `n` 是空的——那讀起來就是「沒找到」。命中標頭不算在這裡（見 `--include-headers`）。
這個做法在兩處被指定、卻到 2026-08-22 之前一次也沒有被示範過，而這份文件為了「不分大小寫比對」
寫出了一整段 Python。

**兩個行程同時編輯同一個檔案：最後完成的那個全贏，而且是靜默的。** 兩邊都以 0 結束、兩邊都
寫下一筆「自己成功了」的稽核紀錄，而其中一個編輯不在檔案裡。在一個 2,000 筆的檔案上，以兩個
並行的 `-update --in-place` 實測，3 次有 3 次如此。csv2 不加鎖，而它裡面沒有任何東西會告訴你
這件事發生了——`-log` 的每一筆對「它自己那個行程」都是真的，而整份軌跡對「那個檔案」是錯的。
**如果有兩個寫入者可能碰到同一個檔案，請自己把它們排成序列。**

**「兩個行程同時追加」是唯一不屬於「弄丟一次編輯」的情況。** `-append --in-place` 不會重寫
檔案，因此沒有暫存檔、也沒有 rename：它把位元組寫到檔尾。那次寫入走的是一個以 `O_APPEND`
開啟的描述子，核心會把「找到檔尾」與「寫在那裡」合成一個動作——於是兩個並行的追加都會完整
落地，誰也蓋不到誰。「後完成的那一個」會發現（檔案長大的量比自己寫的多）並以 `WARN` 說出來——先完成的那一個
去看的時候，只看得到自己那一次寫入、看不到別的，這正是為什麼只會出現一則警告而不是兩則。
那份索引誰也更新不了：各自算出來的偏移量已經不是紀錄真正的所在。sidecar 會被原封不動地留著，
下一次讀取會把它當成過期的丟棄。

到 2026-08-22 之前，那次寫入是「seek 到算出來的檔尾，再做一次普通的 write」——而那完全是
另一回事。兩個追加競賽時於是寫在同一個偏移量上，較短的那次蓋在較長的那次上面，留下被蓋掉
那一列的一個碎片：有時是一個裸換行，於是 csv2 自己的空白行規則拒絕了一個 csv2 剛剛寫出來的
檔案；有時是一筆**格式完整、卻沒有任何人追加過**的紀錄，它以 rc=0 被讀回來，而沒有任何地方
會說一句話。`-log` 檔案早就為了同一個理由搬離了那個構造——就在隔壁一個原始檔裡。

**讀取端永遠不會看到一個寫到一半的檔案——前提是寫入者是 csv2，而那次編輯不是追加。** 輸出寫的是暫存檔，再
rename 到位，而 rename 是不可分割的，因此並行的讀取者拿到的要嘛是完整的舊檔、要嘛是完整的
新檔，絕不會是兩者的混合——即使寫入者正做到一半。那是一個可以拿來建構東西的承諾，不是實作
細節：暫存檔加 rename 存在的理由就是它。

**它的代價是磁碟：峰值用量是檔案的兩倍。** 暫存檔會長到「完成後的輸出」那麼大，而原檔還在
那裡，因此改寫一個 1 GiB 檔案裡的一格需要 1 GiB 的可用空間，而不是那次編輯改動的那幾個
位元組。後文那個「寫入放大」的數字算的是**寫出的位元組**；這裡說的是「必須同時存在」的空間。
中途 ENOSPC 會讓原檔完好無損並回報失敗——那是這個承諾在生效，不是它失效。

**那個承諾屬於「寫入者」，不屬於 csv2 的讀取端**，而本文件會把你送去用別的寫入者——`iconv`、
`tr`、一個 shell 的重導向。以一個普通的 `cat > file` 與一次讀取相競，實測 30 次：12 次安靜地
截斷、18 次大聲報錯，一次完整的都沒有。**那兩者的比例不是 csv2 的性質**：它取決於讀取端的
EOF 剛好落在離紀錄邊界多遠的地方，因此後來一個回合在它自己的 fixture 上量到的是 5 與 25。
會重現的是「一次完整的都沒有」。csv2 偵測不到安靜的那一種：一個在紀錄邊界被切斷的
檔案，是一個「比較短的檔案」，不是一個格式錯誤的檔案，而**csv2 印出來的任何數字都不能告訴你
一次讀取是完整的**——`records` 回報的是它讀到哪裡，而那正是會錯的那個數字。若某個檔案正被
「不是 csv2 的東西」改寫，請自己 rename 到位，不要直接覆蓋著寫。

**`--in-place` 同樣成立，而且在那裡更要緊：** 失敗的就地編輯會讓原檔**逐位元原封不動**，
旁邊也不會留下暫存檔——包括執行中途被 `SIGINT`、`SIGTERM` 或 `SIGHUP` 殺死時，以及每一個
其他「可攔截且會結束執行」的訊號：`SIGQUIT`、`SIGXFSZ`、`SIGALRM`、`SIGUSR1`、`SIGUSR2` 等等。**「等等」是字面意義**：處理常式是對「每一個可攔截且會結束執行的訊號」安裝的，不是對一份由誰維護的清單安裝的，因此沒有被列名的訊號，行為與被列名的那些相同。那份
清單一開始只有三個，而一個盲測回合發現其餘每一個都會留下一個好幾 MB 的隱藏檔；`SIGXFSZ`
正是 `ulimit -f` 或檔案系統配額會產生的那一個，一點也不罕見（T131e、T131f）。`SIGKILL` 與斷電攔不下來，會留下一個，
它的名字是 `.<檔名>.csv2tmp.<pid>`，可以安心刪除。有一個值得知道的後果：rename 會重新建立
目的地，因此**在一次編輯進行中刪掉那個檔案，它會回來**——`rm` 落在舊的 inode 上，而 rename
把新的那一個放回那個名字上。這是唯一沒有退路的一條保證——用 `-o` 時輸出錯了你手上還有輸入，
而用 `--in-place` 時輸入「就是」輸出。由 T28c 斷言。

**多個位址，一次執行。** `-update` 是可重複的，而一次執行裡的每一個位址都是對「檔案到達時
的樣子」解析的，因此 N 次編輯要嘛全部落地、要嘛一個都不落地。「每個位址跑一次 csv2」的迴圈
不是那樣：第四次失敗時，前三次已經寫進去了，rc=1，而從檔案上看不出哪些發生過。`-insert`
也是如此，那正是它的編號被記載為「對輸入解析」的原因。

```sh
csv2 -update 3:6 A -update 12:6 B -update 40:6 C -i f.csv --in-place   # 不可分割
```

**在一次無法還原的編輯之前，`-so` 就是一次乾跑。** 它把那次編輯「會產生什麼」寫到 stdout、
什麼也不動，而且會與真正執行時一模一樣地拒絕越界的位址——因此
`csv2 -update 12:6 X -i f.csv -so | head` 能在 `--in-place` 回答「做了什麼」之前，
先回答「將會做什麼」。

**那句話講的是「輸入」，而 `-o` 對「目的地」什麼也沒承諾：目的地原本若已有檔案，它會被覆寫，
沒有任何提示，rc=0。** 沒有旗標可以防它——shell 的 `>` 也是這樣，而 csv2 不打算與它不同——
因此那道防線是你的：寫到一個新名字，或事先檢查。有一個盲測回合就是這樣弄丟了一個檔案，
而它當時把 `-o` 當成「比 `--in-place` 安全的那一個」——如果只讀到上面那句話的「安全」二字，
讀起來確實就是那樣。

**一次編輯會重寫每一個紀錄分隔符，包括它沒有碰過的那些。** 輸出在每個平台上都用 `\n`，
因此編輯一個 CRLF 檔案裡的一格，回來的是一個 LF 檔案——欄位逐位元相同，而檔案不同。
每一種「對整個檔案」的驗證慣用法（檢查碼、`diff`、「我沒指名的紀錄應該沒變」）在 CRLF 輸入上
都是錯的；請改比對「值」，用 `--json` 或 `-get`。`-append --in-place` 是那個反證：它寫在檔尾、
並配合檔案「已經是的」行尾，因為它不重寫其餘部分。

**「暫存檔 + rename」是有代價的，而代價落在 symlink 與權限上。** rename 取代的是一個
「名字」，因此寫到一個 symlink 自身的路徑上，會把連結換成一般檔案、目標動也沒動——而
shell 的 `>` 是會寫穿過去的。因此 `-o` 與 `--in-place` 都會先解析目的地：連結繼續指向
原處，被寫入的是它指向的那個檔案。原檔的權限位元會在 rename 之前套到暫存檔上，因此一次
編輯不會改變「誰讀得到它」——而那個暫存檔一開始就是以 0600 建立的，因此在它被寫入的期間，
別人也讀不到。2026-08-21 之前它在那段時間裡是 0644，而在大檔案上那是一個以秒計的時間窗。
由 T129、T130 與 T161 斷言。

**當 `-o` 指的是一個「還不存在」的路徑時，就沒有「原本那個檔案」**，於是沒有東西可以被帶過去，
那個檔案會保留暫存檔的模式：**0600**，不是你的 umask。在 `umask 022` 之下，
`csv2 -r -t -i pkgs.csv -o new.csv` 產生的是 `-rw-------`；而寫到一個已存在的 0644 檔案上，
產生的是 `-rw-r--r--`。預設是安全的那一邊，而在把那個檔案交給另一個使用者的管線之前，
這件事值得先知道。

**在診斷訊息裡，「輸入」路徑照你打的樣子印，「輸出」路徑印解析過的那一個。**
`cannot open input file: ./nope.csv` 會保留那個 `./`；`-o` 的拒絕在目的地被解析之後，印的是
絕對路徑，而 `--in-place` 印的是解析過的——macOS 上 `/private/tmp/x` 會變回 `/tmp/x`——因為 `--in-place`
解析的是目的地、不是來源。因此一條「引用了你的 `-i` 參數」的拒絕，即使這次是 `--in-place`，
印出來的仍然是你打的那個。這件事有影響：分辨不同的拒絕只能靠比對英文字句。
**例外是「一個因為不存在而無從解析的目的地」**：`-o nodir/out.csv` 印的是
`the directory nodir does not exist`，照你打的樣子——因為沒有東西可以拿來解析。
這一段到 2026-08-21 之前，兩半都寫反了；到 2026-08-22 之前，它沒有那個例外。
每一版都是從眼前的那幾個例子寫出來的。

不會被保留的有三件，而三件都是刻意的：**硬連結**會被斷開，因為 rename 沒有別的做法；
**擴充屬性（xattr）**會遺失，因為暫存檔是一個新檔案，沒有任何東西把它們複製過去；
**唯讀檔案**若位在可寫目錄中仍會被取代，因為 rename 要的是「目錄」的權限，它從來不看那個
檔案。還原模式擋住的是「一次編輯悄悄放寬誰讀得到」，那才是會把資料交給別人的那一半；而
拒絕寫入一個唯讀檔案，等於讓 csv2 對你的目錄權限有意見，那不是它的事。

`--build-index` 與 `--verify-index` 會印到 **stdout**——它們是明確的管理動作、不屬於正常
路徑，但若你把它們接進管線，那些行就在你的串流裡。`--build-index` 印一行；`--verify-index`
成功時印一行，不符時**每一項不成立的宣稱印一行**——那可能比「每個格點一行」更多：一個格點的
偏移量與行號都錯時，它會印兩行。實際上，一次編輯常常把兩者移動同樣的量，於是只有偏移量會被
回報：把一筆紀錄切成兩筆，會讓其後每一筆的「編號」加一、也讓每一行的「行號」加一，於是每個
格點所指的行號仍然對得上，只有位元組那一項會觸發。「一個格點兩行」是**一份被竄改的 sidecar**
會產生的樣子，而不是「一個被改動的檔案」通常會產生的樣子。一份「整體
位移了」的大索引可以印出好幾千行。兩者都不能與動詞併用——那個旗標是取代該操作，因此同時
給出時會被拒絕，而不是把動詞靜默丟掉（T160）。

錯誤訊息走 stderr，恰好**兩行**（英文一行、中文一行）——以與 log 相同的「整行」規則跳脫，而那
正是「兩行」這個數字可靠的原因，**而那條規則涵蓋每一個控制字元**：換行、TAB、CR 分別是
`\n`、`\t`、`\r`，其餘 0x20 以下與 DEL 一律是 `\xNN`。2026-08-21 之前它只涵蓋換行與 CR，
於是 `no column named "<ESC>[2K…"` 會把一段「活的」擦行序列放在承載診斷的那一行上——而那正是
本文件在一個螢幕之外、為「定位報告要跳脫」所給的理由。行數的承諾一直守著，規則沒有。

**反斜線刻意不由那條規則處理**，因為一則在教 `\n` 的訊息必須讀作 `\n`——`undefined escape
sequence \q` 是一句話，不是一個值。被插進訊息裡的「值」，會在插值的那一點被完整跳脫、連反斜線
一起，因此 `no column named "…"` 分得出一個字面叫做 `na\nme` 的欄位與一個名字裡含換行的欄位。
引述「路徑」的訊息會保留它的**反斜線**——Windows 的路徑滿是反斜線，把它們加倍會把檔案叫錯
名字——而它裡面其餘的東西，與其他每一行一樣會被跳脫：一個名字裡含換行的檔案，會以
`no\nsuch.csv` 出現，含 ESC 的會是 `x\x1B[2Ky.csv`。那正是「一次拒絕是兩行、一筆 log 是一行」
得以成立的原因。這也表示：訊息裡的路徑，不一定就是你可以拿去 `open` 的那個字串。
這句話到 2026-08-22 之前寫的是「路徑不動」——那是從它當初為之而寫的那個反斜線推出來的全稱。
一則引述了含換行輸入值的訊息，過去會印出四行，而依這兩行去讀的
腳本會把被注入的那一行當成錯誤訊息的一部分。由 T102 斷言。給了 `-log FILE` 時，同一個失敗
會另外帶時間戳追加到該檔；沒給則不會再印任何東西。正常路徑上完全不輸出任何訊息——它必須
能放進管線。

**有一種東西不需要 `-debug` 也會印，而那是刻意的**：一行 `WARN`，出現在「這次執行成功了，
但它做的事幾乎確定不是呼叫端的本意」時——例如起點超過檔案結尾的 `-mid` 視窗，或一個超過
1 MiB、將被完整寫進 log 的值、`--truncate-partial` 指出它丟掉了多少位元組、一份寫不出去的
索引 sidecar、**一個寫不出去的 `-log` 檔案**，以及**在一次 `-append --in-place` 期間，有另一個
行程也追加到同一個檔案**。**它是一張清單，不是一條原則**——就這六種，沒有別的。最後那一種到 2026-08-21 之前都不在這張清單上，而它是這張清單最不能漏掉的一個：
呼叫端要的是一份稽核軌跡，那次執行以 0 結束，沒有任何 log 檔存在，而全部的通知就是 stderr 上
一行英文。原本它是先給一條原則
（「執行成功了，但做的事幾乎可以確定不是呼叫端想要的」）再接那張清單，而讀者無法從那段文字
判斷自己拿到的是哪一種承諾：那條原則涵蓋了清單沒有涵蓋的一個情況，而那個情況會毀掉資料。
WARN 是預設門檻。與錯誤不同，它是**一行，而且只有英文**，
這個工具裡每一則診斷都是如此；「兩行雙語」那個形狀屬於「結束一次執行」的那則訊息。
結束狀態仍然是 0，因為那次執行做了它被告知的事。

**訊息帶多少位置資訊，取決於實際上有多少可帶。** 不要寫一支「預期每則訊息裡都找得到
`record N, field M`」的腳本：

| 錯誤發生在 | 訊息會指出 | 範例 |
|---|---|---|
| 某一格 | `record N (line L), field M` | `record 1 (line 3), field 2: undefined escape sequence \q; .csv2 defines only \n, \r and \\` |
| 某一筆，但不屬於單一欄位 | `record N` | `record 1 (line 2) has 2 fields but the header has 3` |
| 參數 | 兩者都不指出——它在讀到任何一筆之前就被丟出 | `unknown flag --nope` |
| 整個檔案 | 兩者都不指出——沒有紀錄可指 | `cannot open input file: /nope.csv` |

只有「錯在某一格」的情況會兩者都指出。其餘只指出紀錄，或什麼都不指——因為再沒有別的為真的
東西可指。由 T60 斷言。

**錯誤裡的紀錄號是一個「可以拿來用」的位址。** 直接把它餵回 `-get` 或 `-update`：一則寫著
`record 1 (line 3), field 2` 的訊息，就是 `csv2 -get 1:2`。它數的是資料紀錄，因此與這支工具
其他地方一致；行號會一併給出，因為那是文字編輯器要的東西。標頭列裡的錯誤改說
`header row 0a` 或 `0b`，因為標頭列沒有紀錄號可給。由 T93 斷言。

**但「能不能拿它去動」取決於那是什麼錯誤。** 上面那個範例是**解析錯誤**，而一個 csv2 解析
不了的檔案，任何動詞都不會碰——對它下 `-get 1:2` 回來的是同一個錯誤，不是那一格。那是對的：
另一個選擇是「對一個形狀未知的檔案動手」。請先修好位址所指的那一格，再去定址它。至於不是
解析失敗的那些錯誤——越界的 `-update`、被拒絕的旗標組合——檔案讀得了，位址當場就能用。

**參數**本身的錯誤是在 `-log` 被讀到之前就丟出的，因此它會到 stderr 但不會進 log 檔：
要寫進哪個 log，正來自那批解析失敗的參數。

### 會被拒絕的組合，以及為什麼

「拒絕」正是這支工具的重點，所以在此列出，而不是留給人自己撞到。以下每一項都會以
非零結束，並說明原因。**右邊那一欄是「理由」，不是「訊息」**：csv2 實際印出來的往往更短，
而且會指名它看到的那個引數。請以結束狀態去比對、把訊息讀出來，不要拿訊息去比對這張表。

**這張表列的是「值得一提的拒絕」，不是「全部的拒絕」。** 它存在的目的，是那些「否則要靠撞到才
知道」的組合；它不列一般的引數錯誤（`-get: expected r:c, got "x"`、`--headers takes 1 or 2`、
讀不到的 `-i`、目錄不存在或不可寫的 `-o`），也不列那些寫在別處散文裡的：重複的旗標、
`--headers` 與副檔名不符、沒有副檔名的檔案、對已標記欄位的兩個方向的重複遮蔽、
`0:`／`0a:`／`0b:` 定址、COLS 的四條拒絕、`--verify-index` 或 `--build-index` 搭配動詞，
以及環境變數的上限。2026 年 8 月有一個回合把這張表當成一份「封閉的合約」來測，找到九條它沒有
提到的拒絕；修法是在這裡說清楚，而不是把這張表養成一份沒有人會讀的東西。

| 組合 | 為什麼被拒絕 |
|---|---|
| `-head 3 -o out.csv2`（未給 `-t`，且讀的是 `.csv2`） | 把不帶標頭的資料列寫進一個「副檔名承諾了標頭」的路徑；下次讀取會把最前面的紀錄當成標頭吃掉。**這條適用於選取，不適用於編輯**——見下。若讀的是 `.csv` 而寫的是 `.csv2`，無論你加什麼旗標，先觸發的都是另一條拒絕：csv2 不做兩種格式之間的轉換 |
| `-md` 未給 `-t` | 沒有標頭列就渲染不出 Markdown 表格；自動補上會讓「預設不帶標頭」出現一個看不見的例外 |
| `-md -o out.csv2` | 副檔名宣告的是 CSV，內容卻是 Markdown。要抵達這一條，輸入必須是 `.csv2`：從一個 `.csv` 出發時，無論加什麼旗標，先觸發的都是第一列那條「格式轉換」的拒絕 |
| `-si` 未給 `--headers 1` 或 `2` | stdin 沒有副檔名，格式未被宣告；此處的預設值就是猜測 |
| `-head` 與 `-tail` 併用 | 兩者沒有一個明顯正確的合併讀法 |
| `-mid 7,3` | `a > b`；不替你對調，因為範圍寫反通常表示別處的邏輯也反了 |
| `-i x -o x` 未給 `--in-place`（無論兩者怎麼拼——也無論那個檔案有幾個名字） | 那就是一次就地編輯，而 `--in-place` 還會讓 symlink 繼續指向原處、並保留權限。「拼法」涵蓋 `./x`、`../d/x`、絕對路徑與 symlink；而硬連結不是一種拼法，因此也會比對該檔案的 (device, inode)。**僅限 POSIX**：Windows 的 CRT 對每個檔案都回報 inode 0，在那裡做這個比對，答案會是「每個檔案都是彼此」 |
| `-delete 12:6` | 那是儲存格位址；請加 `-cell`，或改給紀錄號 |
| `-delete -cell -col 3` | 兩者是相反的：`-cell` 清空一格並保留該欄，`-col` 則移除整欄 |
| `-delete -col` 移除全部欄位 | 沒有任何欄位的檔案不是 CSV 檔 |
| `-delete -col X` 同時對 X 下 `-update`／`-delete -cell`／`-encrypt`／`-hash` | 該編輯不會有效果，卻仍會被回報為已完成 |
| `-delete -col` 與 `-insert`／`-append` 併用 | 那列字面值必須符合舊形狀或新形狀其中之一，而無法判斷是哪一個 |
| `--a1` 或 `--physical` 而沒有定位報告 | 它們是在報告的位址上「加一段」，而 `-r`／`--filter`／`-md`／`--json` 不產生位址，沒有東西可加 |
| `-insert -cell` | 在一列中間插入儲存格，會把該列後面的欄位全部往後推一格 |
| 在 21 筆的檔案上 `-update 99:3` | 越界是錯誤，絕不是「自動長大」 |
| 在 7 欄的檔案上 `-append 'a,b,c'` | 欄數必須與標頭相符；csv2 不會補空或截斷來湊合 |
| `-o` 指向 `-keyfile` 或 `-log` 檔；`-log` 指向輸入；`-keyfile` 就是一次 `--in-place` 執行的輸入 | 那道「守住 -i 與 -o」的同檔案比對，拿去問「這次執行會碰到的其他檔案」。這幾種原本都以 0 結束、兩條輸出流皆空，而且各自毀掉了一樣東西：唯一能解開剛剛被寫出的那些密文的金鑰、正在寫入的那次執行自己的稽核軌跡，或是輸入本身——csv2 會把呼叫紀錄追加進它正在讀的那個檔案，於是它從此過不了自己的欄數檢查 |
| 用 `--in-place` 做一次「選取」 | `-head`、`-tail`、`-mid`、`-contains`，以及單獨的 `-r`，全都是選取；`--in-place` 是「編輯」要去的地方。把一個選取寫回它自己的輸入，會丟掉它沒有指名的每一筆紀錄，而 2026-08-21 之前它就是這樣做的：rc=0、什麼都沒說、log 裡也沒有。要裁切請用 `-o NEW.csv` |
| `-insert N ROW` 的欄數與標頭不符 | 與 `-append` 是同一道檢查，而且兩邊的數字都會說出來：`-insert 2 has 2 fields but the header has 4`。2026-08-21 之前它不在這張表裡，而一張自稱完整的表，會被當成完整的來讀 |
| `-encrypt` 未給 `-keyfile` 且沒有 tty | 無法顯示的提示絕不視為「是」 |
| 編輯時沒有給 `-o`、`-so` 或 `--in-place` | `-insert`/`-append`/`-delete`/`-update` 需要明確的目的地；沒有「隱含就地編輯」這回事 |
| `-o /dev/stdout` | 輸出會先寫到目標旁的暫存檔再 rename，那需要一個一般檔案。請改用 `-so` |
| 對「檔案標記為 `:enc:`、`:hmac:` 或 `:hash`」的欄位下 `-update`／`-delete -cell` | 寫進去的原始值讀不回來，而對加密欄位而言 `-decrypt` 會停在那一格——於是該次編輯從未碰過的紀錄也一起失去 |
| `-insert`／`-append` 到含有這種欄位的檔案 | 那一列的每一欄都是原始值，包括那一欄，而**你給得出的值沒有一個會是對的**：轉換需要金鑰，而標頭裡只有它的指紋 |
| 對「最後一筆不完整」的檔案 `-append` | 結尾紀錄欄數不足，或因未閉合引號而未收尾。`-o` 與 `--in-place` 一視同仁——快路徑過去會跳過這項檢查，產生一個 csv2 接著就拒讀的檔案 |
| `-append` 搭配 `--truncate-partial` | 追加只會加上位元組、移除不了那筆不完整的紀錄，因此檔案會同時保留它、並在其後多出一筆完整的。請先寫出一份乾淨的複本：`csv2 -r -t --truncate-partial -i f.csv -o clean.csv` |
| 不是合法 UTF-8 的值、row 或搜尋字串 | Swift 以「替代字元補上」的方式解碼 `argv`，那些位元組在抵達之前就沒了；把送進來的東西存起來，等於靜默地用 U+FFFD 頂替一個位元組。請把值放進檔案——位元組在那裡活得下來，而那正是 round-trip 保證所指的事。**COLS 清單也不檢查**——`-hash`、`-encrypt`、`-decrypt` 與 `-delete -col` 收的是「欄名」，那裡的一個非法位元組會比對不到任何欄位，並被回報成 `no column named "caf<U+FFFD>"`：那次執行同樣被拒絕，而且什麼也沒有被存下來。**路徑不檢查**：在 Linux 上路徑本來就可以是任意位元組，而 csv2 是把路徑交給檔案系統，不是把它當成資料儲存 |
| 未知旗標 | 絕不被當成別的東西吞掉 |

### 每一個編輯索引都指向輸入，而 `-insert` 讓這件事看得見

`-insert`、`-delete`、`-update` 與 `-delete -cell` 在一次執行裡都可以給不只一次，而
**每一個索引都是對「檔案送達時的樣子」計數**。所有編輯先收集完、再一次套用，因此先前的
插入不會推移後面那一個的目標。

那是唯一能讓「一批」可預測的語意，而它同時也是「同樣三個數字，分組方式不同就代表兩件事」
的原因：

```console
$ csv2 -insert 2 A -insert 4 B -insert 5 C -i f.csv --in-place   # 一次跑
r1  A  r2  r3  B  r4  C  r5

$ csv2 -insert 2 A -i f.csv --in-place                            # 分三次跑
$ csv2 -insert 4 B -i f.csv --in-place
$ csv2 -insert 5 C -i f.csv --in-place
r1  A  r2  B  C  r3  r4  r5
```

兩者都是 rc=0。**兩者都不算錯**——每一次執行的索引，對「它拿到的那個檔案」都是正確的——
但只有第一個是「一批」。**請決定你要哪一種，不要用試的發現。** 若你要那幾列落在**最終**的
第 2、4、6 位，以輸入為基準的數字是 2、3、4。

兩個容易踩到、因此值得寫明的後果：

- **範圍同樣是對「輸入」檢查的，而合法範圍是 `1..N`。** `-insert` 是把一列放在第 N 筆
  「之前」，因此在一個五筆的檔案上，最後一個合法位置是 5，而 `-insert 6` 會被拒絕——批次
  裡如此，單獨執行也如此。**`-insert` 無法定址到檔案的結尾，那是 `-append` 的用途。**
  本條的舊版本說 `-insert 6` 在「三次分開執行中的第三次」是合法的，「因為那時檔案真的有
  第六個位置可放」。那個預測成立——到那時檔案已有七筆，6 落在內部——但那個理由不成立：
  一個五筆的檔案有五個插入位置，不是六個。
- **同一個 N 的兩次插入，保持你寫下的順序**，而 `-insert` 可以與 `-append` 在同一次執行裡併用。

由 T27 斷言。

### `-t` 管的是選取，從不管編輯

選取產生的是**片段**，因此「標頭要不要跟著出去」是一個問題，由 `-t` 回答。編輯產生的是
一個**檔案**，因此那不是問題：標頭一律寫出，給不給 `-t` 都一樣；寫到 `.csv2` 目的地時
兩列都寫。

```console
$ csv2 -head 1 -i pkgs.csv2 -o sel.csv2
csv2: /home/you/work/sel.csv2 declares a format with a header, so writing data rows there needs -t; without it the next read would take the first record(s) as the header
csv2：sel.csv2 的副檔名宣告了帶標頭的格式，因此在此寫入資料列必須給 -t；否則下次讀取會把最前面的紀錄當成標頭
$ echo $?
1

$ csv2 -update 1:note X -i pkgs.csv2 -o edited.csv2   # 沒給 -t，也沒有被拒
$ head -2 edited.csv2
pkg,ver,note
套件,版本,備註
```

這個不對稱正是重點。拒絕編輯，會讓人根本無法在不記得某個旗標的情況下編輯 `.csv2`——
而那個旗標一旦漏掉，唯一可能的產物就是一個壞掉的檔案；接受選取，產生的就正好是那個壞掉的
檔案。由 T59 斷言。

### 遮蔽欄位：使用 `-hash` 之前請先讀這一段

`-hash` 是**確定性**的——那正是選它而不選 `-encrypt` 的全部理由。相等的值產生相等的
摘要，因此你仍然分得出哪些列原本的值相同。`-encrypt` 每格用新的 nonce，相同的明文會
得到不同的密文，那個能力就沒有了。

確定性是有代價的，而且代價不小：

> **沒有金鑰的 `-hash` 就是該值無鹽的純 SHA-256。** 對於可能值很少的欄位——
> `license`、`status`、`category`、國碼——任何拿到雜湊後檔案的人，只要把一份詞表
> 拿去雜湊，就能把該欄直接讀回來。

這不是假設。一次對本工具的盲測，**僅憑雜湊後的輸出**、沒有原始檔、只用一份 SPDX
識別碼清單，就還原了範例檔中 21 個 license 裡的 3 個。

**給 `-keyfile`，它就變成 HMAC-SHA256。** 仍然是確定性的，相等的值仍然相等，但摘要
現在取決於那把金鑰——而對「拿不到那把金鑰的人」來說，那份詞表就失效了：

```console
$ csv2 -hash license -i TARGET_PACKAGES.csv -o masked.csv -t
$ csv2 -contains ':hmac:' --include-headers -i masked.csv | cut -f3
license:hash                       # 無金鑰——字典適用

$ csv2 -hash license -keyfile k.bin -i TARGET_PACKAGES.csv -o masked.csv -t
$ csv2 -contains ':hmac:' --include-headers -i masked.csv | cut -f3
license:hmac:289b9391              # 有金鑰——附上所用金鑰的指紋
```

**`--yes` 同樣會選定一把金鑰，因此它同樣選定了演算法。** 它的意思是「使用預設金鑰、不再詢問」，
而那對 `-hash` 而言，正是 `:hash` 與 `:hmac:<指紋>` 之間的差別：

```console
$ csv2 -hash license -i pkgs.csv -o m.csv -t          # license:hash
$ csv2 -hash license --yes -i pkgs.csv -o m.csv -t    # license:hmac:9c65c01a
```

因此，為了讓腳本不需互動而加上 `--yes`，會在 rc=0 之下換掉演算法；把它拿掉，又換回來。

**但它不會讓那一欄對「這台機器上的其他人」保密。** 預設金鑰是這台主機上的一個**檔案**，而
`--yes` 是一個「有文件記載的、一個單字」的方式去請 csv2 用它——於是一個本地讀取者可以造出
與你相同的表：

```console
$ printf 'w,license\n1,Zlib\n2,MIT\n3,GPL-2.0\n' > words.csv
$ csv2 -hash license --yes -i words.csv -o rainbow.csv -t
$ csv2 -contains ':hmac:' --include-headers -i rainbow.csv | cut -f3
license:hmac:9c65c01a               # 與你的檔案帶著同一個指紋
```

以摘要對接，字典裡有的值全部還原——在一個授權欄上實測是 6/6，比無金鑰那種**還多一個**，
因為有金鑰的摘要碰撞更少。標記甚至會公告用的是哪一把金鑰，而這份文件把那個指紋印了出來。
**`--yes` 的用途是「不要問我」，不是「不要讓這裡跑得動 csv2 的人看到」。** 要防本地讀取者，
請用一把他們讀不到的 `-keyfile` 金鑰；不防任何特定對象時，無金鑰的形式對「它是什麼」是誠實的。**檔案會記錄下發生的是哪一種**——那正是標記的用途——但兩個以不同方式雜湊的檔案
永遠不會相等，於是跨檔案的比對會安靜地一個都對不上。請針對每一欄決定一次，並以「標記」
而不是「命令列」為準。由 T142 斷言。

只有在值空間確實夠大時才選無金鑰的形式——長的自由文字欄位、不透明的識別碼——或者
你其實並不需要對「拿到檔案的人」隱藏那些值。

### `-hash`、`-encrypt`、`-decrypt` 是「編輯」

它們會重寫每一筆紀錄，因此行為上屬於編輯動詞而不是選取動詞——而這件事到 2026-08-21 之前
沒有寫在任何地方，於是一個「選取」與其中之一併用時，把自己寫回了它自己的輸入。

- **在 `--in-place` 之下不得與選取併用。** `-head 1 -hash col -i f.csv --in-place` 會被拒絕，
  理由與 `-head 1 -t --in-place` 相同：那個選取沒有指名的紀錄會被丟掉。
  `-r -hash col --in-place` 沒問題——它重寫每一筆、不丟掉任何一筆。
- **沒有目的地時，它們把 CSV 寫到 stdout。** 它們是「沒有 `-o`／`-so`／`--in-place` 的編輯
  會被拒絕」那條規則的例外；那條規則點名的是 `-insert`、`-append`、`-delete`、`-update`，
  而它指的就是那四個。
- **它們一律寫出標頭**，給不給 `-t` 都一樣，因為標記住在那裡，而一個「沒有標記」的遮蔽檔案
  無法被正確讀回。在 `.csv2` 上，兩列標頭都會被標記。
- **它們會寫下那一行「結果」**——`wrote N records, M fields, atomic rename OK`——與其他每一次
  寫入相同。2026-08-21 之前它們不會，於是這份文件叫稽核者去找的那一行，獨獨在「無法還原」
  的那幾種寫入上不存在。

### 受保護的欄位會在檔案中被標記

`-hash`、`-encrypt`、`-decrypt` 會改寫**標頭**，讓檔案記錄下對哪一欄做了什麼：

| 標記 | 意義 |
|---|---|
| `license:hash` | 無金鑰的 SHA-256 |
| `license:hmac:<指紋>` | HMAC-SHA256，`<指紋>` 標識所用的金鑰 |
| `license:enc:<指紋>:<salt>` | 已加密；`-decrypt all` 會找出這些 |

**一份 `.csv2` 的兩列標頭必須帶著同一個標記，而兩列互相矛盾的檔案會被拒絕**——每一個動詞、
在其他一切之前，並且指出是哪一欄、以及兩列各說了什麼。每一項「這一欄是否受保護」的檢查讀的
都是標頭，而到 2026-08-25 之前，它們讀的都是 0a 那一列：一個「0b 說 `:enc:`、0a 沒說」的檔案，
從它們全部旁邊走了過去——於是 `-update` 把明文寫進加密欄，而 `-hash` 覆寫了 `:enc:` 標記、
連同 salt 一起帶走，rc=0，而那個檔案的中文標頭列上 `:enc:` 明明還在。「兩列都讀、取聯集」會
修好那些漏接、卻留下一個自相矛盾的檔案；而「兩個來源互相矛盾」時，這個工具的做法是拒絕。

一個以 `:hash`、`:hmac:<指紋>` 或 `:enc:<指紋>:<salt>` 結尾的欄名因此是**保留字**：一個純粹
叫做 `secret:hash` 的欄位會被當成受保護的，csv2 會拒絕編輯它——安全的那一邊，而那則訊息描述的
是一個它讀錯了的檔案。請把那一欄改名。

定址仍使用原本的欄名：遮蔽之後 `-update 3:license` 照樣可用。對已標記的欄位再次遮蔽
會被拒絕，而不是疊加一層——**兩個方向都是**。2026-08-20 之前，每個動詞只找自己那一種標記：
對 `:enc:` 欄位下 `-hash` 是被接受的，而那是這個工具做得出來最糟的一件事——它把「密文」
單向雜湊掉，並連同 salt 一起覆寫 `:enc:` 標記，rc=0、不印任何東西，而事後拿正確的金鑰去解，
得到的是 `no encrypted columns found`。那條規則是通則，而實作是兩個「各自只認得自己」的
特例。由 T124 斷言。

`--json` 的鍵維持乾淨的欄名，因此同樣的標記改為出現在 metadata 那一行：

```console
$ csv2 -head 1 -t --json -i masked.csv
{"meta":{"format":"csv","headers":1,"fields":7,"protected":{"license":"hmac"}}}
```

沒有任何欄位受保護時，該鍵完全不會出現。

## 索引 sidecar

關於那個 `.index` 檔案的一切，寫在同一個地方——因為那段警告你的文字原本指向這裡，而這裡
先前什麼也沒有。

**它是什麼。** `packages.csv` 對應 `packages.csv.index`——完整檔名加上 `.index`，因此
`foo.csv` 與 `foo.csv2` 永遠不會相撞。它存的是每 256 筆一個的位元組偏移量與實體行號、
紀錄總數、一個 `no_embedded_newlines` 旗標、資料檔的一份戳記，以及涵蓋它自己的檢查碼。
它是衍生物，永遠不是真相的來源：把那個名字放進 `.gitignore`。

**什麼時候會出現一份。** `--build-index` 任何大小都會建。否則只以副作用出現，而且只在
`CSV2_INDEX_MIN_BYTES`（16 MiB）以上：一次「會重寫檔案」的編輯會建，`-tail` 因為本來就要
讀到結尾也會建，而 `-append --in-place` 也會建，因為它同樣讀到結尾——它必須先證明檔案的
最後一筆是完整的，才能在其後加上位元組。`-mid`、`-contains`、`-r`、`-get` 永遠不會建。
一次追加是「延續」一份已經存在的索引而不是重建它，那也是這個工具裡唯一一處「索引被編輯」
而非「被推導」的地方。

**誰會讀它。** `-contains`（用來把檔案切成區塊）、`-mid` 與 `-tail`（用來 seek）。
`-get` 與各個編輯動詞是掃描的，不理它。`--no-index` 把上述全部關掉。

**它被拿來對照什麼，以及那擋不住什麼。** 使用之前比對：資料檔的大小、**精確到奈秒**的 mtime、
首尾各 64 位元組的雜湊，以及索引自己的檢查碼。那是 O(1)，而它是一個啟發式——一個「讓上述全部
維持不變」的改動不會被偵測到，而那種改動是存在的：以相同的位元組數覆寫一筆紀錄，再把 mtime
原樣還原。`--verify-index` 是 O(n) 的那個答案，它把索引的四項宣稱拿去對資料；成立時以 0 結束，
不成立、或根本沒有索引時以 1 結束，並且「每一項不成立的宣稱印一行」。

**從它得到的位址，會錯的兩種方式。** 一份戳記仍然接受的過期 sidecar（如上），以及「檔案在你的
兩個指令之間被改了」——後者與 sidecar 無關，也沒有任何旗標擋得住。請在編輯「之前」驗證，不是
之後：一次會重寫檔案的編輯會順手修好 sidecar，於是事後的 `--verify-index` 報告的是「你已經
改過的那個檔案」。

**為什麼它永遠不是必要條件。** 每一個操作在沒有它時給的是同一個答案。過期、截斷、損毀、
版本落後——一律丟棄改用掃描，沒有一個是錯誤，因為一個會很快給你錯資料的索引，比沒有索引更糟。

### 環境變數

每一個的存在理由都是**讓它的邏輯能被測試**，而不是為了調校：一個不能被調低的門檻，
唯一的測試方式就是真的產生它本來要防的那種資料（例如一個 16 MiB 的 fixture）。

| 變數 | 預設 | 作用 |
|---|---|---|
| `CSV2_INDEX_MIN_BYTES` | 16 MiB | 低於此值時，不會以「副作用」的方式讀寫索引。`--build-index` 是明確的要求，任何大小都會寫出一份 |
| `CSV2_PARALLEL_MIN_BYTES` | 16 MiB | 設成大於檔案大小即可強制走單執行緒 |
| `CSV2_PARALLEL_MAX_BYTES` | 1 GiB | 「同時在飛的區塊」可以持有的上限。它管的是**輸出**片段——一整批必須被保留，才能依區塊順序寫出，而那正是平行輸出能與單執行緒逐位元相同的原因。讀取側不需要上限：一個工作者以 64 KiB 為單位讀自己的區塊，從不多持有。調低它會讓同時在飛的區塊變少、其餘排隊；`-debug` 會說出來，並帶著數字。**它不是行程的記憶體上限**——設成 8 MiB 時實測峰值 RSS 仍是 58 MB，因為固定的工作集不在它管轄的範圍內 |
| `CSV2_PARALLEL_CHUNK_BYTES` | 4 MiB | 調小可讓小檔案也切出多個區塊，區塊邊界才真的被測到 |
| `CSV2_PRETTY_MAX_BYTES` | 16 MiB | `-md --pretty` 超過此值時拒絕，而不是被 OOM 殺掉。**它量的是「要對齊的那批資料」，不是輸入檔**——`--pretty` 必須把整張表握在手上才能算出欄寬。因此「任意大的檔案取一個切片」永遠沒問題：在一個 23 MB 的檔案上 `-mid 150000,150004 -t -md --pretty` 對齊的是 237 bytes 的材料，成功；而同一個檔案上的 `-r` 會被拒絕。**這個上限不是行程記憶體的上限**：對齊 15 MB 的材料，峰值 RSS 是 81 MB，大約 5 倍——那張表在算繪之前是以「紀錄」的形式握著的。2026-08-21 之前這一列說那個切片「只持有 9 MB」，而 9 MB 是 `csv2 -tail 1` 也要付的——行程的地板，卻被釘在這一列存在所要教的那個概念上 |
| `CSV2_MAX_BUFFER_RECORDS` | 1,000,000 | `-tail N` 與 `-B N` 的上限。要求超過此值會被**拒絕，而不是截斷**——一個看起來像完整答案的短答案，正是這支工具存在所要避免的失敗。訊息會指出請求值、上限值與該變數——而且引用的是「使用者實際打的那個旗標」，因此同樣會設定 before 側的 `-C 6` 會被回報成 `-C 6`，不是 `-B 6`。2026-08-21 之前，`-B` 那則訊息只說了三者中的兩個，而 `-C` 被回報成 `-B` |

**平行化只適用於 `-contains`，別的都不適用**，而且必須以下每一項都成立。單是設定上面那兩個
旋鈕，並不會讓一次執行變成平行的：

| 條件 | 理由 |
|---|---|
| 是搜尋，且未給 `--filter` 或 `-md` | 那兩者會送出紀錄，而分塊會讓紀錄失序 |
| 沒有 `-A`/`-B`/`-C`，沒有 `-head`/`-tail`/`-mid` | 上下文與位置是相對於「一個分塊看不到的串流」而言的 |
| 沒有轉換、沒有編輯 | 那些會寫入，而寫入端不分塊 |
| `-i FILE`，不是 stdin | 分塊需要 seek |
| 不只一個核心 | |
| 至少 `CSV2_PARALLEL_MIN_BYTES` 那麼大 | |
| **一筆一行** | `.csv2` 保證了這件事。`.csv` 只有在「有一份掃描過該檔、並記下沒有內嵌換行的索引」時才符合——用 `--build-index` 建立一份。這是「平行路徑」的條件，不是 seek 的條件：自索引 v4 起，`-mid` 與 `-tail` 的 seek 對任何有索引的檔案都適用，因為每個格點都帶著自己的行號 |

最後一列才是會令人意外的那一條。**一個含有內嵌換行的 `.csv` 永遠走不到平行路徑**——而那正是
「想構造一個跨越分塊邊界的測試」時最想拿來用的案例。

**`-debug` 一律會說出走的是哪一條路**，包括走的是普通那一條時，以及為什麼：

**「拒絕」不算在下面這句裡**：結束一次執行的那兩行錯誤，兩行都是 `csv2: <訊息>`，沒有時間戳、
也沒有層級，而它們的範例就是照實印出來的樣子。
每一行診斷訊息實際上都以 `csv2: <ISO-8601 時間戳> 層級 ` 開頭，而本文件裡的範例**省略了那個
前綴**，好讓訊息本身能放進一行。此處完整顯示一次，讓腳本可以照著「真正的形狀」去寫：

```console
$ csv2 -r -i pkgs.csv -debug     # 2>&1，全部四行
csv2: 2026-08-20T19:32:39.922+08:00 INFO  csv2 -r -i pkgs.csv -debug
csv2: 2026-08-20T19:32:39.922+08:00 DEBUG single-threaded: not a search; parallelism applies to -contains only
csv2: 2026-08-20T19:32:39.922+08:00 DEBUG format=csv fields=4 records=2
csv2: 2026-08-20T19:32:39.923+08:00 DEBUG metrics: read_bytes=103 file_bytes=103 peak_rss_bytes=8962048
```

**第一行是那筆「呼叫」紀錄，層級是 `INFO`。** 它與 `-log` 寫下的是同一行，而 `-debug` 把門檻
降得夠低，因此它也會出現在 stderr 上——於是一個去讀「`-debug` 輸出第一行」的腳本，拿到的是
那個指令，不是那個診斷。這個區塊到 2026-08-21 之前，在一段「把它當成真實形狀提供給你」的
文字裡，只印了四行中的一行。

以下省略該前綴：

```console
$ CSV2_PARALLEL_MIN_BYTES=1000 CSV2_PARALLEL_CHUNK_BYTES=512 \
      csv2 -contains xyz -i big.csv2 -debug      # 2>&1，在一個 2,980 bytes 的檔案上
DEBUG parallel: 6 chunks, 10 workers, chunk 512 bytes
DEBUG parallel: 199 records, 0 matched
$ csv2 -contains xyz -i pkgs.csv -debug
DEBUG single-threaded: .csv with no index proving one record per line; build one with --build-index
$ csv2 -r -i pkgs.csv2 -debug
DEBUG single-threaded: not a search; parallelism applies to -contains only
```

**第一行裡那兩個環境變數不是裝飾。** 沒有它們，那個指令印出的是
`single-threaded: file is 2980 bytes, under CSV2_PARALLEL_MIN_BYTES (16777216)`
——與這個範例要展示的正好相反——因為一個小到能印在這裡的 fixture，遠低於 16 MiB 的門檻。
**一個逐字執行會給出相反答案的範例，比沒有範例更糟**——而到 2026-08-21 之前，**這個**就是
那種範例：它指名的是上面那個 44 bytes 的 `pkgs.csv2`，而那低於同一行所設下的 1000 bytes
門檻，因此那行印出來的 `parallel:` 不可能發生；9 個 512 bytes 的區塊也需要大約 4.6 kB。
這裡用的檔案是 199 筆 `row<N>,value<N>`，而它做的就是印出來的那件事。

只回報「有趣的那一種」會讓沉默變得有歧義，而那個歧義正好咬在這裡：拿一次「平行」執行去比對
一次單執行緒執行，若兩者其實悄悄走了同一條路，那什麼也證明不了——而「輸出相同」看起來
恰恰就是那個樣子。由 T72 斷言。

**而當一個 `.csv` 走上平行路徑時，它所相信的那個 sidecar 會被指名**：

```console
$ csv2 -contains xyz -i pkgs.csv -debug
DEBUG parallel: trusting index pkgs.csv.index, which declares no_embedded_newlines;
      if the file changed since that was built while keeping the same size and mtime,
      record numbers will be wrong -- csv2 --verify-index -i pkgs.csv is the O(n) proof
DEBUG parallel: 6 chunks, 10 workers, chunk 4194304 bytes
```

2026-08-20 之前這一行並不存在，而那個不對稱正好反了：唯一「採信」索引的那條路徑什麼都不說，
而拒絕索引的那些路徑會說明自己。依下文所述那個 O(1) 戳記自身的限制，被採信的
索引可能是過期的——因此那是唯一可能靜默給出錯誤答案的分支，卻也是唯一不留痕跡的分支。讀
`-debug` 的人看得到 sidecar 為何被拒，卻永遠看不到它被信了、信的是哪一個檔案。由 T101 斷言；
該案例同時固定了這一行的另一個性質：**每次執行只印一次**，而不是每做一次資格檢查就印一次。
另外要留意這件事真的發生時，紀錄編號是從哪裡開始出錯的——不是從跨行的那一筆（它自己的號碼
存活了下來），而是從它之後的第一個區塊邊界開始，因為過期的 `no_embedded_newlines` 弄壞的是
「之後每一個區塊」的起始紀錄號。

**如果某一次執行不能接受那個風險，`--no-index` 就是答案**——而它值得在這裡被指名，而不是
留成一個「在別處被描述的機制」。它的意思是「絕不讀寫 sidecar」，於是搜尋會自己讀檔案、自己
數：比較慢，而且依構造就是對的。**慢多少，不只是那次掃描**：在 `.csv` 上它同時放棄了平行
搜尋，因為 `.csv` 需要一份索引才能證明「一筆一行」。在 17.7 MB / 450,000 筆上實測，
`-contains` 從 204 ms 變成 528 ms——2.6 倍，而 `-debug` 會說出是上述兩個理由中的哪一個。
在上面那個檔案上，被信任的過期索引回報 `40000:2`，而該筆
真正的位址是 `39999:2`；`--no-index` 回報 `39999:2`。`--verify-index` 從另一個方向回答同一個
問題——在你依賴那個 sidecar 之前先證明它，一次，而不是每次執行都做。

一位讀了這一節的盲測受測者，得到的結論是「沒有任何旗標能說『未經證明的索引就不要信』」。
有的；它只是從來沒有被寫成「你正在問的那個問題的答案」。


## 讀程式碼前值得先知道的幾項決定

以下每一項在 [plan/plan.md](./plan/plan.md) 中都有完整論證。

- **標頭是選擇加入的。** 未給 `-t` 時只輸出資料列，因為多數輸出會被接到下一個工具。
  但把不帶標頭的輸出寫進 `.csv`／`.csv2` 檔會被拒絕：那種檔案是在對自己的格式說謊。
- **用 `-update` 而非 `-set`。** `-insert`／`-update`／`-delete` 是 SQL 的既有詞彙，
  一起看就是一組。
- **刪除儲存格的意思是清空。** 真的移除該欄位會使該列少一欄、其後全部左移——正是本
  工具要防止的那類損壞，而且它不會報錯。
- **沒有 `-key` 旗標。** 命令列上的秘密在 `ps` 中可見，也會留在 shell 歷史裡。
  只提供 `-keyfile`。
- **正常路徑上不輸出任何訊息。** 會說話的 CLI 放不進管線。預設的記錄門檻是 WARN。
- **索引永遠是最佳化，永遠不是必要條件。** 沒有索引時行為完全相同。過期、截斷、
  損毀、版本不符——一律丟棄改用掃描，沒有一個是錯誤。一個會很快給你錯資料的索引，
  比沒有索引糟得多。這一點同樣涵蓋索引自身的內容：檔頭帶著一個涵蓋整份索引（含偏移量）的
  檢查碼，因此受損的索引會被丟棄而不是被跟隨，而下一個「寫入檔案」、或「本來就必須讀到
  檔尾」的操作——`-tail`、一次「會重寫檔案」的編輯——會寫回一份好的，**前提是那個檔案在
  `CSV2_INDEX_MIN_BYTES` 以上**：在門檻以下沒有任何東西會建 sidecar，因此受損的那一份就
  留在原地，每次讀取時被丟棄一次。`-append --in-place` 同樣會替換它，理由與 `-tail` 相同：
  它會讀到檔尾，以證明最後一筆是完整的。「本來就有效」的索引會被延續而不是重建；受損的
  那一份會被丟棄，並在原地寫上一份新的。單純的 `-contains`
  或 `-r` 會讀過
  每一個位元組卻不寫索引，因為建索引不是免費的，而一次「讀取」沒有被要求為它付帳；
  `--build-index` 那個條目從另一邊說的是同一件事。
  由 T68 斷言。
  **這個檢查碼不是什麼：** 它攔的是「損毀」——翻轉的位元、寫入不完整、被部分覆寫的檔案
  ——它不是簽章。能改寫偏移量的人，同樣能改寫另外八個位元組。它同樣幫不上「資料檔改變了，
  但大小、mtime 與首尾位元組都沒變」的情況；那正是 O(1) 檢查一直以來的本質：一個啟發式。
  **要用手佈置出那個情況，比聽起來難得多，而有兩個盲測回合因此推論「這個檢查比本段所說的更
  強」。並不是。** 被比對的 mtime 含**奈秒**，因此一個只帶整秒的 `touch -r` 就會讓它變動；
  替換必須逐位元組等長；而錯誤的紀錄號來自分塊搜尋，所以檔案得大到讓那條路徑真的啟動。
  三件同時做對，索引給的答案就會比掃描多一筆——已經重現過，並由 T143 釘住，讓它在本段仍如此
  宣稱的期間保持可重現。
  要證明，請執行 `--verify-index`，它之所以是 O(n)，正因為它非得是不可。**它證明的是**
  **它證明的是「索引那四項宣稱是準確的」，而不是「那些宣稱說了什麼」。** 在一個每隔一筆就
  跨行的檔案上，它照樣印出 `index OK`，因為索引正確地記錄了這件事。它不是用來問「這個檔案
  有沒有內嵌換行」的工具；回答那個問題的是搜尋時的 `-debug` 那一行，它說得很明確。
  它涵蓋索引的全部四項宣稱：格點偏移量、每個格點所指的行號、紀錄筆數，以及是否有紀錄跨行。
  行號那一項是 2026-08-21 加的，而這一段到 2026-08-22 之前都還寫著「三項」——正是這份文件
  本身一直在講的那種漂移。「是否跨行」那一項是 2026-08-19 才
  加上的，而它正是要命的那一項——平行路徑把「一行」當成「一筆」時，取用的就是這個宣稱；
  它是唯一沒有任何東西重新推導的宣稱；而破壞它的那種改動會讓另外兩項完好無損，因此只檢查
  那兩項時，對一份「接著就產生錯誤紀錄號」的索引回報了 `index OK`。由 T79 斷言。
  `packages.csv` 的 sidecar 是 `packages.csv.index`——完整檔名再加上
  `.index`，因此 `foo.csv` 與 `foo.csv2` 永遠不會相撞。那也就是要寫進 `.gitignore` 的
  那一行：它從資料檔衍生而來、永遠不是真實來源，因此不該提交，也不需要備份。
- **平行的輸出必須與單執行緒逐位元相同。** 那是驗收條件而非期望：本專案的失敗多半
  是靜默的，而平行化尤其擅長產生「大部分情況正確」的結果。
- **`--pretty` 以顯示寬度對齊，而那是第四個數字。** `套件名稱` 是 12 位元組、
  4 個碼位、4 個 grapheme cluster，以及 **8 欄**。Swift 的 `String.count` 給的是
  cluster 數，用它對齊在中文上就是錯的——而這在 emoji 出現之前就已經成立，因為
  `.csv2` 的第二列標頭就是繁體中文。

## 比較

[`compare/vs-sqlite.csv2`](./compare/vs-sqlite.csv2) 與
[`compare/vs-postgresql.csv2`](./compare/vs-postgresql.csv2) 逐項列出比較結果。
它們就以自己所描述的格式寫成——兩列標頭，第一列英文、第二列繁體中文——因此同時是
第一批真實的 `.csv2` 測試素材。

每一列都有 `basis`（依據）欄，標明該項是在此地**實測**、取自**已記載**的行為、
由工作的形狀**推論**而得，還是**UNMEASURED**（尚未量測，不可倚賴）。這一欄比結論本身
更重要：儲存空間各列是實測的，而全檔掃描各列不是。

那些表寫成時，理由是「還沒有 Swift 的 RFC 4180 解析器可以量」。現在有了，所以那些列
是量得出來的，只是還沒去量——一個比較站不住腳的理由；而表格仍標示 UNMEASURED，
因為那就是它們的現狀。

實測的儲存結果並非一面倒。相對 SQLite，CSV 在文字資料上較小（1.31 倍，若已建索引則為
1.75 倍），但在整數資料上**較大**（SQLite 為 0.75 倍）——因為 SQLite 存的是 varint，
CSV 存的是十進位數字的文字。

## 什麼時候該改用別的

> 超過約 1 GiB 且有寫入流量，或需要依鍵值查詢時，改用 SQLite。

每次編輯都會重寫整個檔案，因此改動 1 GiB 檔案中的一個儲存格要寫入 1 GiB，
而 PostgreSQL 只需約 10 KB。`-append` 是例外：它只寫入那一列的位元組。但它仍然會先讀過整個檔案（見上面的旗標說明），
因此省下的是寫入，不是時間。
查詢是依位置而非依鍵值，所以「找出 `pkg_name = busybox` 那一列」是全檔掃描。

真正的鄰居是 SQLite 而非 PostgreSQL——同樣是單一檔案、無 daemon、無 schema migration，
但它有 B-tree、page 級更新與交易。csv2 相對它只保有**一個**優勢：
**檔案仍是人看得懂、git diff 得出來的純文字**。對本專案而言那正是全部的重點，
因為兩次 CSV 事故都是從 git 還原的。
