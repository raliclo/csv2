# csv2

`csv2` 是以 Swift 撰寫的命令列 CSV 解析器與編輯器。它支援 RFC 4180
CSV、雙標頭 `.csv2`、Markdown 表格、JSON Lines、串流輸入輸出、索引讀取、
平行搜尋，以及受保護欄位。

English documentation: [README.md](README.md)。

## 狀態

解析器、編輯器、Markdown 讀寫、索引、平行搜尋、加密、記錄，以及跨平台建置
都已實作並由測試涵蓋。
公開 Swift module surface 已提供，並已在 macOS、aarch64 Linux、WSL 與 Windows
透過獨立 module／client 檢查完成驗證。

## 安裝發行版

每個版本發布三份封存，各屬於一個「既建得出、也驗得了自己」的平台——每一份都在它的執行檔被建置的
那台機器上打包，而打包腳本的結尾是**解開封存、執行解開後的執行檔、並讓它讀一個 CSV**。

```sh
curl -LO https://github.com/raliclo/csv2/releases/download/v0.1.0/csv2-0.1.0-macos-arm64.tar.zst
curl -LO https://github.com/raliclo/csv2/releases/download/v0.1.0/csv2-0.1.0-macos-arm64.tar.zst.sha256
sha256sum -c csv2-0.1.0-macos-arm64.tar.zst.sha256
zstd -d csv2-0.1.0-macos-arm64.tar.zst -c | tar -x
./csv2-0.1.0-macos-arm64/csv2 --version
```

另外兩個把 `macos-arm64` 換成 `linux-x86_64` 或 `windows-x86_64`。**aarch64 Linux 有測試，而它的封存
還沒發布**——單純是還沒在那台機器上建出來。

直到 2026-09-09 為止，這一段給了一個理由：「測試它的那個映像沒有 zstd」。**那是假的**，它有
`/usr/bin/zstd`。我讀到的是 Buildroot **上游自帶的範例 defconfig**，而不是這個專案實際餵給 Buildroot
的那份設定——後者寫著 `BR2_PACKAGE_ZSTD=y`，而且上方還有一段解釋為什麼需要它的註解。那之後的每一步
推論都成立，而且每一步都繼承了一個假前提。這個提醒比它取代的那一段更值得留著：**去問那台機器，
不要問描述它的檔案。**

用 Homebrew——這個 repo 就是它自己的 tap，不需要第二個：

```sh
brew tap raliclo/csv2 https://github.com/raliclo/csv2
brew trust raliclo/csv2
brew install raliclo/csv2/csv2
```

**`brew trust` 那一行不是可省的。** Homebrew 6 會拒絕載入一個未受信任的第三方 tap 的 formula，
而那則拒絕出現在 `brew install`，不是 `brew tap`。

用 Scoop：

```powershell
scoop install https://raw.githubusercontent.com/raliclo/csv2/develop/scoop/csv2.json
```

## 從原始碼建置與安裝

需求：Swift 6，並將警告視為錯誤。建置使用純 Swift 原始檔、Foundation 與
Dispatch，不使用 SwiftPM 或 SwiftNIO。

```zsh
./compile_csv2.zsh
./test/test_csv2.zsh
./install.zsh
```

建置腳本會自動辨識 macOS、Linux 與 Windows。POSIX 系統輸出
`release/csv2`，Windows 輸出 `release/csv2.exe`。`install.zsh` 接受：

| 旗標 | |
|---|---|
| `--dry-run` | 說出它會做什麼，不寫入任何東西 |
| `--prefix DIR` | 裝進 `DIR/bin`，不存在時建立 |
| `--dir DIR` | 就裝進 `DIR` 這個目錄，不存在時建立 |
| `--no-rc` | 不寫任何啟動檔——因此之後 `csv2` **不會**能用名字執行 |
| `--uninstall` | 移除那個執行檔，以及它寫下的那個區塊 |

它們可以組合：`--uninstall` 單獨使用時只看預設位置，會在什麼都沒移除的情況下以 0 結束，因此請把它
與你當初安裝時用的那個 `--prefix`／`--dir` 一起給。

**預設是 Homebrew 的 `bin`**——正是上一段叫你「經 ssh 的腳本不要用」的那個目錄。`--dry-run` 會印出
它。裝到別處會把先前的執行檔留在磁碟上並替換那個啟動區塊，於是舊的那個還在、只是不再被找到。

**它會寫 `~/.zshenv`**，不存在時建立；而 `--uninstall` 移除的是它自己標記的區塊，不是那個檔案。
rc=0 **不代表** `csv2` 可以用名字執行：在 `--no-rc` 之下明確地不代表——那也正是這支安裝器要去探測、
並把探測結果印出來的理由。

在 macOS 上，如果有「經 ssh 執行的腳本」需要找到它，請裝到 `/usr/local/bin` 而不是 Homebrew
的目錄：一個乾淨的非登入 shell，PATH 裡有 `/usr/local/bin`，而**沒有** `/opt/homebrew/bin`
——後者是 `path_helper` 從 `/etc/zprofile` 加的，那只在登入 shell 執行。install.zsh 會說出
你拿到的是哪一種。

## 格式

輸入副檔名會宣告格式：

| 副檔名 | 標頭 | 規則 |
|---|---:|---|
| `.csv` | 1 列 | RFC 4180；支援引號內逗號與換行 |
| `.csv2` | 2 列 | 英文與繁體中文標頭；引號規則與 `.csv` 相同（RFC 4180）——引號內的逗號與成對的雙引號都可用——**唯一的例外**是「一筆一行」：欄位內的換行以跳脫寫出而不是用引號包住，歸位字元亦然 |
| `.md` | 從表格還原 | Markdown 表格；文件有多張表時使用 `--md-table N` |
| 其他（`.txt`、`.log`…）或沒有副檔名 | 0 列 | 每行一欄；位元組原樣保留。`--json` 稱它為 `"format":"lines"` |

副檔名的比對**不分大小寫**（`DATA.CSV` 是一個 `.csv`），而當一個名字有好幾個副檔名時，**最後一個**
說了算——因此 `--backup` 寫出的 `data.csv.bak` 會被讀成逐行模式，而不是 CSV。`-o` 那個路徑的副檔名
同樣會宣告格式，並會與輸入的標頭列數對照檢查。`.csv2` 搭配 `--headers 0` 會留下 `"format":"csv2"`
與 `"headers":0` 並存。

**沒有副檔名的檔案沒有結構可與之矛盾，因此裡面沒有任何東西是可疑的。** `#`、一個 JSON
物件、一行 XML 宣告、一張 Markdown 表的資料列與它的 `|---|` 分隔列，全都會以自己的位元組
回來——那正是「一份含表格的文件可以逐行編輯」的原因。而一個 `.csv` 或 `.csv2`，若其中有一列分隔列
**而那列是該行唯一的欄位**，**會**被拒絕，因為那裡的副檔名宣告的是另一回事，而一個「只有一欄、
又長得像 Markdown」的檔案，是被冠上錯誤名字的 `-md` 輸出。兩欄檔案裡的 `|---|,2` 是資料、rc=0——
與底下 `#` 那條規則是同一個「恰好一個欄位」的述詞，而那則拒絕自己就說了：
「is a Markdown separator row **and has one field**」。

**空行在那裡也是一筆紀錄**，所以 `-insert N ''` 與 `-append ''` 會放進一個真正的空行——
散文絕大部分是空行，而一份插不進空行的文件不算可以編輯。`.csv` 與 `.csv2` 仍然拒絕 `''`，
因為那裡的副檔名已經說了一筆紀錄有幾欄，而空字串不是其中之一。

輸出的紀錄分隔符一律是 LF，而且 **CRLF 輸入在進來時會被正規化成 LF**——一個在 Windows 上
寫出的檔案讀得正確，出去時帶的是 LF 結尾，那是對**位元組**的改動，不只是對「新增內容」的改動。
`-debug` 會說出這件事（`input contained CRLF line endings; normalised to LF`）；正常路徑上不印
任何東西。加引號 CSV 欄位內的 CR 與其他位元組都是資料，會被保留。UTF-8 BOM 會被移除；
UTF-16 輸入會拒絕並提供轉換指令。

選取輸出預設不含標頭，給 `-t` 才會包含。把沒有標頭的資料列寫到
`.csv` 或 `.csv2` 路徑會被拒絕，因為副檔名會錯誤描述檔案。csv2 不會靜默
把單標頭格式與雙標頭格式互相轉換。

## 讀取與選取

```sh
csv2 -r -i data.csv
csv2 -head 10 -t -i data.csv2
csv2 -tail 5 -i data.csv
csv2 -mid 20,30 -i data.csv
csv2 -contains MIT -i data.csv
csv2 -contains MIT --filter -t -o matches.csv -i data.csv
```

`-contains --json` 會在兩行 metadata 之間，為**每一個命中的儲存格**輸出一個物件。下面是一個三筆
紀錄的檔案的**完整輸出**，不是節錄——直到 2026-09-07 之前，這個區塊在一個 `$` 提示符底下只展示了
**最後一行**、而且沒有省略號，那是這一頁裡最可能造出一個壞掉解析器的東西：

```text
$ csv2 -contains busybox --json -i test/fixtures/TARGET_PACKAGES.csv
{"meta":{"format":"csv","headers":1,"fields":7,"header":["pkg_name",…]}}
{"record":1,"field":1,"header_en":"pkg_name","value":"busybox","line":2}
…此處省略另外四行命中，值也已截短…
{"meta":{"records":21,"matched":3}}
```

那些 `…` 是**這一頁的**，不是程式印的：共有五個儲存格命中，分佈在三筆紀錄裡。直到 2026-09-07
之前，這個區塊在一個 `$` 提示符底下**只**展示了最後一行、而且沒有省略號，那是這一頁裡最可能造出
一個壞掉解析器的東西。

**那個紀錄形狀與 `-r --json` 用的不是同一個。** 一個命中的儲存格帶的是 `record`、`field`、
`header_en`（`.csv2` 還有 `header_zh`）、`value` 與 `line`，而且**完全沒有 `fields` 物件**——因此一個
對著 `.fields` 寫成的腳本，會在每一行拿到 `undefined`。在 `-A`／`-B`／`-C` 之下形狀又變回整筆紀錄
（有 `fields` 物件），並多出 `"match": true|false`——那是以程式分辨「命中」與「它的上下文」的唯一方法。

結尾的 `records` 是「紀錄編號走到了哪裡」，而 `matched` 數的是命中的**紀錄**——三筆紀錄裡的五個
儲存格會回報 `matched:3`，因此它**不是**上面那些命中行的行數。

讀取選項：

```text
-r                 讀取紀錄（預設）
-contains S        回報命中的儲存格：record:field TAB 欄名 TAB 值
--filter           搭配 -contains 時輸出命中的紀錄
--include-headers  搜尋標頭列
--normalize       **兩邊**都以 NFC 比對；可能讓命中變少，見下
-A N -B N -C N     命中前後的紀錄上下文
-head N -tail N    前 N 筆／後 N 筆紀錄；N 至少要是 1
-mid a,b           包含兩端的紀錄範圍；任一端可省略
-t                 輸出標頭列
-rownum            在最前面加入紀錄號欄位
--physical         在位址中加入來源行號；不可與 --json 併用
--a1               在位址中加入試算表 A1 表示法
-get r:c           輸出一個儲存格的值
-count             輸出這個檔案有幾筆資料紀錄
```

`-count` 輸出一行：資料紀錄的筆數。它**數**它們，但不檢查每一筆是否符合這個檔案的欄寬，因此它可以
對一個 `-r` 會拒絕的檔案自信地作答——20000 筆中第 15000 筆欄數不齊時，它仍以 rc=0 給出 `20000`。
它**會**檢查引號是否封閉，因此一個斷在引號中間的檔案會被拒絕。檔案旁有可用的 `.index` sidecar 時是 O(1)，否則是 O(n)，
而兩種情況都**不會**寫出 sidecar。只有標頭列的檔案數出 0，那不是錯誤。`--json` 的 meta 裡刻意
**沒有** `total`：那個數字只有在索引存在時才知道，因此那個欄位會時有時無，而讀不到它的呼叫端
分不出「空檔案」與「這次執行沒有索引」。

**`-o` 必須指向一個一般檔案。** `-o /dev/null` 會被拒絕，而那則拒絕說出了原因：`-o` 會在目的地旁邊
寫一個暫存檔再改名，而一個裝置節點做不到這件事。要丟棄輸出，請改用 `-so` 重導。

**`-count` 不接受同伴，並且會逐一指名地拒絕它們。** 這裡的「同伴」，指的是任何會改變**產出什麼**的
東西——一個動詞、一種輸出形狀、一個目的地、一次搜尋。只改變「同一個計數怎麼得到或怎麼回報」的旗標
——`--no-index`、`--headers`、`-debug`——不是同伴，仍然可用。 它是一次「整個檔案」的計數，除此之外什麼都
不做，因此把它與一個動詞、一種輸出形狀或一個目的地併用都會被拒絕：那則拒絕恰好列出**被打出的**
那些旗標。直到 2026-09-08 為止，那些旗標是「被接受並丟棄」、rc=0——
`csv2 -count -update 1:1 X -i f.csv --in-place` 印出一個數字，而檔案逐位元未變；
`-contains ZZZ -count` 回傳的是整個檔案的筆數，於是「有幾筆提到這個」拿到的是一個回答了另一個
問題的合理答案。`--no-index`、`--headers` 與 `-debug` 不屬於這個意義下的同伴，仍然可用。

**`-mid a,b` 的 `a` 在最後一筆之後是錯誤**，而訊息會說出總筆數。`b` 在最後一筆之後則不是：一個
起點在檔案內、卻要得比現有的多的視窗，有一個明確的答案——現有的這些。這個不對稱存在，是因為空
輸出與「這幾列真的是空的」分不出來——那正是 `-get` 越界一直都是錯誤的同一個理由。

紀錄號計算資料紀錄，不是實體行。

**標頭位址是 csv2 會「印出來」的東西，絕不是你可以「寫進去」的東西。** 定位報告為 `.csv` 的標頭印
`0`、為 `.csv2` 的兩列印 `0a`／`0b`——而**沒有任何動詞收它**。`-get 0:1`、`--search-cell 0a:1` 與
`--search-row 0` 全部會被拒絕。要搜尋標頭列，請用 `--include-headers`。直到 2026-09-07 之前，這句話
只給出那兩種寫法而沒有任何這樣的警告，而且它就夾在 `-get r:c` 與 `--search-cell R:C` 之間——那兩個
都是**收位址**的。

`-contains` 預設搜尋所有欄位；使用 `--search-cell R:C`、
`--search-row R` 或 `--search-column C`，即可限定只搜尋一格、一筆或一欄。
這些範圍選項**彼此**互斥，且必須搭配 `-contains`；它們**各自**都能與 `--filter`、`-A`／`-B`／`-C`、`-rownum` 與 `--json` 配對——但那四個**彼此之間**
並非都相容：`-rownum --json` 會被拒絕，`-rownum` 用在定位報告上也會。在 `.csv2` 上，欄名必須來自**英文**那一列標頭。

`--filter`、`-A`／`-B`／`-C` 與 `--normalize` 同樣需要 `-contains`，少了它們會這樣說。
**一次沒有命中的搜尋仍然以 0 結束**，因此 `if csv2 -contains X …; then` 在每一個檔案上都成立
——那與 `grep` 的行為不同。

定位報告的格式是 `record:field`、TAB、欄名、TAB、值。值裡面的 TAB 會寫成 `\t`、換行寫成 `\n`、
反斜線寫成 `\\`，因此一行永遠只描述一個儲存格，而那個分隔符不可能出現在儲存格內部。
`--a1` 會把試算表的格號加進位址：`2:2 [B3]`。它的**列號**是「標頭列數 ＋ 紀錄號」——**不是實體行號**
——因此一個含有引號內換行的值，會讓兩者分開。它需要 `-contains`，並且與 `--filter`、`-md`、`--json`
併用會被拒絕。A1 只會被**印出來**、絕不會被接受：`-get C3` 會像標頭位址一樣被拒絕。

`-rownum` 是在**紀錄**前面加上一欄紀錄號。在定位報告上它是**惰性的**——會被接受、然後被忽略——因為
那份報告的位址本來就帶著紀錄號，而 `-rownum` 只作用在輸出側：它**絕不可以**改變一個位址的意義。
在 `--json` 底下它則會被**拒絕**，因為在那裡它不只是惰性的：`--json` 是替欄位命名而不是編號，
那一欄無處可去。

那份報告的欄名欄位跟隨 `--en`／`--zh`，預設是英文——即使那個命中的值來自 `.csv2` 的中文標頭列。

`-A`／`-B`／`-C` 不是「加在那份報告上」——它們**取代**它，改為輸出整筆紀錄，並在**不相鄰**的群組之間
放一行 `--`。重疊的群組會合併成一個，而且沒有分隔線。

`--normalize` 會在比對之前把**搜尋字串與儲存的文字兩邊**都正規化成 NFC，而它可能讓一個命中
**消失**：在一個存著 `Jos` 後接結合用尖音符的檔案裡，`-contains Jos` 命中原始位元組，而在 NFC 之後
不命中——因為把那個重音組合起來之後，`s` 被換成了 `ś`。它從不改變被儲存的東西。
欄名不可包含 `:`，因為該字元保留給 `r:c` 定址語法。`:hash`、`:hmac:` 與 `:enc:`
後綴是 csv2 保留的保護標記，不是使用者定義的欄名。

## 輸出格式與串流

```sh
csv2 -r --json -i data.csv2
csv2 -r --json --json-ascii -i data.csv2
csv2 -r -t -md --pretty -i data.csv2
csv2 -r -si --headers 1 -so < data.csv
```

`--json` 輸出 JSON Lines；第一行與最後一行是 metadata，中間才是紀錄。
第一行 metadata 會帶 `header`——欄名，依**檔案自己的順序**；`.csv2` 還會帶 `header_zh`，
也就是第二列標頭在相同的位置上。因此消費端可以使用任一列標頭，**而且知道欄位的順序**——
那是一個 `fields` 物件的鍵給不了的東西。只要那個檔案**有**標頭列，`header` 就一定在——
因此沒有標頭列的 `.lines` 檔**完全不帶 `header` 這個鍵**，而不是帶一個空陣列；從那裡讀
欄序的腳本必須預期這件事。若要在**不讀紀錄**的情況下取得欄序，只取第一行即可：
`csv2 -head 1 --json -i f.csv | head -1`。沒有「只回傳標頭」的動詞。沒有標頭列時，`fields` 物件
以「位置的十進位字串」為鍵——`{"1":"one"}`——因此一個依**欄名**寫成的腳本在那裡拿到的是數字，
而不是一個錯誤。

meta 行的 `fields` 是**標頭的寬度**：三欄的 CSV 是 3，而**只要沒有標頭列就是 0**——`.lines` 檔，
或任何以 `--headers 0` 讀的檔案。`0` **不表示**寬度不固定：一個以 `--headers 0` 讀的 `.csv` 仍然把
它釘在第 1 筆，仍然會拒絕欄數不齊的檔案。只有在它非零時，才用它來決定列的大小。直到 2026-09-07
之前，這裡寫的是「0 表示不固定」，而那句話恰好在「會回報 0 的那種執行」上為假。

`--json-ascii` 會跳脫非 ASCII 字元，**而那是一個「分行」的保證，不是外觀選項。** 純 `--json` 會把
U+0085、U+2028 與 U+2029 以原始位元組輸出。那是合法的 JSON、也是合法的 JSON Lines——紀錄分隔符是
`\n`，`jq` 與 `while IFS= read -r` 都不受影響——但一個依 **Unicode 行邊界**分行的消費端（Python 的
`str.splitlines()` 就是這樣做的）會在字串中間看到一個換行，拿到無法解析的碎片。`--json-ascii` 把
三者都跳脫掉，而且不花任何代價。

`-md` 與 `--json` **互斥**，而且會明講；沒有任何一次執行能同時輸出兩者。

**`meta.format` 的值是 `csv`、`csv2` 或 `lines`，而一張 Markdown 表回報的是 `csv`。** 一個 `.md`
輸入會在任何讀取者看到它之前先被轉換成 CSV，因此消費端**無法**用這個欄位分辨 Markdown 表與 CSV；
需要知道時請看路徑。

**`meta.records` 是「紀錄編號走到哪裡」，而它對除了 `-head` 與 `-mid a,b` 以外的每一個動詞都等於
檔案總筆數**——那兩個動詞會讓讀取者提早停下。它不是筆數，而且刻意沒有 `total`，見 `-count`。

**一次零筆紀錄的讀取，是兩行 metadata、中間什麼都沒有。** 一個只有標頭的 `.csv`，或一個以 `.lines`
讀取的空檔案，產生的正是那個。一個切「第 2 行到第 n-1 行」的消費端——那正是上面那個說法所**邀請**的
寫法——在這種檔案上會選到結尾那行 metadata 並在它上面失敗。請改用**結構**來選：紀錄行就是那個
**沒有** `meta` 鍵的行。

**`-t` 在 `--json` 底下會被接受但沒有效果**：標頭已經在 meta 那一行裡，它沒有東西可以加。它是被
忽略而不是被拒絕，這與 `-rownum` 不同——後者會需要憑空造一個鍵出來。

**在 `--filter` 之下，`--json` 輸出的是紀錄形狀**——`record`、`line`、`fields`——與 `-r` 相同，沒有
任何欄位指出是哪一格命中。那件事屬於定位報告。

**`--include-headers` 會多出第六個鍵與兩個 0。** 標頭列上的命中會輸出 `record: 0`、多一個值為 `"0"`
（`.csv2` 則是 `"0a"`／`"0b"`）的 `header_row`，而且**不會**讓 `matched` 加一——`matched` 數的是資料
紀錄。因此一支以 `matched > 0` 當閘門的腳本，會在串流裡明明有一行命中時回報「沒有命中」；而把
`.record` 餵回 `-get` 會被拒絕，因為沒有任何動詞接受標頭位址。

**一個提早停止的消費者拿到的是 141，不是 1——前提是輸出大到會塞住。** `csv2 -r --json -i big.csv |
head -1` 會讓 csv2 被 SIGPIPE 殺死，而 stderr 是空的，與「失敗」可以區分（後者是 1 加上一個錯誤
物件）。而在一個小到「整份輸出塞得進管線緩衝區」的檔案上，csv2 會在 `head` 關閉之前就跑完，狀態是 0。
因此請把 0 與 141 都當成「消費者提早停止」、把 1 當成失敗；**不要**把 141 當成必然。直到 2026-09-08
為止這一句是無條件寫的，而它在一個三筆的 fixture 上是假的——那正是任何人拿來驗證一個宣稱的檔案大小。

**在 `--json` 之下，一次被截斷的執行是可以用結構偵測出來的**，這與「錯誤」那一節描述的 CSV 輸出不同。
一個在中途發現的錯誤，會在 stdout 上留下**已經寫出去的**那些紀錄行，而**沒有結尾那行 metadata**。
要求那一行存在，是一個消費端能做的最便宜的完整性檢查；而且不論有沒有紀錄行流出去，它都成立：在小
檔案上，錯誤會在緩衝區沖出之前就被發現，於是 stdout 是空的——那同樣沒有結尾那行 metadata，同一個
檢查照樣接得住。

`-md` 輸出 Markdown，必須搭配 `-t`。`--md-style` 選擇排版，而這三個名字**只關於 padding**
——沒有任何一個會改動值：

| `--md-style` | 作用 |
|---|---|
| `preserve`（預設） | 保留**每一列你沒有動過的**原始間距。**在 CSV 輸入上沒有「原始間距」可保留，因此它的行為與 `compact` 完全相同**——如果你是要把一個 CSV 渲染進一份給人閱讀的文件，請指定 `pretty`。你編輯過的那些列會以精簡形式重新輸出，所以它的意思是「保留你沒碰的列」，不是「保留原始排版」 |
| `compact` | `\|zstd\|1.5.6\|BSD\|`——任何地方都沒有 padding |
| `pretty` | 把整張表的每一欄重新對齊到共同寬度 |

因此就地編輯一份文件時，`preserve` 給出最小的 diff，而那正是它是預設值的原因。在 CSV 輸入上，
那裡沒有「原始間距」可以保留，它的行為等同 `compact`。

**`--pretty` 就是 `--md-style pretty`**——同一個設定的兩種寫法，輸出逐位元相同，共用同一個上限。
直到 2026-09-07 之前，這一頁稱它為「另一個旗標」，而那正是一個讀者在「該用哪一個」時會依賴的句子。
兩者以**不同的值**同時給出時會被**拒絕**而不是替你決定，因為先前的結果取決於哪一個排在後面。
兩者都需要 `-md`，少了它會被拒絕。

對齊依的是**顯示寬度**，逐欄計算：每一欄的寬度是「它的標頭與它的儲存格之中最寬的那個」，兩側各加
一個空格。寬度量在**已跳脫**的文字上，單位是 grapheme cluster——一個 CJK 字元算 2、一個結合字元算 0，
而一個 ZWJ emoji 序列算**一個** cluster：那在「會把該序列算繪成一個字形」的終端機上是對的，在不會的
終端機上會窄兩欄。`.csv2` 量的是那個以 `<br>` 接起來的標頭字面值。

「為了對齊而必須持有整張表」正是 `CSV2_PRETTY_MAX_BYTES` 所限制的東西。超過它時，該次執行以 1 結束、
stdout 空白，訊息會指名兩個逃生口。**那個上限數的是「資料儲存格」已跳脫的位元組**，而
`CSV2_MD_MAX_BYTES` 數的是**輸入檔的原始位元組**。它們在下面那張表裡都寫成「16 MiB」，而它們量的
不是同一樣東西。

以 `--md-table N` 從一份文件中選出一張表時，每一筆 `--json` 紀錄上的 `line` 就是**文件裡**的
行號——與你的編輯器顯示的同一個數字——而 `--physical` 的 `@L` 也是同一個數字。一筆位於文件第 27 行
的紀錄就回報 27，無論那張表位於檔案多下面。

2026-09-06 到 09-07 之間，這裡寫的是相反的話：那個數字相對於表格，而這一頁叫你自己加上表格的偏移量。
**那個建議行不通**——`|---|` 分隔列在你的文件裡是一行、在翻譯後的表格裡不是，因此資料列的偏移是 +25、
標頭是 +24，而最直覺的實作會差一行。現在那個數字就是文件的，沒有東西要加。

`--physical` 不能與 `--json` 併用：它加的是「定位報告」裡的位址，而 `--json` 不產生定位報告。
請直接用 `--json` 自己的 `line`。

人類可讀的輸出可用 `--en` 或 `--zh` 選擇標頭語言。`--version`／`-V` 會印出
建置版本；`--help`／`-h` 會印出完整選項清單。

`-si` 從 stdin 讀取，`-so` 寫到 stdout；兩者都不會把整個輸入載入記憶體。
使用 stdin 時必須給 `--headers`，因為 stdin 沒有可以用來宣告格式的副檔名。

對**讀取**而言，`-so` 是預設值，給了它不會改變任何東西。對一次經由管線的**編輯**，它變成兩個
目的地之一，而其中一個是**必要的**——`-o FILE` 或 `-so`；`--in-place` 在那裡不可用，因為沒有一個
具名的檔案可以寫回去：

```sh
csv2 -update 1:1 'X' -si --headers 1 -so < data.csv
```

`-count` 與 `--in-place` 會直接拒絕 stdin，並指名 `-i FILE`。

從管線讀取**永遠是單執行緒**的，因此無論門檻允許什麼，`-contains` 在那裡都不會走平行路徑；而
`-debug` 會回報 `file_bytes=0`——那讓「索引」那一節描述的「`read_bytes` 對上 `file_bytes`」比較，
在管線上失去意義。那個比較是 2026-09-07 寫在這裡的，而當時沒有寫下「讓它成立的那個條件」。

**`--headers 0` 會把輸入逐行讀** —— 每行一個欄位，位元組原樣。那是「沒有 `.csv`／`.csv2`
副檔名的檔案」本來就有的格式，而在此之前它只能靠「**沒有**副檔名」來取得，因此 stdin 與散文
`.md` 都指名不到它。一個會宣告的副檔名拒絕的是**不一致**：
`.csv2` 搭配 `--headers 1`、`.csv` 搭配 `--headers 2`，兩者都是錯誤；而一個**與副檔名一致**的
`--headers` 會被接受，且什麼也不做。

**`--headers 0` 在每一種副檔名上都會被接受**，而它接下來的意思**取決於副檔名**——這一段值得讀兩次：

| 輸入 | `--headers 0` 的結果 |
|---|---|
| 沒有副檔名，或 `.txt`、`.log`… | 每行一個欄位、位元組原樣——逐行模式 |
| `.md` | 同上：散文，可以當成散文編輯並寫回去 |
| `.csv`、`.csv2` | 無標頭的 CSV——**仍然依逗號切割**，欄數由第 1 筆釘住 |
| stdin | 逐行模式；那裡必須給 `--headers`，因為沒有副檔名 |

所以在 `.csv` 上它只是拿掉那一列標頭，其餘不變。以那種方式讀一個欄數不齊的檔案仍然會被拒絕，
而訊息指名的是**第 1 筆**，不是一列並不存在的標頭。

這裡有兩句話直到 2026-09-07 都是假的，相距四行而且**彼此矛盾**：「`0` 無論副檔名說什麼都會被拒」，
以及「它是唯一一個副檔名蓋不過去的值」。那一天的一次修正改掉了同一段裡的 `--headers 1|2`，
而把這兩句留在原地。
以這種方式讀的 `.md` 是散文，可以當成散文編輯並寫回去——給那些「裡面**含有**一張表」而不是
「本身就是一張表」的文件用。

## 錯誤

錯誤會寫到 stderr，先是英文行、再是繁體中文行——**永遠恰好兩行**，或在 `--json` 之下恰好一個
JSON 物件。**每一次失敗都以 1 結束。**

**當錯誤是在讀到檔案中途才發現時，stdout 並不是空的，你必須檢查退出碼。** csv2 是串流的，而一個
會串流的工具，不可能同時保證「在它停下來之前沒有任何東西到達 stdout」：一個 537 KB、第 20001 筆
有問題的檔案，寫出了 19126 筆好的紀錄然後失敗，而**那份被截斷的輸出讀回來是一個完好的 CSV，
19125 筆，沒有任何標記**。`csv2 -r -i data.csv > out.csv` 而不檢查 `$?`，就是「安靜地得到一個變短的
檔案」的方法。

直到 2026-09-07 之前，這一節寫的是 stdout 保持空白「因此可以安全接在管線中處理」——那與四節之外的
串流保證互相矛盾。**假的是那個承諾。**

**csv2 會停在第一個錯誤。** 一個有兩處壞紀錄的檔案，只會回報第一處，對第二處隻字不提，因此清理一份
同事給的檔案，是「一個錯誤一趟」。沒有一個「一次列出全部」的模式：要回報第二個錯誤，就得先決定第一個
錯誤**是什麼意思**，而在那裡猜錯，正是一個修復工具弄壞檔案的方式。請預期要反覆幾次。

在**開始讀取之前**就發現的錯誤——不能併用的旗標、找不到的檔案、副檔名衝突——確實會讓 stdout 保持
空白，而那是其中的大多數。

在 `--json` 之下，一次拒絕是 stderr 上的一個物件，帶有 `code`、`message` 與 `message_zh`。
**這組 code 不是封閉的——請給你的消費端一個 default 分支。** 以下是已觀察到的：

| `code` | 由什麼引發 |
|---|---|
| `not-found` | 輸入、輸出或金鑰檔開不起來 |
| `unknown-flag` | 這個版本不認得的旗標 |
| `ambiguous-match` | 兩欄同名，因此一個位址解析不出來 |
| `invalid-input` | 一個檔案無法滿足的值或位址，以及**部分**旗標衝突 |
| `conflicting-options` | **其餘的**旗標衝突 |

直到 2026-09-08 為止，這裡寫的是「共有三個 code」，只列出第一、第四與第五個，而下一句就承諾
`code` 的值跨版本穩定——正是那句話讓一個封閉清單變成承重的。一支寫成三向分支加上
`default: unknown` 的腳本，在任何一個有重複欄名的檔案上都會掉進 default。**錯的是那個數量，不是那些
code**：每一個個別的條目都一直成立。

後兩者的分法跟隨的是「那個檢查寫在哪裡」，而不是一條你推論得出來的規則——`--physical --json` 回報
`invalid-input`，而 `-md --json` 回報 `conflicting-options`，兩者都是旗標衝突。請以退出碼分支，
或把這兩個 code 當成同一類。**不要依賴這組 code 是完整的**——這一段先前以一句「跨版本穩定」的承諾
作結，而正是那句話讓一個封閉清單變成承重的。英文版在 2026-09-08 拿掉了它，中文版多留了一個回合
（PR）。個別的 code 一直是穩定的；會變的是「總共有哪些」。

*這裡刻意不逐字重現那句被移除的話：一句假承諾被原樣抄進頁面裡，略讀的人看到的就是那句話，而釘住
這件事的測試也會抓到它自己（T295a 的第一版就是這樣失敗的）。*

`-get` 同樣拒絕 `--json`，而那個拒絕會**取代**你原本會拿到的錯誤——因此 `-get --json` 之下一個越界
的紀錄號，回報出來的是旗標衝突而不是那個範圍。

**一次失敗的編輯，會讓輸入逐位元不變。** `--in-place` 寫的是一個私有的暫存檔再 rename，因此不存在
「輸入寫到一半」的狀態；`-append --in-place` 是有記載的例外，它直接追加。那個保證先前只能從那個
例外反推出來。

**`#` 開頭的一行是資料，不是註解。** CSV 沒有註解語法，而一個叫 `#id` 的欄位是合法的，
因此跳過這樣的一行就等於去猜哪些行是資料。**觸發條件是欄數，而 `#` 只是選擇了訊息。** 一行在檔案的
任何位置、只要**恰好只有一個欄位**，就會以「指名那個 `#`」的方式被拒絕，而不是以欄數——因為對那一行
來說，欄數離原因有兩步之遙；出現在**中段**的 `#` 也會拿到那則訊息，並指名紀錄與行號。而一個欄數與
檔案相符的 `#` 行是**資料**：`#comment,x` 在兩欄檔案裡是紀錄內容、rc=0；`#x,y,z` 在兩欄檔案裡是普通
的欄數錯誤，從頭到尾不會提到 `#`。以 `#` 開頭的**標頭**是合法欄名——那正是上面兩句所說的「`#id`
是合法的」。

這一段先前有兩個版本，錯的方向相反。直到 2026-09-08 為止它寫的是「開頭有 `# ...` 的檔案」，那會
邀請讀者假設中段的 `#` 沒關係；而那次修正寫成「不論那一行在哪裡都會觸發」，那宣稱的又比程式守住的多。
隨那次修正寫下的測試之所以通過，是因為它的 fixture 剛好是一個單欄位的行——一個與程式一致、卻與它本該
保護的句子不一致的案例。

**要在不動那個檔案的前提下把它當成一行行來讀，用管線送進來**：`csv2 -si --headers 0 < FILE`。
以「沒有 `.csv`／`.csv2` 副檔名」的名字讀取效果相同；移除那一行則會讓它成為一份 CSV。注意：
在**有**那兩種副檔名的檔案上，`--headers 0` 的意思是「沒有標頭列的 CSV」而不是逐行——副檔名
已經宣告了逗號分隔。先前的訊息只說出那條要改檔名的路，於是一個讀到它的節點得出「這個檔案
根本讀不了」的結論。

## 編輯

```sh
csv2 -update 12:3 'new value' -i data.csv --in-place
csv2 -update-where 'pending' 'done' -i data.csv --in-place
csv2 -update 12:3 --value-file value.bin -i data.csv --in-place
csv2 -insert 4 'a,b,c' -i data.csv --in-place
csv2 -append 'a,b,c' -i data.csv --in-place
csv2 -delete 4 -i data.csv --in-place
csv2 -delete -cell 4:3 -i data.csv --in-place
csv2 -delete -col 3 -i data.csv --in-place
csv2 -add-column 3 'note,備註' 'todo' -i data.csv2 --in-place
```

支援的編輯動詞是 `-insert`、`-append`、`-delete`、`-update`、`-add-column`，以及依內容定位的
`-update-where`。**一次執行可以給好幾個動詞。**

所有**紀錄號**都以原始輸入為準，而每一次編輯都在同一次通過中套用——因此
`-insert 2 'NEW' -delete 4` 刪掉的是「插入**之前**排第 4 的那一筆」，不是插入之後排第 4 的那一筆。
（直到 2026-09-07 之前，這句話寫的是「所有索引」，而在這一頁裡「索引」在別處指的都是 `.index`
sidecar。）

**`-delete a,b` 刪掉的是一個包含兩端的「範圍」**，讀法與 `-mid a,b` 相同。要刪掉**不相鄰**的紀錄，
請重複那個旗標：

```sh
csv2 -delete 2,4 -i data.csv --in-place         # 刪掉 2、3 和 4
csv2 -delete 2 -delete 4 -i data.csv --in-place # 刪掉 2 和 4，保留 3
```

兩種寫法都以 0 結束、都不印任何東西，因此選錯的那一種會讓你少掉一筆紀錄，而沒有任何跡象顯示
發生過非預期的事。直到 2026-09-07 之前，這裡只出現過 `-delete 4`，於是一個有兩筆要刪的讀者
只能盲選。

`-insert N` 會讓新紀錄**成為**第 N 筆；原本在第 N 筆的那一筆與其後全部往後移。它不能定址到
「最後一筆的下一個」——那請用 `-append`。

`-delete -cell` 會清空欄位，
不改變欄數；`-delete -col` 會從每筆紀錄及每列標頭移除欄位。`-add-column N NAME VALUE` 會讓新欄位**成為**第 N 欄——原本在第 N 欄的那一欄與其後全部右移——並把
VALUE 寫進每一筆既有紀錄的那一格。在 `.csv` 上 NAME 是一個標題；在 `.csv2` 上它是兩個、以逗號分隔，
而省略繁中的那一半會留下空白標頭並發出警告。NAME **一律**以逗號切開，因此一個含逗號的標題無法表達。

**N 可以是「最後一欄的下一個」，而那會附加。** 在一個兩欄的檔案上 `-add-column 3` 是合法的，會把新欄
放在最後；`-add-column 4` 會被拒絕，而那則拒絕說出了規則——「this file has 2 columns, so the highest
position is 3, which appends」。**這與 `-insert` 相反**：`-insert` 拒絕「最後一筆的下一個」並要人改用
`-append`，因此從旁邊那個動詞推論出來的結果，恰好是反的。

**同一個 N 上的兩個 `-insert`，依它們被給出的順序解析**，所以 `-insert 1 A -insert 1 B` 會讓 A 在前、
B 在後。沒有東西被丟掉、也沒有東西被拒絕；一支由片段組出命令列的腳本，得到的是一個有定義的答案，
而不是一個意外。

`-delete -col` 可以重複，在一次執行裡移除好幾欄。

**任何接受欄號的地方都可以改用欄「名」定址**——`-update 1:license`、`-delete -cell 1:license`、
`-delete -col license`。名字與號碼都指向「**輸入裡**」的那一欄，因此一個位址在同一次執行裡與
`-delete -col` 或 `-add-column` 併用時仍然正確。直到 2026-09-07 之前並非如此：位址是對著**結構性
編輯之後**的標頭解析、再套到編輯之前的紀錄上，於是它會寫進隔壁那一欄，rc=0 而兩條串流都沒有輸出。

`--in-place` 透過私有暫存檔與 rename 寫回，`-append` 除外：它使用追加快路徑。
`-append` 寫入前會驗證輸入，只寫入新增的位元組，但仍會讀取既有檔案來驗證它——**整個**檔案，不只是最後一筆：對一個「8000 筆中第 5000 筆有錯」的檔案追加，會被拒絕並指名第 5000 筆。平行追加可保證完整寫入，但不支援一般平行編輯。

`-append --in-place` 不使用暫存檔，也不會 rename 結果；它會開啟既有檔案並直接追加。
如果程序在寫入開始後被訊號中斷，檔案可能留下部分紀錄。一般就地編輯所提供的「失敗時
原檔完整保留」保證，不適用於這條只追加的快路徑。

`--truncate-partial` 丟棄結尾不完整的紀錄——而那指的是**一件特定的事**：這個檔案結束在一個
**沒有被關閉的引號裡面**。一個「最後一行欄位太少」的檔案是**另一種**錯誤，它會被拒絕、不會被截斷。
它在**一般讀取**上也有效，不只在重寫時——而那正是一個手上拿著破損檔案的人想要的；它與 `-append`
併用會被拒絕，因為追加無法移除既有位元組。當它真的丟棄時，會在 **rc=0** 之下於 stderr 說出來：

```text
csv2: --truncate-partial discarded 12 bytes: an unterminated record beginning at byte 4
```

**一次成功的執行，stderr 並不一定是空的。** 警告是一行、只有英文、不改變退出碼；`-add-column`
少了繁中標題時也會發出一則。以上就是全部。

`-update-where OLD VALUE` 要求資料區中恰好有一個儲存格的完整內容等於 `OLD`。
零個命中、多個命中，或重複指定而命中同一格，都會在寫出任何內容前被拒絕。
這是整格更新，不是子字串取代。

`--value-file PATH` 與 `--value-stdin` 會把 `-update` 的值當成原始位元組讀取，包括結尾換行與空白。

**它們存在的理由是：一個命令列參數帶不了每一種位元組。** 一個參數是 NUL 結尾的字串，因此一個含有
NUL 的值會**在 csv2 看到它之前**就被切掉——靜默地、rc=0——而一個不是合法 UTF-8 的字面值則會直接被
拒絕。這兩個限制都不適用於這兩個旗標，而那正是要用它們的全部理由：

```sh
printf 'before\0after' > value.bin
csv2 -update 1:3 --value-file value.bin -i data.csv --in-place
printf 'from a pipe' | csv2 -update 1:3 --value-stdin -i data.csv --in-place
```

在這兩個旗標之下，`-update` **只收位址**——那個放值的位置消失了。它們必須恰好搭配一個 `-update`
（`-update-where` 不算），不可重複，彼此互斥，也不可與字面值或 `-si` 併用。`--value-file -` **不是**
stdin，它是一個名字叫 `-` 的檔案。一個空的**一般**檔案會被接受並把那一格清空（rc=0）；而一個目錄、
一個像 `/dev/null` 的裝置、以及一個不存在的路徑，都會被拒絕，並指名路徑與理由。

`--in-place` 可以與 `--value-stdin` 併用——這一頁別處那條「拒絕 stdin」講的是 `-si`（**輸入**），
不是「值從哪裡來」。

**怎麼把位元組讀回來。** `-get r:c` 會寫出被儲存的位元組，加上**恰好一個** LF 結尾，因此往返檢查是
`cmp <(csv2 -get 1:3 -i f.csv) <(cat value.bin; printf '\n')`。定位報告印不出非 UTF-8 的位元組，
會把那樣的儲存格呈現為 `<non-UTF-8: 58 ff 59>`；而 `--json` 會以 `invalid-input` **拒絕整個檔案**，
不會拿 U+FFFD 去替換。因此一個存著任意位元組的欄位，用 `-get` 讀得回來，用 `--json` 讀不回來。

`--dry-run` 目前預覽 `-update` 與 `-update-where`，會以 `old -> new` 印出每個變更儲存格，
且不寫入任何**資料**檔。但若你同時給了 `-log`，它在磁碟上並不是沉默的：那次預覽會被追加到記錄裡，
**包含那個新值**，後面跟著一行 `dry run: N change(s), wrote nothing`。**那一行對資料檔為真，
對它自己所在的那個檔案為假。** 直到 2026-09-07 之前，這一頁寫的是「不寫入任何檔案」，沒有任何限定。

其他編輯動詞會被拒絕，而不是回傳一個可能被誤認為「沒有變更」的空輸出。`--in-place` 搭配
`--backup` 會把原始輸入備份為旁邊的 `INPUT.bak`，若備份已存在則拒絕覆寫——因此**每個路徑只能用一次**，
第二次帶備份的編輯必須先把那個 `.bak` 移開。而一次**失敗**的編輯會把它剛取的備份移除，因為輸入並未
改變，而一個留下來的 `.bak` 會擋住之後每一次使用；在 2026-09-08 之前，一次失敗會永久燒掉那唯一的
一次機會。

**編輯根本不能搭配 `--json`**，因此你拿不到「一次編輯**自己的**錯誤」的 JSON 物件：把 `--json`
加到編輯上，會把原本該回報的東西換成 `conflicting-options`——那是一個關於「旗標」的拒絕，而不是
關於那次編輯的。**但你拿到的仍然是 stderr 上一個可解析的物件**，帶有 `code`、`message` 與
`message_zh`、離開碼 1——`csv2 -update 1:license X --json -i f.csv --in-place` 印出的正是那個。
所以一個消費端可以解析這個工具產生的**每一則**拒絕；它做不到的是「從 JSON 得知那次編輯**本來**
會如何失敗」，因為那次執行根本沒有走到編輯。

直到 2026-09-07 之前，這一段在這裡承諾了「編輯自己的錯誤」。而 09-07 的修正**矯枉過正**：它說一次
編輯的拒絕「永遠不會」是 JSON 錯誤物件，下面那張表則說它「只以 stderr 上的文字形式提供」——那等於
在叫一個腳本作者根本不要去解析，並讓他失去一條本來可以運作的程式路徑。

目的地是 Markdown 的編輯**必須同時**給 `-md` 與 `-t`，兩者都不是選配——`-t` 之所以必要，與讀取時
同一個理由：一張 Markdown 表少了標頭列就沒有形狀。本節的範例都是 CSV 編輯，因此兩者都沒有出現。編輯一個 `.md` 檔而不給它會被拒絕、
訊息會指名那個副檔名，而檔案不會被動到。搭配 `--md-table N --in-place` 時，只替換選定的表格；
周邊散文會被帶回，所有輸出行尾統一為 LF。`--dry-run` 在這裡的行為與在別處相同：印出每一個
變更的儲存格，且不寫入任何東西。在 2026-09-06 之前，上一句是**假的**——`--dry-run` 搭配 `-md`
會真的寫入，並在兩條串流都沒有輸出的情況下回報成功——那正是這件事現在被明講、而不是留給人
假設的原因。

## 保護與稽核記錄

```sh
csv2 -hash email -i data.csv -o masked.csv -t
csv2 -encrypt secret -keyfile key.bin -i data.csv -o encrypted.csv -t
csv2 -decrypt secret -keyfile key.bin -i encrypted.csv -o clear.csv -t
csv2 -log audit.log -update 1:2 value -i data.csv -o result.csv
```

沒有金鑰的 `-hash` 就是那個值的、**未加鹽的** SHA-256。它是單向的，也保留相等比較，但「未加鹽」
意味著任何人都可以把自己的猜測拿去雜湊再比對：對一欄 email 或郵遞區號而言，那等於把值還原回來。
**那正是「要給金鑰」的理由**，而不是它的一個精緻版本。

`-keyfile PATH` 從檔案讀取金鑰——至少 16 bytes，`head -c 32 /dev/urandom > key.bin` 是個好做法。
`--yes` 是**另一件事**，不是同一件事的另一種寫法：它使用一把**環境裡的**金鑰，位於
`~/.multissh/generated/mldsa44-ed25519.key.raw`，由 `mssh-keygen` 產生。以那種方式加金鑰的輸出，
只有在持有那個檔案的機器上才可重現，因此凡是你需要重現或備份的東西，請用 `-keyfile`。
兩者同時給時，`-keyfile` 勝出。

`-encrypt` 使用 ChaCha20-Poly1305，每次都用新的 nonce，因此同一份輸入加密兩次會得到不同的位元組；
兩份都解得開。

**`-hash` 與 `-encrypt` 不需要 `-t`**，給了也不會改變任何東西——上面的範例帶著它，而在 2026-09-07
之前它們是唯一的線索，讀者很合理地會推論那是必要的。這兩個動詞**一定**會寫出標頭列，因為保護標記
就在那裡。`-md` 編輯**真的**需要 `-t`；這兩個不需要。

受保護的欄位會標記在標頭裡：`name:hash`、有金鑰的雜湊是 `name:hmac:KEYID`、密文是
`name:enc:KEYID:SALT`。

第四個欄位是**每檔一個的 salt**，不是 nonce。直到 2026-09-07 之前，這一頁把它寫成 NONCE——那描述的是
「一個 nonce 覆蓋整個欄位」的 ChaCha20-Poly1305，**那是災難性的重用，而 csv2 並沒有那個設計**。真正的
AEAD nonce 是**每格一個**、藏在各自的密文裡；那正是同一個明文在同一欄的兩列中會加密成不同位元組的原因。

那兩個 `KEYID` 不是同一種東西：

| 標記 | `KEYID` |
|---|---|
| `name:hmac:KEYID` | 對某把金鑰**穩定**。同一把金鑰在每個檔案、每次執行都給出同一個值 |
| `name:enc:KEYID:SALT` | 對「金鑰**與**該檔的 salt」取的指紋，因此即使金鑰完全沒變，每次加密都不同 |

所以 `:enc:` 的 KEYID **只在單一檔案之內**標識那把金鑰。不要用它把檔案分組來找「哪把金鑰開得了它們」
——那什麼也找不到，而且每個檔案看起來都需要不同的金鑰。金鑰不對時由解密回報，它會說出兩個指紋並指名
那個 salt。

**一個加密欄位仍然洩漏什麼。** 密文是明文長度加 28 bytes 且沒有 padding，而它以 **base64** 儲存，
因此一個儲存格裡是 `4 * ceil((len + 28) / 3)` 個字元。長度因此是**以三為一階**可見的：0、1、2 位元組
的明文都存成 40 個字元，所以一個**空儲存格與一個 1 或 2 位元組的值分辨不出來**；3 與 4 位元組都存成
44 個字元。直到 2026-09-08 為止，這一段說的是空儲存格**分辨得出來**——它錯的方向是保守的（宣稱的
洩漏比實際多），但一個為了藏起空儲存格而去補齊值的讀者，是依據一句假話在行動，而一個要估算欄寬的
讀者，從這一頁算不出任何儲存長度，因為 base64 這件事整頁從未出現。

*直到 2026-09-08 為止，這一段說的是空儲存格**分辨得出來**。英文版當天稍早就改對了，而這一段在同一個
commit 裡被漏掉，於是兩份文件在一個與安全有關的宣稱上互相矛盾了一天。記在
`todo/known-defects.md` 的 PH；那一天的另一半，是這個註記本身先前寫成了現在式，讀起來像是在說
上面這段**仍然**是錯的（PQ）。*

欄位自己的名稱、其他每一欄、紀錄筆數與列的順序，全都是明文。**不會**洩漏的是
相等性：兩筆持有相同值的紀錄會加密成不同的位元組，而那正是它相對於 `-hash` 的具體優勢。

`-encrypt`、`-decrypt` 與 `-hash` 都接受 `--in-place`，而 `--backup` 對它們有效。直到 2026-09-07 之前，
`--backup` 在那裡被**靜默忽略**——rc=0、兩條串流都不印任何東西、明文被覆寫、旁邊沒有 `.bak`——偏偏在
那條「原檔一旦失去就無法復原」的路上。對一個已經加密的欄位再加密會被拒絕；對一個從未加密、或是被
雜湊而非加密的欄位解密，同樣會被拒絕——雜湊是單向的，沒有東西可以還給你。

「會把原始值放進受保護欄位」的編輯會被拒絕——而它涵蓋的動詞比「編輯」二字暗示的多：

| 對受保護欄位的動詞 | |
|---|---|
| `-update`、`-update-where`、`-delete -cell` | 拒絕 |
| `-append`、`-insert` | **拒絕**——一整筆紀錄會把一個原始值帶進那一欄 |
| `-delete -col` | **允許**——刪掉整欄不寫入任何原始值 |

在 `--json` 底下，一個受保護檔案的 meta `header` 帶的是**儲存時的**標記（`email:hmac:6e9c89ad`），
而每一筆紀錄的 `fields` 以**基底名稱**為鍵（`email`）——那也是你**定址時**使用的名字。兩者是刻意
不同的；要把它們依名字接起來的腳本，必須在第一個 `:` 處把標記切掉。meta 行還會多出一個 `protected`
物件，列出每個受保護的欄位與它的種類。

`-hash` 與 `-encrypt` 會標記 `.csv2` 的**兩列**標頭，因此一個有英文與中文標頭的檔案會得到
`license:hmac:KEYID` 與 `授權:hmac:KEYID`。

金鑰從檔案讀取，不接受命令列上的秘密值。`-debug` 將診斷寫到 stderr；`-log` 追加帶時間戳的操作
記錄——純文字、一行一筆、只追加、只有英文，檔案不存在時會被建立：

```text
2026-09-07T15:37:42.384+08:00 INFO  csv2 -log a.log -update 1:license <value> -i d.csv --in-place
2026-09-07T15:37:42.388+08:00 INFO  update 1:license: "MIT" -> "Zlib"
2026-09-07T15:37:42.398+08:00 INFO  wrote 2 records, 2 fields, atomic rename OK
```

第一行是把**值**遮蔽後的指令；`--value-file` 與 `--value-stdin` 會以它們自己的樣子被記下來，
因此那筆紀錄說得出「值從哪裡來」。直到 2026-09-07 之前，兩者都被換成 `<value>`，於是一次
`--value-stdin` 的執行與一次字面值的執行分不出來。

**那份記錄含有明文的儲存格資料，而且以 0644 建立。** 那正是它的用途——上面第二行才是讓這份紀錄
有價值的東西——但那意味著 `-update`、`-update-where`、`-delete` 與 `-delete -cell` 會把值寫進去，
`-delete N` 會寫進一整筆紀錄，而一次 `-contains` 搜尋會記下它的搜尋字串。**保護一個欄位，並不會
保護它旁邊的那份記錄**：請把它放在你放資料的地方，而不是放建置產物的地方。那份記錄**不會**含有的
是金鑰——`-keyfile` 記的是路徑，而在「金鑰該標識自己」的位置出現的是它的指紋。

沒有 `-key` 選項：命令列上的秘密會被其他行程看見，也可能留在 shell 歷史中。
請改用 `-keyfile`。

## 索引與效能

索引 sidecar 是完整資料檔名再加 `.index`，例如 `data.csv.index`。它只是最佳化，
不是資料來源，也不是必要條件：

```sh
csv2 --build-index -i data.csv
csv2 --verify-index -i data.csv
csv2 -contains needle --no-index -i data.csv
```

缺少、過期、損毀或不支援的索引會被**靜默地**捨棄並改用掃描。那次執行以 0 結束、答案正確，
而兩條串流都不印任何東西——因此一個你為了速度而建的索引，可能因為一次 mtime 變動就失去，
**而沒有人會告訴你**。讀取仍然正確，只是慢上許多。`-debug` 是唯一看得見這件事的窗口，它會印出
`index hit`，或印出它沒有用到索引的理由：

```text
$ csv2 -mid 500,500 -debug -i data.csv 2>&1 >/dev/null
csv2: 2026-09-08T01:17:16.211+08:00 DEBUG index hit: record 500 via grid point 257 at byte 6297
csv2: 2026-09-08T01:17:16.212+08:00 DEBUG metrics: read_bytes=65536 file_bytes=76898 peak_rss_bytes=9404416
```

每一行 `-debug` 都帶前綴、時間戳與等級，並且走 stderr。直到 2026-09-08 之前，這個區塊把那些訊息
展示成**裸的**，那是一份從未發生過的轉錄——與 2026-09-07 修正的 `-contains --json` 範例是同一個
毛病，而它之所以活下來，是因為釘住它的那個案例用的是**子字串**比對。

`read_bytes` 對上 `file_bytes`，就是「這個視窗是 seek 過去的、不是掃出來的」的證據；一個被捨棄的
索引會顯示整個檔案都被讀過。

**有些動詞會在你沒有要求的情況下建立 sidecar。** 在 `CSV2_INDEX_MIN_BYTES` 之上，`-tail` 與任何
`-update … --in-place` 都會在資料旁邊寫出一個，而且是**靜默的**——`-r`、`-count`、`-head`、`-mid`、
`-get` 與 `-contains` 不會。要阻止它請用 `--no-index`。直到 2026-09-07 之前，這一頁只為 `-count`
提到「不會寫」，那讓人把它讀成通則。

**編輯會維護索引，而不是讓它失效**，因此一個正在被編輯的檔案，它的 sidecar 仍然有用。例外是兩個
並行的 `-append --in-place`，其中第二個會警告它無法更新索引。

`--verify-index` 檢查的是 sidecar **自身的**完整性——它的檢查碼、檔頭與形狀——並在它不存在或無效時
以非零結束。它**不會**把索引拿去與資料比對，那是它自己的失敗訊息說的話，而這一頁直到 2026-09-07
之前用「完整驗證」說了相反的事。無法使用的 sidecar 會原封不動留在磁碟上；`--build-index` 會取代它。

`--build-index` **不理會** `CSV2_INDEX_MIN_BYTES`——明確的要求勝過啟發式——而把它與 `--no-index`
併用會以「兩者互相矛盾」被拒絕。`--no-index` 同時停用讀取與寫入 sidecar；「寫入」那一半只對上面
那兩個動詞有意義。

`-contains` 可以使用平行搜尋，而且**只有** `-contains`——一般讀取**永遠不會**平行，不論檔案多大。
輸出與單執行緒路徑逐位元相同。直到 2026-09-08 之前，上面那兩列的標籤是「完整讀取」，那邀請讀者去
期待 `-r` 會有那個加速；它們量的是一次掃遍全檔的**搜尋**。

底下每一條都必須成立，平行路徑才會啟用；而 `-debug` 會指名第一個不成立的：

| 條件 | 註 |
|---|---|
| 動詞是 `-contains` | 而且不是 `--filter`、`-A`／`-B`／`-C` 或 `--search-*` 範圍——那些每一個都會強制單執行緒 |
| 具名檔案，不是 stdin | 那個檔案必須可 seek |
| `.csv` 或 `.csv2` | 無副檔名的檔案與 `.md` 被排除；在 2026-09-08 之前強迫它們走上去會當機 |
| `.csv` 需要一個 `.index` | 「一筆一行」必須被**證明**，而只有建出來的索引能證明它——因此 `--no-index` 同樣會關掉 `.csv` 的平行 |
| 至少 `CSV2_PARALLEL_MIN_BYTES` | 邊界值算符合 |
| 不只一個核心 | |

```text
$ csv2 -contains x -debug -i data.csv 2>&1 >/dev/null | grep single-threaded
csv2: 2026-09-08T02:00:12.643+08:00 DEBUG single-threaded: .csv with no index proving one record per line; build one with --build-index
```

`CSV2_PARALLEL_MAX_BYTES` 限制「同時持有在手上的量」，它在底下那張表裡。

測試與調校使用的環境變數：

| 變數 | 預設值 | 用途 |
|---|---:|---|
| `CSV2_INDEX_MIN_BYTES` | 16 MiB | **自動**建立 sidecar 的最小檔案大小；`--build-index` 不理會它 |
| `CSV2_PARALLEL_MIN_BYTES` | 16 MiB | 平行搜尋的最小檔案大小 |
| `CSV2_PARALLEL_CHUNK_BYTES` | 4 MiB | 搜尋區塊大小 |
| `CSV2_PARALLEL_MAX_BYTES` | 1 GiB | 平行搜尋同時持有的檔案量上限 |
| `CSV2_PRETTY_MAX_BYTES` | 16 MiB | `--pretty` 可以持有的「**資料儲存格**已跳脫位元組」上限 |
| `CSV2_MD_MAX_BYTES` | 16 MiB | Markdown **輸入檔的原始位元組**上限 |
| `CSV2_MAX_BUFFER_RECORDS` | 1,000,000 | `-tail` 與上下文緩衝上限 |

## 測試與量測

```zsh
./test/test_csv2.zsh
../test_submodules/run_csv2_test.zsh
./verifications/measure.zsh
```

本地測試會回報通過、失敗與略過數量，任何失敗都以非零結束。母專案 runner
會在 aarch64 Linux guest 建置 csv2、比較 host 與 guest 輸出、執行 guest 測試，
並保存量測結果。

### 讀寫效能量測

以下是基準資料集的 wall-clock 完整執行時間，以微秒（µs）表示。這不是固定的每筆成本保證；
數字包含行程啟動、儲存裝置、資料集大小與主機條件。macOS 與 Windows 使用 200,000 筆
（25.4 MiB）；Linux guest 使用 20,000 筆（2.48 MiB），因此只能比較資料量相同的列。

每個數字都是**一次** `measure.zsh` 的執行——而它本身每一列都取 best-of-N——而每一欄就是它旁邊那個
檔案。這一頁上沒有別的東西是像這樣跨機器量測的，因此檔名直接寫出來，不用暗示：

| 欄位 | 檔案 | 量測時間 |
|---|---|---|
| macOS arm64，sparse image | `measure_output.txt` | 2026-09-10，`c0ea3c5` |
| macOS arm64，本機 SSD | `measure_output_macos_ssd.txt` | 2026-09-10，`c0ea3c5` |
| WSL2 x86_64 | `measure_output_linux_x86_64.txt` | 2026-09-10，`62d1e1c` |
| Windows x86_64 | `measure_output_windows.txt` | 2026-09-10，`62d1e1c` |
| Linux aarch64 guest | `measure_output_linux.txt` | 2026-09-08，早一個 commit |

`c0ea3c5..62d1e1c` 只動到 `verifications/measure.zsh`，`src/` 之下一個檔案都沒動，因此那四個
2026-09-10 的欄位跑的是**同一個** csv2。guest 那一欄比較舊，而它自己說了。

| 量測項目 | macOS arm64<br>sparse image | macOS arm64<br>本機 SSD | WSL2<br>x86_64 | Windows<br>x86_64 | Linux aarch64<br>guest |
|---|---:|---:|---:|---:|---:|
| 掃遍全檔的搜尋，單執行緒 | 544,000 µs | 534,000 µs | 1,179,000 µs | 1,822,000 µs | 62,000 µs |
| 掃遍全檔的搜尋，平行 | 205,000 µs | 201,000 µs | 456,000 µs | 820,000 µs | 71,000 µs |
| 小型耐久編輯 | 56,800 µs | 7,800 µs | 11,200 µs | 74,600 µs | 9,000 µs |
| 整檔重寫 | 1,258,000 µs | 587,000 µs | 1,323,000 µs | 2,131,000 µs | 150,000 µs |

**WSL2 有一欄，是因為它是這個專案測試迴路裡的一台機器，而直到 2026-09-10 為止它沒有。** 那正是
它的量測會覆蓋掉 guest 那一份的原因：`measure.zsh` 依 `uname -s` 為輸出檔命名，而兩個節點都是
Linux，於是一次「沒有自己位置」的執行，就跑到別人的位置去了。現在檔名帶上了架構，而且腳本會拒絕
覆蓋一個「`host` 行指名另一台機器」的檔案。

**那兩個 macOS 欄位是同一台機器、同一個執行檔、同一分鐘。** 唯一的差別是語料放在哪個檔案系統上。
兩個讀取列察覺不到它（2%），而兩個寫入列差了 **7.3 倍與 2.1 倍**。直到 2026-09-08 為止，這張表
只有一個 macOS 欄位，而且從未說出語料在哪裡——那讓一個**儲存效應**看起來像是 csv2 的性質。

**寫入列在多次執行之間會移動，讀取列不會。** 七次執行裡，sparse image 的小型編輯落在
35,800–56,800 µs、整檔重寫落在 1,201,000–1,322,000 µs；SSD 則是 5,800–7,800 µs 與
587,000–619,000 µs。兩個讀取列都在 2% 以內。而**兩種媒介之間**的小型編輯比值，2026-09-08 是
4.8 倍、2026-09-10 是 7.3 倍——同樣那兩個檔案系統，相隔兩星期。任一媒介上的**單一**寫入數字，
值多少就看它的區間說了多少，而那個區間比第一次量測所暗示的更寬。

**guest 的平行列比它的單執行緒列慢，而那就是真正的結果。** 在 2.48 MiB 的語料上，找邊界的那一遍
與工作者交接的成本，超過四個工作者省下來的：harness 回報 `speedup 0.88x on 4 workers`。它是一次
**真正的**平行執行——harness 現在會拒絕回報一個「沒有走它自己命名的那條路徑」的列——而它就是
「小檔案該不該平行」這個問題的誠實答案。

原始量測保存在 `verifications/measure_output*.txt`，由
`verifications/measure.zsh` 以 best-of-N 時間產生。
`RECORDS=20000 ./verifications/measure.zsh` 量測較小的語料，那正是與 guest 欄位做 like-for-like
比較的方式；這支腳本**不收位置參數**，給了會被靜默忽略。它也會自己在每一列上設定
`CSV2_PARALLEL_MIN_BYTES`，以強制該列所要量的那條路徑，因此執行前 export 那個變數不會有作用。

**語料放在哪裡，對這些數字的影響大於這一頁上的任何其他因素。** harness 會把語料造在它自己的目錄
裡，因此一份放在 sparse image 上的 checkout，量到的就是那個 sparse image。

### 平行搜尋吞吐量與 RSS

平行搜尋量測使用相同的 10,000,000 筆資料：`.csv` 檔案為
1,307,777,815 位元組，`.csv2` 檔案為 1,307,777,833 位元組。每筆資料都命中
`needle`。2026-09-10 於 `c0ea3c5`、macOS arm64（sparse image）量測，10 個工作者、4 MiB 區塊，
交錯執行三輪取最小值；時間與峰值 RSS 取自**同一次**執行。來源是
[`verifications/measure_parallel_rss_output.txt`](verifications/measure_parallel_rss_output.txt)，
而底下每一個數字都由測試套件對著它檢查。

**一個 `.csv` 必須有 `.index` 才會被平行搜尋**，因此底下的 `.csv` 各列都有一個。最後一列是同一個
檔案但沒有索引——它在那裡，是因為它同時是這裡最有用的一條調校事實，以及「這張表以前是什麼」的證據。

| 格式 | 索引 | `CSV2_PARALLEL_MAX_BYTES` | 時間 | 吞吐量 | 峰值 RSS |
|---|---|---:|---:|---:|---:|
| `.csv` | 有 | 預設 1 GiB | 9.781 秒 | 127.5 MiB/s | 52.89 MiB |
| `.csv2` | 不需要 | 預設 1 GiB | 32.814 秒 | 38.0 MiB/s | 52.12 MiB |
| `.csv` | 有 | 8 MiB | 39.601 秒 | 31.5 MiB/s | 51.28 MiB |
| `.csv2` | 不需要 | 8 MiB | 34.552 秒 | 36.1 MiB/s | 52.59 MiB |
| `.csv` | **沒有——單執行緒** | — | 30.492 秒 | 40.9 MiB/s | **9.28 MiB** |

**直到 2026-09-08 為止，這張表的兩個 `.csv` 列就是最後那一列。** harness 從不建立索引，而設定
`CSV2_PARALLEL_MIN_BYTES=1` 幫不上忙，因為阻擋者從來不是大小門檻。先前公布的數字是 34.886 秒、**9.28 MiB**
——而上面那個「沒有索引」的列，在 2026-09-10 以今天的程式碼重新量測，是 **9.28 MiB**。舊表那個
記憶體數字就是掃描路徑的記憶體，**到小數第二位相同**，隔了兩星期、而且 harness 已經重寫過一次。一張標題寫著「平行」的表，有一半的列回報的是
掃描路徑的時間與掃描路徑的記憶體；而 `CSV2_PARALLEL_MAX_BYTES` 那一欄——它存在的全部目的就是顯示
那個旋鈕的代價——恰好是在「那個旋鈕什麼都做不了」的地方量的：單執行緒路徑上沒有任何 chunk 在飛。
任何依 9.28 MiB 去開容器的人，開的是一次**掃描**的大小。

修正後的表說出兩件舊表說不出來的事：

- **去建索引。** 同一個檔案、同一次搜尋，31.150 秒變成 9.636 秒。
- **這裡的 cap 花掉時間、而且沒省下記憶體。** 有索引的 `.csv` 從 9.781 秒變成 39.601 秒，而峰值
  RSS 幾乎沒動。在「每一筆都命中」的情況下，峰值由**輸出端**主導而不是由飛行中的 chunk 主導，
  因此限制 chunk 只會掐住搜尋，卻碰不到真正大的那一塊。在命中率低的語料上，同一個旋鈕正是讓記憶體
  有界的東西——這也正是為什麼這是**一種工作負載的量測**，而不是一條規則。
- **而那個代價並不均勻。** 同一個 cap 讓沒有索引的 `.csv2` 慢 5%（32.814 → 34.552 秒），卻讓有索引
  的 `.csv` 慢 4 倍。而相隔兩星期的兩次「三輪取最小值」之間，帶 cap 的 `.csv` 那一列從 34.259 秒
  移到 39.601 秒——16%。所以要讀的是**比值**，不是小數第二位。

這是量測結果，不是效能保證；只有在二進位檔、資料筆數、主機、**儲存裝置**與搜尋條件相同時才適合
比較。它由 `verifications/measure_parallel_rss.zsh` 產生——那是與上面那支不同的腳本，而且**不在**
`measure_output*.txt` 這個 glob 的涵蓋範圍內——原始輸出見
[`verifications/measure_parallel_rss_output.txt`](verifications/measure_parallel_rss_output.txt)。

這裡的吞吐量由**輸出**主導，而不是由輸入位元組主導：每一筆都命中，而每一次命中都是寫出的一行。
那正是為什麼這張表的 MiB/s 與上一節的 `parallel` 那一列，在同一台主機、同一個執行檔上會差三倍
——它們量的是不同的瓶頸，而兩者都不是「csv2 的速度」。

## 什麼時候該停止使用它

下表每一列都是 2026-09-06 實測的，不是從舊清單抄過來的。原本在表上的**三項**已經移除，因為那些
功能做出來了——第三項是「不讀檔就計數」，`-count` 從第 8 階段起就回答了它，而這張表還在把讀者
送去做一次讀完整個檔案的 `--json`。它撐過了一次標註為 2026-09-01、且自稱涵蓋每一列的重新量測，
而那正是「該把每一列重跑一遍、而不是重讀一遍」的理由。

| 不提供 | 改用什麼 |
|---|---|
| 欄位投影（`-cols`） | `csv2 -r --json -i f.csv \| jq -r 'select(.record) \| .fields.license'`。`select(.record)` 不是可省的：少了它，兩行 meta 會以 `null` 的形式混進你的欄位清單。或逐格 `-get`，迴圈的上界用 `csv2 -count -i f.csv`。兩條路都經過 `--json`，而 `--json` 會**拒絕**一個含非 UTF-8 位元組的檔案——那種檔案 `-get` 讀得好好的 |
| 精確的「整格」搜尋 | `-contains` 是**子字串**比對，因此 `-contains MIT --search-column license` 也會找到 `MIT-0` 與 `NON-MIT`——限定欄位**不會**讓比對變成精確。`-update-where` **是**精確的（它的訊息是「no data cell equals」），所以兩種語意都存在，而只有其中一種能拿來搜尋。要精確計數：`csv2 -r --json -i f.csv \| jq -r 'select(.record) \| select(.fields.license == "MIT") \| .record' \| wc -l` |
| 不分大小寫比對 | 沒有任何東西做得到——`-contains mit` 找不到 `MIT`，**而且以 0 結束、什麼都不印**，那與「沒有這筆資料」無法區分。請自己折疊大小寫：`csv2 -r --json -i f.csv \| jq -r 'select(.record) as $r \| $r.fields\|to_entries[] \| select(.value\|ascii_downcase\|contains("mit")) \| "\\($r.record)\\t\\(.key)\\t\\(.value)"'` |
| 一次「不管在哪一欄」的搜尋 | `-contains` 比對的是**每一欄**裡的子字串，因此 `-contains MIT` 也會找到 `transMITter`——見下方最後一個範例。要限定範圍請用 `--search-column license`，或 `--search-row`／`--search-cell`。直到 2026-09-07 為止，這一列說「限定一欄」根本不提供，還警告計數會「安靜地錯」——而記載了那個解法的段落，就在它上面 260 行處 |
| 跳過 `#` 註解行 | 沒有任何東西做得到，而且是刻意的：`#` 是資料，而 `#id` 是合法的欄名，跳過它就等於去猜哪些行是資料。那道拒絕會在任何**只有一個欄位**的行上指名那個 `#`，不論它在哪裡——但觸發條件是**欄數**，所以 `#comment,x` 在兩欄檔案裡是資料、rc=0。要逐行原樣讀取，請以沒有副檔名的名字讀它 |
| 只讀標頭 | `csv2 -head 1 --json -i f.csv \| head -1 \| jq -r '.meta.header[]'`——那行 meta 帶著 `header`；沒有任何動詞只回傳欄名。輸入是 `.lines` 時根本沒有 `header` 這個鍵 |
| 在 `.csv` 與 `.csv2` 之間轉換 | 刻意拒絕。要自己做，`.csv` → `.csv2`：`csv2 -r -t -i p.csv -o work`（**`-t` 是必要的**，少了它標頭列會被靜默丟掉），接著 `csv2 -insert 2 '套件,版本,授權' -i work --in-place`，然後**把它改名**：`mv work out.csv2`。**改名才是完成轉換的那一步**；把那個沒有副檔名的路徑讀回來，得到的是 `.lines`——而它本來就是。反方向：`csv2 -r -t -i p.csv2 -o work`、`csv2 -delete 2 -i work --in-place`、`mv work out.csv`。csv2 不會發明一列沒有人給它的標頭 |
| 安全的並行寫入，**append 對 append 除外** | 請自己把寫入者排成序列；兩個寫入者會靜默地弄丟其中一次編輯——檔案仍然是**有效的**，活下來的是「最後把暫存檔改名」的那一版，因此失去的是一次編輯，而不是一種你會注意到的損壞。兩個並行的 `-append --in-place` 是例外：兩筆紀錄都會完整落地，而「後完成的那一個」會警告自己無法更新索引 |

這張表原本還說了一件事，現在不再說：**編輯 Markdown 表**已經支援，它在下方的範例裡。

它原本也說**以程式分辨不同的拒絕**可以用 `--json` 的錯誤物件做到；那一列在 2026-09-07 被移除，
理由是「一次編輯的拒絕只以 stderr 上的文字形式提供」。**那個理由是錯的**：一次帶著 `--json` 的編輯
會印出一個可解析的物件，`code` 是 `conflicting-options`。這個工具產生的**每一則**拒絕都是機器可讀的。
編輯給不了你的，是「那次編輯**自己的**錯誤」的 JSON——因為 `--json` 在編輯執行之前就被拒絕了。
那是一個比「移除那一列」所暗示的窄得多、也遠沒那麼嚇人的事實。

## 範例

自足：這裡每一道指令都對著第一個區塊建出來的檔案執行，而每一段輸出都是這個版本實際印出來的。

```console
$ printf 'pkg,version,license\n套件,版本,授權\nzlib,1.3.1,MIT\nzstd,1.5.6,BSD\n' > pkgs.csv2
```

讀出紀錄。兩列標頭不是紀錄，因此不會被印出來：

```console
$ csv2 -r -i pkgs.csv2
zlib,1.3.1,MIT
zstd,1.5.6,BSD

$ csv2 -r -t -i pkgs.csv2
pkg,version,license
套件,版本,授權
zlib,1.3.1,MIT
zstd,1.5.6,BSD
```

一格的值，以名稱定址，前後不帶任何東西：

```console
$ csv2 -get 1:license -i pkgs.csv2
MIT
```

**定位報告是以 TAB 分隔的三個欄位：位址、欄位名稱、值。** 它不是 CSV，而那是刻意的——一個含
逗號的值會弄壞 CSV 格式的報告：

```console
$ csv2 -contains MIT -i pkgs.csv2
1:3	license	MIT
```

**`--json` 會輸出兩行 metadata，而它們都不是紀錄。** 第一行說出 csv2 認為自己在讀什麼；
最後一行帶著計數。一個「把每一行都當紀錄」的解析器，第一筆輸入就會撞上它：

```console
$ csv2 -r --json -i pkgs.csv2
{"meta":{"format":"csv2","headers":2,"fields":3,"header":["pkg","version","license"],"header_zh":["套件","版本","授權"]}}
{"record":1,"line":3,"fields":{"pkg":"zlib","version":"1.3.1","license":"MIT"}}
{"record":2,"line":4,"fields":{"pkg":"zstd","version":"1.5.6","license":"BSD"}}
{"meta":{"records":2,"matched":0}}
```

一張 Markdown 表。兩列標頭以 `<br>` 分隔、裝在同一格裡，而 `--pretty` 是依**顯示寬度**對齊的，
因此那些中日韓標題各算兩欄：

```console
$ csv2 -r -t -md --pretty -i pkgs.csv2
| pkg<br>套件 | version<br>版本 | license<br>授權 |
|-------------|-----------------|-----------------|
| zlib        | 1.3.1           | MIT             |
| zstd        | 1.5.6           | BSD             |
```

**動手之前先看見那次編輯。** `--dry-run` 印出將要發生的改變，而且不寫入任何東西：

```console
$ csv2 -update 1:version '1.3.2' --dry-run -i pkgs.csv2 --in-place
update 1:version: "1.3.1" -> "1.3.2"

$ csv2 -update 1:version '1.3.2' --backup -i pkgs.csv2 --in-place
$ csv2 -r -i pkgs.csv2
zlib,1.3.2,MIT
zstd,1.5.6,BSD
$ ls pkgs.csv2*
pkgs.csv2	pkgs.csv2.bak
```

**以「內容」定位的編輯，在命中不唯一時會拒絕**，而且會列出它找到的每一個位址，不會替你挑一個：

```console
$ printf 'k,v\n甲,乙\na,x\nb,x\n' > dup.csv2
$ csv2 -update-where x Z -i dup.csv2 --in-place
csv2: -update-where "x": more than one data cell matches (1:2, 2:2); refusing an ambiguous update
csv2：-update-where「x」：有多個資料儲存格符合（1:2, 2:2）；拒絕這個有歧義的更新
```

**在 `--json` 之下，拒絕是程式讀得懂的**——stderr 上的一行，帶一個穩定的 `code`。結束狀態
仍然是 1：

```console
$ csv2 --json -i nosuch.csv
{"error":{"code":"not-found","message":"cannot open input file: nosuch.csv","message_zh":"無法開啟輸入檔：nosuch.csv"}}
```

**還有一個值得看一次的陷阱：** `-contains` 是「跨每一欄」的子字串搜尋，因此它也會在另一個值
的內部找到那個字：

```console
$ printf 'pkg,license\n套件,授權\nzlib,MIT\ntransMITter,BSD\n' > lic.csv2
$ csv2 -contains MIT -i lic.csv2
1:2	license	MIT
2:1	pkg	transMITter
```
